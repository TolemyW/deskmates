# Approvals

The broker lives in `src/approvals/`: `approvals.ts` is the `approvals` table, `rules.ts` the per-bot rule store, `broker.ts` the decision path. It implements ADR-0002 amendment 2.

**Decision order: risk tier → matching rule → thread.** The tier check runs in the sidecar's `PreToolUse` hook, so only L2 calls reach `POST /internal/runs/:runId/approvals`; anything else is 400. The broker then looks for a stored rule on the requesting bot (`findMatchingRule` from contracts, oldest rule first). A match settles the request at once — `allow` or `deny`, an `approval` ledger event `{phase: "rule_matched", ruleId, …}`, nothing posted to the thread. Only an unmatched request becomes a thread message.

**The request is a `system` message.** `ThreadRouter.postSystem` appends it with an `{name: "approval", mimeType: APPROVAL_ATTACHMENT_MIME, ref: <approvalId>}` attachment, routing-inert (`{ inert: true }`): it wakes no member (ADR-0002 amendment 3, A4). Members read it in their next delivery, where the sidecar renders it as `[system: approval notice]`, and may decide it then. The body is built only from the `ToolAction` (tool name, target origin, argument summary or a 500-character slice of the raw input) and from the originating instruction (`approvals/instruction.ts`): the human message reached by walking the requesting run's wake chain past bot messages and run-naming `system` notices, else the bot message that woke the run, never a notice. A cron or webhook run has no thread, so `broker.noticeThread` gives its request, and its continuation request, the bot's canonical private chat (ADR-0024) as the approval's `threadId`; the card, echo, reminder and expiry land there while the run stays threadless (A9, `approvals/threadless.test.ts`). It never carries a tool result: page text is what approvals exist to catch.

**Nothing secret-shaped reaches the thread.** `src/approvals/secret-shaped.ts` is a pure `scrubSecretShaped(value, secrets)` that walks the `ToolAction` and replaces bearer tokens, `sk-…` keys, `authorization` / `cookie` / `set-cookie` / `x-api-key` lines, the credential environment variables, credentials in a query string, any property whose key names a credential, and the Gateway's own upstream model token by exact match. `broker.request` scrubs the action before it is stored, posted into the thread or put in the `posted` event, so the approval card — the one place a raw tool input is shown to a human verbatim — cannot carry a token. The sidecar redacts first (`packages/sidecar/src/redact.ts`); the two copies of the patterns are deliberately not shared, because this one has to hold when the sidecar's is old or broken. When the scrub finds anything, the run also gets a `log` event `{source: "approval_guard", redactedFields: <n>}`, so a sidecar that failed to redact is visible in the ledger rather than silently cleaned up after.

**Presence decides live wait vs defer.** `src/events/presence.ts` counts open `/api/events` connections; `humanOnline()` is "at least one". With a human online the run moves `running → waiting_approval_live` and the route answers 202, which tells the hook to poll `GET /internal/runs/:runId/approvals/:approvalId` for the rest of its short wait. With nobody online the route answers 200 `{decision: "defer", reason: "nobody online"}` straight away and the sidecar parks the run rather than burning the wait.

**Deciding.** Any member of the thread may decide: a human through `POST /api/approvals/:id/decide` (`decidedBy` `human:<authorId>`), a bot through `POST /internal/runs/:runId/approvals/:approvalId/decide` (`decidedBy` `bot:<botId>`), which requires that the calling run's bot be a member of the approval's thread, that it be neither the requesting bot nor upstream in the requesting run's wake chain (a continuation request is exempt from the upstream check: its delegator decides it, ADR-0016 decision 3), and that it decide `allow_once` or `deny` only (ADR-0002 amendment 3, A10; `approvals/bot-decision.ts`). Such a refusal is 403 `forbidden` with `details.refusal` `self_approval`, `delegator_approval` or `bot_allow_always`, and the approval stays pending. Membership is routing, not access control — a deciding bot is a soft boundary of the same kind as `SOUL.md` and workspace grouping (ADR-0004), not a security boundary. A second decision for the same approval is 409 `invalid_transition`. `allow_always` also stores a rule, linked back by `createdFromApprovalId`, from a stable target and never from the displayed summary (ADR-0002 amendment 3, A6; `approvals/always-rule.ts`): `matcherFromAction` proposes the tool plus the sidecar's stable `argumentPattern` with the origin beside it (a shell line's program and subcommand, a click's side-effect phrase, `agent <type>: *` for a subagent spawn, a hash pattern for exact code or terminal input, a connector or integration action), else a file tool's directory prefix, else the origin, else the input's `inputSha256`. The human may send an edited `matcher` with the decision, which is stored as edited. Before anything is decided the Gateway refuses, as 400 `validation` with `details.reason`, a matcher whose `argumentPattern` ends in the truncation marker `…` (`rule_pattern_truncated`), one that does not match the answered action (`rule_does_not_match_action`), and an action with no stable target and no edit (`rule_no_stable_target`); the request stays pending. A pattern without `*` that is not the sidecar's own pattern, or an input hash, is stored with `warnings: ["exact_arguments"]` or `["exact_input"]`, because such a rule matches only this action again. The rule routes refuse the truncated pattern and return the same warnings. Rules stored before A6 are matched exactly as before. Every decision is an `approval` ledger event and a short `system` echo in the thread carrying the same attachment, so the UI updates the card in place. A decision while the run is `waiting_approval_live` moves it back to `running` and the hook's next poll returns; a decision on a parked run is picked up by the scheduler.

**A deny says who denied it.** The `ApprovalResponse` the hook polls (and the immediate answer to a rule match) names the denier: `Denied by human: <reason>`, `Denied by bot <botId>: <reason>`, `Denied by rule <ruleId>[: <reason>]`, or the same without the `: <reason>` tail when none was given. The bare reason on its own reads to the model as the *site* refusing — it goes on to report that the console blocked the submission with "…" — which is a different fact from a human having said no.

**Unattended requests expire (ADR-0002 amendment 3, A7 and A8, accepted 2026-10-17).** `approvals/expiry.ts` runs in every scheduler pass (at least once a minute). A pending tool or egress request older than its workspace's `approval_expiry_minutes` (default 60 since ADR-0002 amendment 6 D7, 1 to 1440, changed with `expiryMinutes` on `PUT /api/workspaces/:id/auto-approval` by an Owner or Admin, audited as `workspace.approval_expiry_set`) is denied as `system:expiry` with the fixed text "Nobody approved this within N minutes. It was not done. Do not try to reach the same effect another way; report what is blocked, then continue with other work or end."; the hook's deny reason is that text, a parked run resumes with it in its `approval` trigger (`reason`), the thread echo reads `Expired by system:expiry: …`, and an `expired` event follows `decided`. A request still waiting for its automatic review expires the same way. When a third of the window is left the sweep claims `approvals.reminded_at` and posts one routing-inert `Reminder: …` line carrying the approval attachment, which a channel bound to the thread relays to its human, re-publishes the approval to the inbox and appends a `reminded` event. Continuation requests keep their own 24-hour window.

**Resume and the attempt key.** A parked run is `waiting_approval` with a `resume_payload_json` naming the SDK session, the approval, the deferred `toolUseId` and the `currentOrigin` the parked process reported. `RunStore.listResumable()` returns those whose approval has a decision, oldest first; `Scheduler.tick` launches each one whose lane is free, and the launch itself is the `waiting_approval → running` transition, so repeated ticks, a double kick, or a Gateway restart on the same database all resume exactly once. `reconcile()` after a restart only fails lane-holding runs and leaves parked ones alone. A resumed run is a second sidecar process of the same run row: `runs.attempt` goes up by one, the run gets a fresh token, and the `StartRunRequest` carries `attempt`, the stored `sdkSessionId` and `trigger: {kind: "approval", approvalId, decision, toolUseId, currentOrigin?, deferredAction}`. Because the sidecar's event counter restarts at 1 in every process, ledger redelivery is keyed on `(run_id, attempt, sidecar_seq)`, and `POST /internal/runs/:runId/events` requires every item's `attempt` to equal the run's current one.

**Usage is per attempt and summed per run.** `run_usage` is keyed on `(run_id, attempt, model)` (migration `0007`), not on `(run_id, model)`. The SDK reports a session's cumulative totals, so a resumed process that reports 160 after the parked one reported 100 turns into a delta of 60; under the old key that delta *replaced* the parked attempt's row and the run was billed for 60 of the 160 tokens it spent. `UsageStore.record` takes the run row's current `attempt` and writes that attempt's row; `UsageStore.list(runId)` — which is what `GET /api/runs/:id` and any cost report read — returns one `RunUsage` per model with the four counts added up across attempts and `costUsd` the sum of the attempts that had a price, null only when none of them did. `listByAttempt` is the row-by-row view for the ledger and its tests.

**The origin and the deferred action cross the process boundary.** The resumed process is a new Playwright MCP session, so it knows neither the page the decision was taken about nor which call it was for: a browser `ref` is local to one snapshot. `run_ended(deferred)` therefore reports `currentOrigin`, which `RunLifecycle.ended` stores in `resume_payload` and `RunLifecycle.resume` puts back on the trigger, so the resumed hook can derive a `targetOrigin` before it navigates. The trigger also carries `deferredAction` — `(toolName, targetOrigin?, argumentPattern?)` read off the approval row's stored action, defined fields only — which is what the sidecar matches a retry on when the replayed call fails. A run that parked without an origin gets no `currentOrigin` key at all: a wrong origin is worse than none.

**Gateway events carry the run's attempt.** `EventStore.append` stamps an input with no `attempt` of its own with the run's current `attempt` (from the `runs` row, 1 when there is none), so `resumed`, `decided` and rule changes land on the process they belong to instead of always on 1, and `RunEvent.attempt` is set on every event the store returns.

**A parked run holds its thread.** A parked run does not occupy its bot's lane (ADR-0005), but it still owns the `(bot, thread)` SDK session it will resume, and decision 3 forbids two processes in one session. `Scheduler.tick` therefore skips a queued run when `RunStore.parkedInThread(botId, threadId)` is true — a run of the same bot in the same thread is `waiting_approval` or `waiting_browser` — and it skips it without claiming the lane, so runs of that bot in other threads and runs of other bots start as usual. The held run starts on the pass after the parked one has resumed and ended.

**Approval mode (ADR-0002 amendment 6; reviewer from amendment 4).** `workspaces.approval_mode` is `manual`, `automatic` (a new workspace's default) or `approve_all`; `GET`/`PUT /api/workspaces/:id/auto-approval` read it (a member) and change it (an Owner or Admin, `{mode}`, the legacy `{enabled}` meaning automatic or manual), each change one `workspace.approval_mode_set` audit row (`approvals/auto-approval.ts`). After the stored rules, `broker.request` asks `ApprovalReviews.mode(run)`. In `approve_all` the request is created already decided `allow_once` by `mode:approve_all` (audited, an `approval` event `mode_allowed`, nothing posted); an egress ask is allowed only after `approvals/approve-all.ts` added its host through `replaceEgressAllowlist` as `mode:approve_all` (the internal route does that before calling the broker) and is recorded `allow_always`, and a host that is not a public hostname goes to humans; a stored deny rule still answers first. In `automatic`, an unmatched L2 request goes to `ApprovalReviews.queue` (`approvals/auto-review.ts`) before anything is posted. `auto-review-policy.ts` refuses, deterministically, egress asks, continuations, unclassified tools, credential-bearing actions, permanent deletion and permission expansion; browser actions are reviewable. `queue` also refuses a run whose wake chain reaches no instruction (a human message, a scheduled task's message, a cron prompt, a webhook body or a welcome prompt, labelled in the package as `instructionSource`) and a run whose last five reviewer verdicts were denials. A refused request is posted to humans exactly as in `manual`, with an `approval` event `review_skipped` naming why. An eligible one gets a review run (row first, `runType = approval_review`, the action's sha256, the policy version and the model in `config_json`, the review package frozen in `triggerPayload.prompt`); nothing is posted, the requester waits live whoever is online, and an event `review_queued` names the review run. The scheduler starts a review run without waiting on its bot's lane, at most `REVIEWS_PER_WORKSPACE` (2) at once. The sidecar runs it as a tool-free one-turn model job (`packages/sidecar/src/model-job.ts`) and `ModelJobs.complete` hands its end to `broker.completeReview`: `allow_once` or `deny` decide the request as `reviewer:<model>` (audited like any decision), `escalate`, an unreadable reply, a failed job or a changed action post it to the thread with a `review_escalated` event, and a verdict that comes after another decision is dropped with `review_late`. The hook's deny reason reads `Denied by the approval reviewer (<model>): <reason>`. Turn-exhaustion continuations follow `approvals/continuation-mode.ts`: in `approve_all` one within the frozen limit is decided `allow_once` by `mode:approve_all` at once, and past the limit `ApprovalReviews.queueContinuation` asks the reviewer (the run config carries `continuationBeyondLimit`, which lets that decision, or a person's after an escalation, continue past the limit); in the other modes nothing changes.

**A workspace operator may override a tool's tier (ADR-0002 amendment 3, A5).** `approvals/tool-tier-overrides.ts` keeps `workspace_tool_tiers`, one row per tool whose tier an Owner or Admin set through `PUT /api/workspaces/:id/tool-tiers/:toolName` `{riskLevel}` (removed with `DELETE`, listed by a Member with `GET`), each change one `workspace.tool_tier_set` audit row and the row's `createdBy` `human:<actor>`. No row is the default. A run's first start reads its workspace's overrides and, only when there are some, records them as `toolTierOverrides` in `runs.config_json` and sends them on the `StartRunRequest`; every later process of the run, a resume included, sends what the row recorded and nothing newer. The sidecar's tier function then answers the override's tier for that tool, in the hook, the `canUseTool` backstop and the ledger. The hard denies (egress and private addresses, IP literals, metadata, the directory guard, the vision withhold, cross-workspace refusals, the secret scrub) run before the tier and are never overridden; `connector_submit` and `integration_execute` are tiered by their own policies and refused as override targets (`tool_tier_not_overridable`). An override is an approval-rule change for that workspace and, like the approval mode, a strategy change in the sense of AGENTS.md.

**The Attention inbox is paged.** `GET /api/approvals` without `threadId` and with `status` pending (the default) answers `{approvals, nextCursor?, total}`: oldest first by `(created_at, id)`, 25 by default and at most 100 (`api/approval-inbox.ts`). The visible set is the caller's workspaces, never another person's private chat, no Guest, and below Admin only the requests of runs the caller started; it is computed before paging, so `total` is honest and feeds the nav badge. A thread's approvals (`threadId`) and the decided history are not paged yet.

Known gap: contracts has no 403-family error code for "this bot is not a member of that thread", so the `approval_decide` route answers 400 `validation` instead of 403.
