# Run observability: collector, spool and the obs model (ADR-0046)

Phase 1 of ADR-0046, with amendment 2's views and failure retrospective: a Gateway module that
copies the ledger, one way, into an append-only analytics model (`obs`) behind a pluggable sink,
and the built-in `sqlite` sink that writes it to `obs.sqlite` beside the ledger. Grafana reads the views of that file; the ledger is never read by
Grafana and never grows columns for it. Dashboards, the Grafana image and the web Analytics entry
are the presentation half and live elsewhere: the dashboards are generated by
`packages/observability-dashboards` into `observability/grafana/`, the image is `images/grafana`,
`stable.sh grafana` runs it ([runbook](../../../docs/runbooks/grafana.md)), the Gateway relays
`/analytics/` to it for the root's own session ([analytics relay](analytics-relay.md)), and the
web side is [Analytics](../../web/docs/analytics.md).

## Configuration

`config/observability.ts`; all empty turns observability off (the default for an existing
installation).

| Variable | Meaning |
| --- | --- |
| `OBSERVABILITY_SINK` | `sqlite` turns the collector on. `postgres` and `forward` (ADR-0046 decisions 4 and 5) are phase 2 and refused at startup like any unknown id. |
| `OBSERVABILITY_SQLITE_PATH` | The sink's file; default `obs.sqlite` beside `GATEWAY_DB`. Refused when it is the ledger, or `:memory:`. |
| `OBSERVABILITY_BATCH_SECONDS` | A batch closes once it is this old (default 300). |
| `OBSERVABILITY_BATCH_BYTES` | ...or once its spool file is this large (default 64 MiB). |
| `OBSERVABILITY_PAYLOADS` | `full` (default) or `derived`; see "Payloads". |
| `OBSERVABILITY_RETENTION_DAYS` | Days the sink keeps; empty or 0 is unlimited. Independent of `RUN_EVENTS_RETENTION_DAYS`. |
| `OBSERVABILITY_RETROSPECTIVE` | `on` (default) or `off`: the failure retrospective. It runs only when ADR-0041's `EMBEDDING_URL` and `EMBEDDING_MODEL` are also set; see "Failure retrospective". |
| `OBSERVABILITY_GRAFANA_URL` | Read on its own: the loopback origin of the Grafana that `/analytics/*` relays to ([analytics relay](analytics-relay.md)); anything but a loopback `http` origin stops startup. When set, `GET /api/config` returns `analyticsUrl: "/analytics/"` (null when empty) for the web's Analytics entry and run link. |

## Pipeline

`src/observability/`:

- `ledger-reader.ts` reads the ledger past a cursor in one short read transaction on the
  Gateway's own connection and computes the derived columns. It never writes the ledger.
- `cursor.ts` is the received/committed watermark, one entry per obs table.
- `spool.ts` keeps rows in JSONL under `<dirname(GATEWAY_DB)>/observability-spool/` until the
  sink has them: `<batch>.open.jsonl` being filled, `<batch>.closed.jsonl` waiting for the sink,
  `committed.json` the committed watermark.
- `collector.ts` runs a step: read, spool, close by age or size, commit closed batches in order.
- `observability-module.ts` puts the collector on a timer (every 5 s when idle, at once while a
  backlog remains, backing off to 60 s after failures) and answers the status route.
- `sinks.ts` is the loader: a static table of the release's bundled sinks, selected by id.
- `sqlite-sink.ts` and `../../observability/sqlite.sql` are the built-in sink and its schema.
- `retrospective.ts` is the failure retrospective (amendment 2), run by the module after the
  collector when an embedding service is configured.

### How each ledger source is read

| obs table | ledger source | read by |
| --- | --- | --- |
| `run_events` | `run_events` | autoincrement id |
| `model_requests` | `model_requests` | id; a row is held until its usage lands, it was refused, its run left the live statuses, or 15 minutes pass; up to one page (500 rows) after it are emitted meanwhile and remembered (`ahead`) |
| `run_usage` | `run_usage` | id; held while its run is live in the same attempt (the row is an upsert) |
| `task_runs` | `task_runs` | rowid |
| `run_states` | `runs` | `(created_at, id)` keyset, plus every run open now or open when last seen, emitted when its row changed |
| `task_states`, `thread_states` | `tasks`, `threads` | `(updated_at, id)` keyset |
| `run_summaries` | `run_activity_summaries` | `(updated_at, run_id/source_version)` keyset |
| `approval_decisions` | `approvals` (decided) | `(decided_at, id)` keyset |
| `approval_requests` | `approvals` (every one, once created) | `(created_at, id)` keyset; a cursor from contract version 1 has no entry and starts from the beginning |
| `bot_states`, `workspace_states`, `run_marks` | `bots`, `workspaces`, `run_marks` | whole-table scan against the fingerprint of the row last emitted; a vanished row is a tombstone (`deleted = 1`, or `verdict = 'unmarked'`) |

Keyset sources read only rows changed more than 2 s ago, so two writes in one millisecond are
both seen before the keyset passes them. `runs`, `bots` and `workspaces` have no `updated_at`,
which ADR-0046 decision 2 assumed; the open-run set and the fingerprints stand in for it without
adding a ledger column (decision 1).

### Crash safety

Every append to the spool is one chunk (rows plus a marker line with the cursor after them),
written once and fsynced before the in-memory cursor moves; on start, anything after the last
complete marker is cut off. A batch closes by appending its close line, fsyncing and renaming it.
The sink commits each table under `obs/<table>/<batch_id>`; the collector writes
`committed.json` (temp file, fsync, rename) only when every table of the batch is committed, and
deletes the batch file only after that. So a kill at spool, close or commit, or between two tables
of a batch, loses nothing and duplicates nothing (`collector.test.ts`). A spool directory that
was lost while the sink kept its data is refused at start, since reading the ledger again from
the beginning would duplicate everything the sink holds: move `obs.sqlite` aside to rebuild it
from the ledger, or restore the spool.

Retention: events reach the sink minutes after they happen, ledger retention (ADR-0042) prunes by
days, and a prune after a batch changes nothing the sink holds. An installation whose collector
is stopped for longer than `RUN_EVENTS_RETENTION_DAYS` loses the pruned events from the obs
model.

## Payloads

The ledger's redaction has already run; this decides how much leaves (`payload-policy.ts`).

- `full`: `payload_json` is the event's payload; a screenshot arrives without its image bytes
  (`base64`, `data`), and a body larger than 64 KB as
  `{"_truncated": true, "_bytes": <original size>, "_head": "<start of the text>"}`, so it stays
  valid JSON. `run_summaries.text` is the Activity summary.
- `derived`: `payload_json` and `run_summaries.text` are null. Derived columns and
  `payload_bytes` still go.
- A run in a private chat is `derived` whatever the setting, and the chat's `thread_states.title`
  is null: a private chat is its person's alone, the root included (ADR-0022 amendment 6), and
  Grafana is not that person. That Grafana is the root's alone (ADR-0046 amendment 1) does not
  change this (decision 17).

## The obs model (contract version 2)

Declared once in `@deskmates/contracts` `observability.ts` (`OBSERVABILITY_TABLE_COLUMNS`,
`OBSERVABILITY_INGEST_COLUMNS`, `OBSERVABILITY_VIEWS`); `model.test.ts` checks the SQLite schema
against it. Every table has a leading `batch_id`. Timestamps are ISO-8601 UTC text, durations are
milliseconds (`REAL`), booleans are 0/1. Snapshot tables get one row per observed change, stamped
`observed_at`; the views pick the newest per key by `(batch_id, observed_at)`.

Tables (columns after `batch_id`):

- `run_events`: `event_id`, `run_id`, `workspace_id`, `bot_id`, `attempt`, `seq`,
  `sidecar_seq`, `kind`, `source`, `ts`, `tool_name` (tool calls and results, skills, phase
  spans), `tool_use_id`, `is_error` (tool results), `risk_level` (tool calls), `model`
  (`turn_usage`, `model_switch`, and a model proxy span's request model, ADR-0046 amendment 2
  decision 21), `phase`, `span_id`, `parent_span_id`, `edge` (`start`/`end`),
  `outcome`, `request_kind` (phase-timing samples), `duration_ms` (a phase span's end, or a tool
  result's time since its call), `payload_bytes`, `payload_truncated`, `payload_json`.
- `run_states`: `observed_at`, `run_id`, `workspace_id`, `bot_id`, `thread_id`, `lane`,
  `trigger_kind`, `run_type`, `status`, `terminal`, `attempt`, `model`, `cheap_model`, `error`,
  `failure_class` (ADR-0042), `created_at`, `started_at`, `finished_at`, `queue_ms`,
  `duration_ms`.
- `task_states`: `observed_at`, `task_id`, `workspace_id`, `title`, `owner_bot_id`, `status`,
  `version`, `blocked_reason`, `created_at`, `updated_at`, `delivered_at`, `accepted_at`,
  `deleted_at`, `delivery_ms`.
- `bot_states`: `observed_at`, `bot_id`, `workspace_id`, `name`, `role`, `model`, `cheap_model`,
  `runtime`, `soul_version`, `created_at`, `archived_at`, `paused_at`, `deleted`.
- `workspace_states`: `observed_at`, `workspace_id`, `tenant_id`, `name`, `status`,
  `approval_mode`, `created_at`, `archived_at`, `deleted`.
- `thread_states`: `observed_at`, `thread_id`, `workspace_id`, `kind`, `channel`, `title`,
  `private`, `status`, `owner_bot_id`, `turn_budget`, `created_at`, `updated_at`.
- `model_requests`: `request_id`, `run_id`, `workspace_id`, `bot_id`, `attempt`, `seq`, `ts`,
  `request_kind`, `model`, `served_model`, `rewritten_from`, `refusal`, `stream`, the token
  counts (`input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_create_tokens`,
  `thinking_tokens`, and `prompt_tokens` = input + cache read + cache create), the request shape
  (`image_blocks`, `cache_control_blocks`, `system_blocks`, `system_chars`, `tools_count`,
  `tools_chars`, `messages_count`) and the three system prompt hashes.
- `run_usage`: `usage_id`, `run_id`, `workspace_id`, `bot_id`, `attempt`, `model`, the four token
  counts, `cost_usd` (null when unpriced).
- `task_runs`: `task_id`, `ordinal`, `run_id`, `workspace_id`.
- `run_marks`: `observed_at`, `run_id`, `workspace_id`, `verdict` (`wrong` or `unmarked`),
  `note`, `marked_by`, `marked_at`.
- `run_summaries`: `run_id`, `source_version`, `workspace_id`, `status`, `text`, `created_at`,
  `updated_at` (the text only; vectors are the retrospective's, below).
- `approval_decisions`: `approval_id`, `run_id`, `workspace_id`, `bot_id`, `thread_id`, `kind`,
  `risk_level`, `tool_name`, `wait_mode`, `decision`, `decided_by`, `decider_kind` (`human`,
  `user`, `bot`, `rule`, `mode`, ...: the part of `decided_by` before the colon), `rule_id`,
  `created_at`, `decided_at`, `wait_ms`.
- `approval_requests` (contract version 2): `approval_id`, `run_id`, `workspace_id`, `bot_id`,
  `thread_id`, `kind`, `risk_level`, `tool_name`, `wait_mode`, `created_at`. One row per approval
  once created; a request without a decision row is pending.
- `ingest_batches` (no leading `batch_id`): `token` (unique), `batch_id`, `table_name`,
  `row_count`, `source_first`, `source_last` (the collector's cursor before and after), `opened_at`,
  `closed_at`, `committed_at`.

Views, the only relations a dashboard reads:

| View | One row per | Notable columns |
| --- | --- | --- |
| `runs_latest` | run | the newest `run_states` row |
| `runs_named` | run | `runs_latest` plus `workspace_name`, `bot_name`, `bot_role`, `thread_title`, `thread_kind`, `thread_private`, `marked_wrong`, `mark_note`, `summary` |
| `tool_calls` | tool call | `tool_name`, `risk_level`, `called_at`, `result_at`, `duration_ms`, `is_error`, `outcome` (`ok`, `error`, `no_result`) |
| `phase_spans` | completed phase span | `phase`, `span_id`, `parent_span_id`, `tool_name`, `request_kind`, `model`, `outcome`, `ended_at`, `duration_ms` |
| `model_request_timing` | model proxy span | `phase_spans` of the `model_*` and `proxy_queue` phases, with `model`, `run_model`, `run_type` |
| `model_latency` | model proxy request | its `model_request` span with `headers_ms`, `first_byte_ms` (null when no body byte came, never 0), `body_ms`; `model` is the span's, else the run's, and `model_source` says which |
| `requests_named` | model request | the request with `workspace_name`, `bot_name`, `run_type`, `trigger_kind`, `run_status`, `failure_class` |
| `request_cache` | inference request | `cache_status` (`refused`, `no_usage`, `not_reported`, `hit`, `write`, `miss`), `cache_reported`, `reported_prompt_tokens` and `cache_read_share`, both null unless the cache-read count was reported |
| `run_metrics` | run | `runs_named` essentials plus `tool_calls`, `tool_errors`, `model_requests`, `refused_requests`, token totals, `cost_usd`, `unpriced_models`, `approvals`, `approvals_denied`, `approval_wait_ms` |
| `approval_waits` | decided approval | the decision with `workspace_name`, `bot_name`, `wait_ms`, `decider_group` (`human`, `reviewer`, `rule`, `mode`, `bot`, `expired` for `system:expiry`, `closed` for another system actor, `other`) |
| `approval_requests_named` | approval request | the request with its decision, if any; `state` is `decided`, `pending` (run still open) or `unknown` (no decision in the obs model although the run ended) |
| `failure_matches` | failed run and match | the failed run (`failure_class`, `failed_error`, `failed_summary`) and a nearest succeeded run (`rank`, `match_run_id`, `match_summary`, `similarity`); a match marked wrong since and any private chat's run are left out |
| `watermarks` | obs table | `batches`, `rows`, `last_batch_id`, `last_source`, `last_closed_at`, `last_committed_at` |

Views are dropped and recreated on every start, so a view change needs no migration; a table or
column change bumps `OBSERVABILITY_CONTRACT_VERSION`, and a file of another version
(`PRAGMA user_version`) is refused, except that a version 1 file is upgraded in place: version 2
only added tables.

The retrospective's tables (`OBSERVABILITY_VECTOR_TABLE_COLUMNS`, no `batch_id`, written by no
batch): `run_vectors` (`run_id`, `source_version`, `workspace_id`, `outcome`, `failure_class`,
`embedding_model`, `dims`, `vector` as an L2-normalised little-endian float32 BLOB, `finished_at`,
`embedded_at`; one row per run and embedding model), `retrospective_matches` (`failed_run_id`,
`source_version`, `workspace_id`, `embedding_model`, `rank`, `match_run_id`, `similarity`,
`computed_at`) and `retrospective_state` (the walk's position).

## The sqlite sink

`obs.sqlite` in WAL mode with `synchronous = FULL`; one `BEGIN IMMEDIATE` transaction per table
per batch, holding the rows and the table's `ingest_batches` row; a replayed token is skipped. A
reader such as Grafana opens the file read-only; with WAL it still needs the `-wal` and `-shm`
files beside it, so mount the directory, not the file alone.

Retention runs at most hourly after a commit: rows of batches closed before the cutoff go, except
the newest snapshot of every bot, workspace, thread, task and mark, and of every run that is not
terminal; the newest batch's `ingest_batches` rows always stay. A vector or match older than the
cutoff whose run has no snapshot left goes with it. The file does not shrink (no `VACUUM`); freed
pages are reused.

The sink declares `capabilities.vectors` and offers `vectors`, the store the retrospective writes
and reads back; similarity is computed in the Gateway, so no SQLite extension is needed.

## Failure retrospective

ADR-0046 decision 9 and amendment 2 decisions 23 to 26, `src/observability/retrospective.ts`. On
by default when the sink stores vectors and an embedding service is configured (ADR-0041);
`OBSERVABILITY_RETROSPECTIVE=off` turns it off. Without an embedding service nothing runs and
nothing is called. The module runs a step after each collector step, at most once a minute unless
a backlog remains; its failure is logged and shown on the status route and never holds a batch.

- **What is embedded.** In `finished_at` order, each ordinary run (no `runType`) that ended
  `succeeded` or `failed`, with the Activity summary it shows (ADR-0033): the verbatim outcome
  when it fits, else the ready summary of its current source version. A pending summary holds the
  walk for up to 15 minutes, then the run is skipped; a failed summary or an empty text is
  skipped. A run in a private chat is never embedded, so it is never matched or offered.
- **Calls.** Up to 16 summaries of one tenant per request, through ADR-0041's `EmbeddingClient`;
  each request writes one `retrieval_calls` row (corpus `retrospective`, purpose `index`, no run
  id). A failed request is retried from the same position on the next step.
- **Matches.** For a failed run, its five most similar succeeded runs of the same workspace under
  the same embedding model, embedded so far, by cosine similarity (a dot product of normalised
  vectors, brute force per workspace). A run marked wrong is left out when matches are computed,
  and `failure_matches` also hides a match marked wrong later. Matches are computed once per
  failed run and source version.
- **Thresholds.** Similarities are stored unfiltered; the Agent runs dashboard's minimum
  similarity is a display filter. Nothing decides by them.
- **Payload policy.** `OBSERVABILITY_PAYLOADS` does not change what is embedded; the sink holds
  the vector and similarity, never the text, and under `derived` the panels have no summary text.

## Status

`GET /api/observability/status` (root only) returns `ObservabilityStatus`: whether it is on, the
Grafana URL, the sink's id, version and engine, the payload policy and batch limits, per table the
received and committed cursor, the newest closed batch and its age, the open batch, pending
batches, spool bytes, the sink's file size and last prune, the last error, and `retrospective`
(the embedding model, the walk's position, runs embedded and failed runs matched since start, its
last error; null when it does not run). With the sink unset it answers `enabled: false`.

## Measurement, not control

Nothing outside `src/observability/` imports it except `src/index.ts` (wiring) and the status
route (`import-graph.test.ts`), and the module is attached to the context through a WeakMap
rather than a context field. A finding becomes a change only through `evals/compare.ts`.
