# Implemented foundation (M0/M1 and M2 F1–F4)

What is implemented: the full schema (`migrations/0001-init.sql` onwards), workspaces and bots, one-to-six-member `chat` threads through the ADR-0005 model (members, `seq`, `last_seen_seq`, mentions parsed and stored), the two-lane scheduler with per-`(bot, thread)` wake coalescing, the run ledger with events, usage and Gateway pricing, short-lived run tokens, the model proxy, SSE, the sidecar-facing internal routes, and the approval broker with rules, live waits, deferral and resume (see [Approvals](approvals.md)).

M2 foundation adds durable in-turn walks, parallel explicit mentions, relay and turn caps, human join-by-mention, pairwise `message_bot` bus threads, and tab-aware browser leases. The sidecar now propagates stable CDP target IDs, restores per-run tabs and fences results across takeover. B1 messaging and focused B3 collaboration checks have passing evidence; the B2 ticket concurrency/reliability gate remains tracked in `docs/design/m2-b1-b3-closeout-plan-2026-09-23.md`. Full M2 and knowledge-base completion are not implied.

Run flow: `POST /api/threads/:id/messages` appends the message, writes a `runs` row (`queued`) and kicks the scheduler. The scheduler starts a run when its bot has no run occupying that lane: it issues a short-lived token and calls `provider.exec(handle, {cmd: ["deskmates-sidecar", "run"], stdin: JSON.stringify(StartRunRequest)})`. The sidecar talks back over the internal routes below and finishes with `ended`. When `exec` resolves without a `run_ended`, the run is `failed`. On `succeeded` / `silent` the member's `last_seen_seq` advances to the highest delivered `seq`; on `failed` it does not, so the next wake redelivers.

Model credentials travel in that `StartRunRequest` (`modelBaseUrl`, `modelAuthToken`) and nowhere else. The Gateway does **not** call `provider.injectEnv` per run: the workspace env file is one file for the whole workspace, so with two concurrent runs in one workspace it would hold the other run's token. `injectEnv` stays on the provider interface for values that are the same for every run in a workspace.

**Upgrades recreate stale sandboxes.** `SandboxRegistry.open` (reached from `ensure` when no handle is cached) first calls `provider.removeStaleSandbox(workspaceId, WORKSPACE_IMAGE)`. When the workspace container or its egress proxy runs an image other than the one `WORKSPACE_IMAGE` / `EGRESS_PROXY_IMAGE` resolves to on the daemon, the provider removes both and keeps the named volumes, the Gateway logs one line `recreating workspace sandbox: it ran a stale image` with `workspaceId` and each `{component, runningImageId, configuredImageId}`, and the ordinary create path builds the sandbox from the current allowlist with new screen credentials. A configured image that is not present on the daemon is `sandbox_unavailable` / `image_missing` before anything is removed; nothing is ever pulled or built. The assumption that makes removal safe: `open` runs only when this process caches no handle, i.e. first use after a Gateway start (`reconcile` has failed every run the previous process left live), after `forget` (the sandbox had gone) or inside `restart` (already destroyed); a run of this process always holds the cached handle. `peek`, used by status and takeover lookups, never recreates. A human takeover screen open on the old container is cut off by the recreation, and its browser lock is not released by it.

If `exec` fails with `not_found` — the container was removed out of band — the scheduler drops the cached handle (`SandboxRegistry.forget`), recreates the sandbox and retries once. `run_ended` is applied in a single SQLite transaction (usage, session id, reply message, status, `last_seen_seq`), so a failure leaves no partial rows; the SSE frames go out after it commits.
