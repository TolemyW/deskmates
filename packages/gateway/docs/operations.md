# Operations (M1)

Three operator knobs that change a running deployment without a redeploy: the egress allowlist, the price table, and `DESKMATES_MAX_TURNS`.

**The allowlist is edited by a human and enforced at two layers.** `PATCH /api/workspaces/:id` with `{egressAllowlist}` replaces the workspace's `egress_rules` rows in one transaction and dates the change in `workspaces.egress_updated_at` (migration `0008`). Every pattern is validated first — `isEgressPattern` from contracts: an exact hostname or `*.hostname`, nothing with a scheme, a path, a port or a space — so a bad list is 400 and the workspace is untouched. `POST /api/workspaces` validates the same way; a list one route accepts and the other refuses would be a trap. There is no tool path to this route: the allowlist is human-maintained and the agent cannot edit it (AGENTS.md, "Egress is deny-by-default").

The two layers refresh at different times, which is why the response carries a `note` saying so:

- *The sidecar hook, per tool call.* It re-reads the list from `GET /internal/runs/:runId/egress` before a navigation check, so an edit reaches a run that started under the old list. The copy on the `StartRunRequest` is only the fallback for a Gateway the sidecar cannot reach.
- *Chromium, at container start.* The image's entry point turns `DESKMATES_EGRESS_ALLOWLIST` into host-resolver rules, read once. `POST /api/workspaces/:id/restart` is what carries an edit down to that layer: it destroys the container and creates a fresh one from the current list. The named volumes (`/profile`, `/work`, `/home`) are not the container and survive it, so the browser profile, the login state and the bots' homes come back. It refuses with 409 `lane_busy` and `details.liveRuns` while any run of the workspace's bots is `running` or `waiting_approval_live` — a restart would pull the sidecar out from under a call in flight. A human browser lock is released by the restart, with a `workspace_lock` frame carrying `null`: the screen it was watching is gone, and leaving the lock held would stall every bot in the workspace.

Every run that is live when the list is replaced gets a `log` event `{source: "egress", op: "allowlist_replaced", by, added, removed}`, so a call that starts being blocked has the reason in its own transcript, and a `workspace` SSE frame goes out so the UI redraws the list.

**The price table is configuration and data.** `MODEL_PRICES` is a JSON array of `{model, inputPerM, outputPerM, cacheReadPerM, cacheCreatePerM, effectiveFrom?}`, parsed and validated in `src/config.ts` — bad JSON or a bad row fails startup with a message naming the row and the field, rather than leaving a month of runs unpriced — and loaded with `PriceStore.upsert` in `buildGateway` before any route can read it. `effectiveFrom` defaults to the epoch so a row prices the runs that already happened. `GET /api/prices` lists every row, `PUT /api/prices` upserts on `(model, effectiveFrom)`; it is not a replace, because a table that dropped what it was not sent would re-price every historical run of a model the caller forgot. A model with no row stays unpriced: `cost_usd` is NULL and the run gets a `pricing_missing` event naming the model. Nothing in code names a model (`src/ledger/model-price.ts` is the shared parser; the tests use `test-model-default`).

**`DESKMATES_MAX_TURNS`** (default 80) is the SDK `maxTurns` of one run. Like the other knobs it is recorded in `runs.config_json` and it rides on every `StartRunRequest` — thread, resume, cron and webhook alike — so a result can be attributed to the setting it ran under.

**Per-bot models.** A bot may override `DEFAULT_MODEL` and `CHEAP_MODEL` with its own `model` and `cheapModel`, set on `POST /api/bots` or changed later with `PATCH /api/bots/:id`; `null` on the patch clears the override and `undefined` on the bot means inherit. An override must have a row in the price table, on both routes, and the empty string is a 400 on both (ADR-0023 decision 1): a model the Gateway cannot price cannot be set on a bot. The run row is the only immutable answer to "what did this run on": `runs.config_json` carries `defaultModel` and `defaultCheapModel` (the Gateway-wide values at creation) and `model` and `cheapModel` (what the run was actually started on), the latter two stamped once at first start in `src/scheduler/run-lifecycle.ts`. A resume is a second process of the same run, so it reuses the stamped pair even when the bot was re-pointed while parked; a mid-run model change would make the run uninterpretable under the measurement protocol. `GET /api/config` returns the two configured ids and the release label (`DESKMATES_RELEASE`) and nothing else, so the UI can offer the models by name without a model literal anywhere in `packages/`; the route is tested never to carry the base URL or anything token-shaped. Changing a bot's model is a strategy change (AGENTS.md), not a framework change: the route makes it easy, the evidence still comes from `evals/compare.ts`.

**What was served, switched and retried (ADR-0023 decision 3).** `FALLBACK_MODEL` (optional, one id) is frozen on each run at first start as `runs.config_json.fallbackModel` (`null` when unset, so a run started without one never gains one), travels in `StartRunRequest.fallbackModel`, which the sidecar passes verbatim to the SDK's `fallbackModel`, and joins that run's frozen set at the model proxy. It must have a price row or the Gateway refuses to start. The SDK is the only retry owner; the Gateway and the proxy never retry a model call. The proxy stores the `model` a successful response named (`message_start` in a stream, the top level of a JSON body) as `model_requests.served_model`; it stays NULL on a failure, a refusal, or a response that names none (a `count_tokens` answer names none), never guessed from the request. The sidecar forwards the SDK's `PostModelSwitch` hook as a `model_switch` event `{from, to, source, requested?}` and each `api_retry` message as a `model_retry` event `{attempt, maxRetries, retryDelayMs, errorStatus, error}`. Usage is still priced per model the SDK reports in `modelUsage`, so a run that fell back has one priced `run_usage` row per model.

**Per-bot reasoning.** A bot may also carry `effort` (`low`, `medium`, `high`, `xhigh`, `max`) and `thinking` (`{type: "adaptive"}`, `{type: "enabled", budgetTokens?}`, `{type: "disabled"}`), set on `POST /api/bots` or `PATCH /api/bots/:id`; `null` clears either. A run's own `config.effort` / `config.thinking`, set when the run row is created, win over the bot's. Nothing is set by default, and unset is a real configuration: the Agent SDK sends its own thinking and effort when a run passes none (adaptive thinking at effort high on 0.3.278, per the 2026-09-30 thinking probe under `docs/design/`). So the run row records `runs.config_json.reasoning = {effort, thinking, effortSource, thinkingSource}` with the value in force or `"sdk-default"`, stamped once at first start like the models and kept across a resume, and the `StartRunRequest` carries `effort` / `thinking` only when something was set. The Gateway does not know which levels an upstream accepts; a rejected value fails the run visibly. `model_requests.thinking_tokens` holds what a response reports in `usage.output_tokens_details`, NULL when it reports none: unknown, not zero. Changing either setting is a strategy change, measured like a model change.
