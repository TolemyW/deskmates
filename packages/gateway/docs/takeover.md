# Takeover (M1)

A human takes the shared browser through `POST /api/workspaces/:id/takeover` and gives it back with `POST /api/workspaces/:id/handback`. **The lock is workspace-wide, never per bot** (ADR-0004 decision 6): one Chromium serves every bot in the workspace, so while a human holds it the browser tools of *every* run in that workspace get `granted: false` with the wait message, the sidecar's `PreToolUse` hook denies the call with it, and the run records a `takeover` event. Taking over and handing back each write a `takeover` event (`{phase, by}`) on every run of the workspace that has a live sidecar, so a transcript says why it stalled and when it resumed, and publish a `workspace_lock` SSE frame.

The human lock has a TTL — `BrowserLockStore.humanTake` defaults to 3600 s — so a takeover nobody ends expires on its own and the bots go back to work. Hand back releases it early; that is the normal path, and the TTL is only the backstop for a browser tab someone closed.

`takeoverScreen` says whether the workspace's container publishes the shared screen: `SandboxRegistry.open` asks the provider to publish `NOVNC_CONTAINER_PORT`, and the Docker provider binds it on **127.0.0.1** and reports the host address on the handle. `SandboxRegistry.peek` reads the handle without creating a container, so opening a workspace page never starts a machine. The address and the workspace's generated VNC password stay in the Gateway (ADR-0022 amendment 1, C7): no route returns either. The lease holder reaches the screen only through the screen proxy (`POST /api/workspaces/:id/takeover/open-screen`, in [HTTP API](http-api.md)), which authenticates to x11vnc with the password and offers the browser the RFB `None` security type (`vnc-relay.ts`).
