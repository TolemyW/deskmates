# Triggers (M1)

Cron and webhook are the two triggers with no thread behind them. Both follow the same rule as a thread wake: **the run row is written first**, with what fired it in `runs.trigger_payload_json`, and only then is the scheduler kicked. Both land on the **background lane**, so a bot's scheduled work and its chat run proceed side by side while two background runs queue behind each other. A run with no thread gets a fresh SDK session (no `sdkSessionId`), the `message_bot` tool (without `thread_post` or `approval_decide`), and keeps its reply in `runs.summary_json` — there is nowhere to post it, so it ends `succeeded`, never `silent`.

**Cron.** `src/triggers/cron.ts`. `CronRunner.start()` ticks on the next minute boundary and once a minute after that (unref'd timers); `tick(now)` takes the minute as an argument, which is what the tests drive. For every bot and every entry in `bots.cron_json` whose five-field expression matches that minute in `CRON_TIMEZONE` (parsed by `parseCron` in contracts), the runner creates one run: `lane: "background"`, `triggerKind: "cron"`, `triggerRef: "cron:<entry index>:<minute ISO>"`, `triggerPayload: {prompt, schedule, entry}`.

- *Idempotent per minute.* The trigger reference carries the minute, so a tick delivered twice, a Gateway restarted inside the same minute, and a clock that went backwards all find the existing run and do nothing.
- *Overlap is a skip, not a queue.* When the bot still has a run for that entry in any non-terminal status — `queued`, `running`, `waiting_approval_live`, `waiting_approval` or `waiting_browser`, i.e. "the previous round has not finished" (design v0.3 §3.4) — no run is created. Parked counts as not finished: a round waiting on an approval holds no lane, but firing the next minute anyway would create a second run and ask the human the same question every minute until someone answers. The skip is recorded as a `log` ledger event on the run that is still going: `{source: "cron", skipped: true, entry, schedule, minute}`. An `approval` event would claim something a human has to answer; a `log` event is what an operator reads afterwards.
- A schedule the parser cannot read is logged and skipped, and the other entries still fire. `POST /api/bots` and `PATCH /api/bots/:id` parse every schedule, so one should never reach a row.
- *A paused bot's round is skipped* (ADR-0026 amendment 1): no run, a Gateway log line per round, and one system message in the bot's private chat per entry and pause. Rounds missed while paused are not run on resume.
- *A round parked on a human says so* (ADR-0029 decision 12). The overlap skip above still holds, but when the round that is still going waits for a human (an approval, a continuation, the browser), the first skip and then at most one per hour post a system message in the bot's private chat naming the parked run and what it waits for. A `waiting_platform` round resumes by itself and posts nothing.
- *Minutes missed while no Gateway ran are skipped, not back-filled* (ADR-0029 decision 11). The next start logs, per entry, the minutes nobody fired; an entry with `misfire: "run_once"` fires one round for the latest of them instead. A round queued during an upgrade drain that cannot start before its minute is `CRON_MISFIRE_GRACE` minutes old (default 5) is cancelled with `cron_misfire`. See [Upgrade drain and restart recovery](upgrade-drain-and-restart-recovery.md).
- *Run now* (ADR-0043 decision 5). `POST /api/bots/:id/cron/:entry/run` creates a run of that entry immediately: `triggerKind: "manual"`, `triggerRef: "manual:<entry>:<id>"`, `triggerPayload: {prompt, schedule, entry, requestedBy}`, background lane. It is not subject to the overlap skip (it queues behind the lane like any background run) and is refused while the bot is paused. The sidecar receives it as a `cron` trigger with the entry's prompt.

**Webhook.** `src/api/webhook-routes.ts`. Each bot gets a token (32 random bytes, base64url, `whk_` prefix) when it is created; only its SHA-256 is stored, in `bots.webhook_token_hash`, and the plaintext is returned once — by `POST /api/bots` and by `POST /api/bots/:id/webhook-token`, which rotates it and invalidates the old one. `BotDefinition` carries neither the token nor the hash, so no read route can leak it.

`POST /hooks/:botId/:token` takes the body raw, whatever the content type (the route's content-type parser is encapsulated, so `/api/...` keeps normal JSON parsing) and answers 202 `{runId}`. An unknown bot and a wrong token get the same 404 `not_found`: telling them apart would make the route an oracle for bot ids. A body over `WEBHOOK_BODY_MAX_BYTES` is 413 and creates no run. Each delivery is its own run — bodies differ, so deliveries are never merged the way two thread wakes for one `(bot, thread)` are — and once a bot has `WEBHOOK_QUEUE_MAX` webhook runs queued, further deliveries are 429 `queue_full`. The body is external data: the sidecar wraps it as untrusted before it enters model context. A delivery to a paused bot is 409 `invalid_transition` with `details.reason: "bot_paused"` and creates no run, so the sender can retry later (ADR-0026 amendment 1).
