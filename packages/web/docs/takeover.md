# Browser takeover

A workspace is one container with one Chromium and a shared desktop containing bot regions
(ADR-0008). Taking the browser over holds the whole workspace (ADR-0004, design v0.3 §3.3).
While a human holds the lock every bot in that workspace gets a wait message from its browser tools.

- **Header controls.** The chat pane reads its thread's `workspaceId` from `getThread` and then `GET /api/workspaces/:id`, which returns the workspace, its bots, the human `browserLock` (never a run's tab lock) and `takeoverScreen`. Free, the header offers **Take over**; held, it says "a human holds the browser" and offers **Hand back** plus an **Open screen** button. `Take over` `POST`s to `/api/workspaces/:id/takeover`, which answers with the lease only. The dialog defaults to the first chat member's region, using `GET /api/bots/:id/screen` and a control ticket from `POST /api/bots/:id/screen/access`. Group chats can select another member. **Entire workspace** explicitly uses `/api/workspaces/:id/takeover/open-screen`; an unready or legacy region uses that overview with a visible explanation and never starts or allocates a desktop. A failed status request shows retry instead of selecting another screen. No noVNC address or password reaches the page (ADR-0022 amendment 1, C7), and the dialog closes when the hold ends (a `workspace_lock` frame with `null`). `takeoverScreen` is false until the workspace container exists, and then the header says "no screen yet (the workspace container has not started)" and opens nothing. `Hand back` `POST`s to `/api/workspaces/:id/handback`. The controls stay hidden until the workspace view has settled, so the header never offers a button that contradicts the Gateway.
- **Details and sizing.** Desktop-card control and the chat header share `TakeoverDisplay`, including region selection and overview. `DesktopView` follows the framebuffer canvas dimensions, with 720p region/overview defaults. It scales locally to fit the available height; it never resizes the remote session. Switching targets closes the old screen ticket and does not retake or release the workspace lease. The chat header's close action returns the lease; closing a desktop card retains its existing explicit **Return control** behavior and explains it beside the action.
- **`workspace_lock` SSE frame** (`{type: "workspace_lock", workspaceId, browserLock}`): emitted on the takeover and again on the hand back. It carries no `threadId`, so the thread-filtered stream drops it; the pane holds a second, unfiltered subscription for it and two operator tabs agree on who holds the browser without either one refetching. `useWorkspaceLock(workspaceId, api)` (`src/features/chats/use-workspace-lock.ts`) owns the fetch, that subscription and the two actions.
- **Run replay.** A `takeover` ledger event shows its phase (`taken`, `handed_back`) when a human moved the lock, and the tool name plus the wait message the `PreToolUse` hook returned when a run was parked behind one.
