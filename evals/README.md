# evals (T4)

Model-in-the-loop measurement. Not framework tests: they answer "did this change make the agent better" with error bars. Method: `docs/design/measurement-2026-09-20.md`.

Layout:

- `tasks/deskbench-v1.json` — the task set, 48 active tasks on the Galaxy Ops Console golden site (`packages/golden-site`), generated by `tasks/build-deskbench-v1.py` from the spec in `docs/design/benchmark-2026-09-20.md`. Each task: id, cluster, duration bucket (short ≤5 tool calls, medium 6–20, long >20), oracles (server state, exact answer, log order, ledger assertions), `allowed_paths` for the side-effect invariant, an English paraphrase, applicable perturbation variants, expected L2 count, holdout and status flags. Retired tasks stay in the file with `status: retired`. Edit the spec and the generator together; never hand-edit the JSON.
- `run.ts` — `npm run evals`: replays every trace under `traces/` with `replay.ts` (zero tokens, no Docker, no network) and exits 1 on a decision mismatch; an empty trace set prints how to add one and exits 0 (issue #11). The model-in-the-loop deskbench runner described by the measurement design (N tasks × K repeats for a labelled configuration, alternating A/B, resetting the golden site before every task, auto-approving L2, diffing `/api/state` against the seed and failing a run that changed a path outside its `allowed_paths` with `unexpected_change`, one JSON line per run in `results/<date>-<label>.jsonl`) is not built yet; `compare.ts` and `power.ts` already read the rows it is specified to write.
- `compare.ts` — paired difference between two result files: cluster-adjusted standard error, 95% interval, per-bucket breakdown, Hotelling T² on fingerprints, cost interval, verdict (better / worse / no difference / inconclusive) under the rule in measurement §4.3. `npm run compare -- <baseline.jsonl> <candidate.jsonl> [--delta 0.10] [--cost-delta 0.15] [--report <file.md>] [--json]`; exit 1 when the total or a bucket is worse. It reads `taskId`, `bucket`, `success`, `fingerprint` (named numeric dimensions) and `costUsd` from each row (`compare/result-row.ts`). The pairing unit is the task: its pass rate over K runs, candidate minus baseline, so the standard error is clustered by task (sd of the task differences over √n, t interval). Fingerprints are compared with a paired Hotelling T² on per-task mean vectors; cost as the per-task mean difference relative to the baseline's mean cost, cheaper is better. Code in `compare/`.
- `power.ts` — given task count, K, and baseline pass rate, prints the minimum detectable effect. Every report starts with this number. `npm run power -- [--tasks 44] [--k 5] [--baseline 0.8]` prints the optimistic MDE (every run independent, the figure the defaults below are quoted at) and the conservative one (each task counted once).
- `replay.ts` — exports recorded run traces from the ledger and replays them through the fake SDK against the current code, diffing every decision point. Zero tokens. Runs on every PR. See "Trajectory replay" below.
- `delegation-metrics.ts` — the six numbers ADR-0016 amendment 1 is judged on, computed from a Gateway SQLite file opened read-only: delegation chains (a bot's message that woke another bot), chains completed, missed replies, stuck delegators, duplicate delegate runs, wall time from delegation to terminal state and to the Gateway's outcome notice, and tokens on the chain. Zero tokens, no Gateway needed. `npm run delegation-metrics -- --db <gateway.sqlite> [--json] [--report <file.md>]`. Definitions are at the top of `delegation/metrics.ts`; "chain completed" is a ledger proxy (delegate succeeded, reply reached the thread, delegator woken), not the task oracle. Run it on the same ledger before and after a change to compare. A second section (ADR-0005 amendment 2, `delegation/offers.ts`) reports what an unaddressed human message costs a group: runs offered the request, runs per request, the silent share, requests nobody took, time to first reply, and the runs an unaddressed bot message woke.
- `latency-report.ts` — run startup latency (ADR-0037) from a Gateway SQLite file opened read-only: p50/p95 of time to first model request, first token, first text, first visible text and attempt end, per class of attempt (fresh or resumed start, new or resumed SDK session, new, existing or warm container, retried or not), with outcome, SDK-retry and first-turn cache-read distributions. Stages an attempt did not observe are counted as missing, never zero. Zero tokens. `npm run latency-report -- --db <gateway.sqlite> [--since <ISO>] [--jobs] [--json] [--report <file.md>]`. Definitions are at the top of `latency/metrics.ts`. Not quality evidence on its own.
- `replay/` — the replay harness: `trace.ts` (format, builder, export guard), `export.ts` (operator API), `replay-run.ts` (the fake-SDK run), `decisions.ts` (decision points and the diff), `report.ts` (markdown).
- `traces/` — exported run traces, one JSON file per run. Committable: a trace that catches a regression belongs next to the code that regressed.
- `baselines/<model>@<gateway>.json` — signed-off baselines per model and gateway version.
- `results/` — committed, so history is diffable.

Defaults: 44 verdict tasks (short + medium) × K=5, δ=0.10 for pass rate, δ=15% for cost. Detects a 10-point regression at 80% power; does not detect 5 points. Say so in the report. The 4 long tasks are a smoke set: run and reported per task, never part of the verdict, and the report must say long-task regression is not measured.

For a separately frozen campaign whose decision rule includes long tasks, use
`npm run compare -- <baseline.jsonl> <candidate.jsonl> --include-long`.
This includes long tasks in the total, per-bucket rejection, fingerprint and
cost comparison, and records `includesLong` in JSON and the scope in Markdown.
The original deskbench defaults stay unchanged; this option does not rebuild
its long smoke set or establish sufficient power. For the M3 memory protocol,
each row must represent a whole ordered campaign with all failures retained.
An exit code of zero means no measured bucket is judged worse. M3 strategy
adoption still requires its predeclared positive per-bucket confidence bounds,
adequate power, complete runtime controls and independent safety gates;
an inconclusive result does not establish improvement.

`npm run evals` needs neither Docker nor model credentials: today it is the trace replay. The deskbench runner, when it exists, will need Docker and the model gateway env vars.

## Trajectory replay (`npm run replay`)

What measurement §5.1 calls trajectory replay: a code change does not run the model, it replays recorded runs and asserts that every decision the sidecar took is the decision it takes now. Zero tokens, no Docker, no network — safe as a required check on every PR.

```
npm run replay -- export --gateway http://localhost:8080 [--since <iso>] [--run <id>]... [--out evals/traces]
npm run replay -- replay evals/traces/<runId>.json... [--report evals/results/<date>-replay.md]
```

**Export** sends `DESKMATES_OPERATOR_TOKEN`, when set, as a bearer on every request, so it works against an authenticated Gateway (ADR-0006); the token never goes into a URL or a trace. A run's drawer in the web UI shows the exact export command for that run ("Save as replay fixture", ADR-0042). It reads the ledger through the operator API only — `GET /api/runs`, `/api/runs/:id`, `/api/runs/:id/events`, `/api/bots/:id`, `/api/workspaces/:id` — so it needs nothing but a URL, and takes terminal runs only (a run still going will not replay to the same place). `--since` filters on `createdAt`; `--run` names run ids and ignores `--since`. Redaction already happened on the way into the ledger; before a trace is written it is checked and the export fails rather than committing a credential.

**The guard** has two halves, because a trace is JSON and a credential hides differently in each. Text patterns (bearer tokens, `sk-` keys, credential variables and headers, credentials in a query string) find what is written into prose: a header inside a shell command, a token inside a URL. A walk over the parsed object finds what sits in a *field*: `{"headers": {"cookie": "sid=…"}}` never matches a pattern written for `cookie: sid=…`, because serialising puts a quote between the key and the colon. The key test mirrors `packages/sidecar/src/redact.ts` `isSensitiveKey` — normalise to `snake_case`, match whole credential words — so `clientSecret` and `x-api-key` are credentials while `runId` and `inputTokens` are not. Both halves are copied from the code they guard rather than imported, on purpose: a guard that shares its rules with the redactor is not a second opinion.

**What the guard reports is a path and a kind, never the value** — not the match, not a prefix of it. A finding is `{kind, path}`, e.g. `credential-named field at events[12].payload.headers.cookie`, and that is what the error message and the CLI's stderr line carry. The guard fires exactly when redaction upstream has failed; copying the credential into a terminal, a CI log and an error report at that moment makes the leak worse, and the run id plus the path is what finding it actually takes.

**A trace** (`evals/traces/<runId>.json`, one run per file) holds the run row (id, bot, thread, trigger kind, status, attempt, model), `runs.config_json`, the knobs the run is restarted with (`shortWaitSeconds`, `maxTurns`), the workspace's egress allowlist, the bot's connectors and the tools the run was offered, the trigger payload, the per-model token counts, and every ledger event in `seq` order. `triggerSource` says how faithfully the trigger could be rebuilt: `run_payload` for cron, webhook and approval resumes, which the run row captures verbatim; `trigger_ref` for a thread wake, whose delivered message slice the operator API cannot reproduce after the fact. A thread wake therefore replays with a different prompt and the same trajectory, which is enough, because the model is not in the loop.

**Recorded run metadata wins over anything still editable.** `run.model` is read from `runs.config_json` first — `model`, which the Gateway stamps at run start with the bot's override already resolved, then the older `defaultModel` — and only falls back to the bot's current model when the row says neither. `run.modelSource` records which it was (`run_config` or `bot`). The bot's model is a setting an operator changes; the run's is a fact. Reading the bot first made a trace claim a run had used whatever the bot points at today, which quietly reattributes months of measurements the first time a bot is re-pointed.

**Replay** builds a fake-SDK script from the trace — each `tool_call` event with its recorded input and the matching `tool_result` as its result, each `thinking` block, the final summary as the `end` step — and runs `runOnce` from `packages/sidecar` against it with the sidecar's own fake Gateway and in-memory filesystem. The recorded approval decisions (`decided`, `rule_matched`, `deferred`, `failed`) answer the replayed run's approval requests in the order they were asked, and the recorded browser-lock outcomes answer its lock acquisitions in the order they were made, so the run meets the same answers the original did.

Two things decide *which* calls those sequences belong to.

**Lock answers follow the calls that asked for the lock, not every browser call.** The `PreToolUse` hook checks the egress allowlist before it acquires the workspace browser lock, so a navigation the allowlist stopped never asks the Gateway for the lock at all. Queuing an answer for it shifted every later answer by one and made the replay report a lock that had not changed behaviour. A browser call whose recorded decision was `egress: blocked` is therefore not in the sequence.

**A resumed run replays as the two sidecar processes it was.** The events are split by `attempt`. Attempt 1 runs until it defers — which is what ends it — and the next attempt is started as `RunLifecycle.resume` starts it: same SDK session, `attempt` one higher, and an `approval` trigger carrying the approval id, the tool-use id, the origin the browser was left on and the deferred action from the attempt that just parked, plus the human's decision read out of the ledger (the Gateway's `decided` event, or the `resumed` event the resumed sidecar writes). That is what makes the stale-`ref` retry replayable: the resumed process re-arms the decision when the replayed call fails on a `ref` from the old snapshot, and flattening the run into one `runOnce` lost it. Only the sidecar's own approval events answer an attempt's requests; the Gateway's `decided` for a parked run lands after the process that asked has exited, and reading it as that process's answer turns a deferred run into an allowed one.

**`unsupported`** is the third outcome, next to identical and mismatched. When a field the resume needs cannot be recovered from the trace — a run whose ledger does not say what the human decided — the trace is reported with the reason and is not diffed, and the run exits 0. Diffing it anyway would print a decision change that came from the replay guessing, not from the code under test.

It then compares **decision points**, one per tool call, matched by order and tool name:

| field | recorded as | what a diff means |
| --- | --- | --- |
| `riskLevel` | `tool_call.payload.riskLevel` | the tier table moved a tool |
| `hookDecision` | approval events, `pre_tool_use` / `can_use_tool` deny logs, `takeover` | the `PreToolUse` hook allows, denies or defers differently |
| `egress` | a deny whose reason starts `egress_blocked` | the allowlist check changed |
| `browserLock` | a `takeover` event naming the call | the workspace lock behaves differently |
| `inputRedacted` | `[redacted]` in the ledger copy of the input | the redactor widened |

A run with no diff reports `identical`; otherwise every mismatch is listed as `{seq, tool, field, recorded, replayed}`, `--report` writes the same as markdown, and the process exits 1. A trace reported `unsupported` carries its reason instead of a table and does not fail the run.

`inputRedacted` has one limit worth knowing: the recorded input is already redacted and the replay feeds it back in, so it cannot catch redaction being *removed*. It catches redaction widening — new code scrubbing a field the old code passed through — which is the direction redaction rules actually move in.

**A mismatch is not automatically a bug.** Per measurement §5.1 it is either an intended behaviour change, which then goes through the strategy protocol in §5.2 (paired A/B against the baseline, one knob per experiment, per duration bucket), or it is a regression. What it may never be is a surprise: a framework change that was meant to be pure and moves a decision is a bug until proven otherwise.

`evals/` is not an npm workspace, so `evals/tsconfig.json` maps `@deskmates/*` to package **sources** through `paths` rather than to built `dist/` through project references the way `acceptance/tsconfig.json` does. Two reasons: a replay must run against the code in the tree, never a stale build, and the harness imports sidecar modules by path (`@deskmates/sidecar/run-once.js`) rather than through the package entry point, which would pull in `real-deps.ts` and with it the real Agent SDK runtime. `npx tsc -p evals --noEmit` needs no prior build; `vitest.config.ts` carries the matching alias.
