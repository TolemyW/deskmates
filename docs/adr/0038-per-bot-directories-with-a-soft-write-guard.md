# ADR-0038: Per-bot directories by default, with a soft write guard between bots

Date: 2026-10-14
Status: Accepted (owner-decided 2026-10-14, owner decision 13 of batch 2026-10-14c; issue #88). Supersedes, for directories only, ADR-0004 decisions 2, 3 and 7 where they say that no tool call is refused because of another bot, ADR-0004 amendment 1 decisions 8, 9 and 12, and the worktree parts of ADR-0036 (decisions 2 and 4, and `worktreeRepo` in decisions 1, 3, 5, 7 and 8).

## Context

ADR-0004 made a workspace one shared computer and said bots are separated only by soft context: `SOUL.md`, working directory, prompt and ledger attribution, with "no code path rejects a tool call on the ground that another bot owns a resource" (its Verification row 3, AGENTS.md "Do not build access control between bots"). ADR-0004 amendment 1 and ADR-0036 added an opt-in per-bot working directory `/work/bots/<bot>` and an opt-in platform-prepared git worktree of one shared repository, both conventions that no hook reads, both off until a paired campaign said otherwise.

The long-horizon campaign of 2026-10-11 (issue #88) showed what the shared default costs: a commit that swept in a teammate's in-flight lines, a red-first check that captured a teammate's stub, two runs overwriting another bot's files, duplicated work. On 2026-10-14 the owner ruled (decision 13): every bot works in its own directory by default in every workspace; other bots' directories are read-only to it; this is enforced now at the tool level (option A) as a guard against mistakes; real OS-level isolation (per-bot Unix users or a sandbox) comes later; each bot clones its own code, so the shared-repo worktree feature goes; `/work/uploads` is read-only for bots; the browser profile stays shared; deliverables stay in each bot's directory, readable by the others. The owner's direction for the batch is effectiveness first and no human approvals or limits without a reason, so this ships as a default without the paired campaign ADR-0004 amendment 1 decision 12 and ADR-0036 decision 8 asked for.

## Decision

1. **Per-bot is the default working-directory mode.** `DESKMATES_BOT_WORKDIR` defaults to `per-bot`; `shared` remains a value of that knob and of the workspace's stored `mode` (ADR-0036 decision 1), set by an Owner or Admin. A workspace that stores no mode follows the Gateway default, so existing workspaces switch to per-bot at the upgrade that ships this ADR; a workspace that stored `shared` keeps it. A run keeps the mode it froze at its first process (ADR-0036 decision 3), so a run already parked at the upgrade resumes where it started. In per-bot mode a run starts in `/work/bots/<bot name>`, which the sidecar creates.

2. **Another bot's directory is read-only to a bot.** In a per-bot run the sidecar's `PreToolUse` hook refuses, before any approval or tier check:
   - `Write`, `Edit`, `MultiEdit` and `NotebookEdit` whose target path, resolved against the run's working directory, is `/work/bots/<name>` or below it for any `<name>` other than the bot's own;
   - a shell command (`Bash`, and the data typed into `tty_session`) with an obvious write there: an output redirection (`>`, `>>`, `&>`, `>|`) to such a path; `rm`, `rmdir`, `unlink`, `mv`, `touch`, `mkdir`, `tee`, `truncate`, `chmod`, `chown`, `chgrp`, `shred` naming one; `cp`, `install`, `ln` or `rsync` whose destination is one; `sed -i`, `perl -i` or `dd of=` on one; a `git` command other than a read-only subcommand (`status`, `log`, `diff`, `show` and similar) whose `-C` directory, `--git-dir`, `--work-tree`, working directory (`cd` earlier in the same command included) or an absolute or `..` path argument is in such a directory, and a `git clone` into one. `rm`, `rmdir`, `mv`, `chmod`, `chown` and `chgrp` on `/`, `/work` or `/work/bots`, which contain other bots' directories, are refused too.

   Reading is never refused: `Read`, `Grep`, `Glob`, `cat`, `cp` from a teammate's directory into one's own, `git clone` or `git log` of a teammate's repository all run as before.

3. **`/work/uploads` is read-only for bots in every mode.** The same hook refuses the same write forms into `/work/uploads` or below it, in shared mode as well. People add uploads through the Gateway (`deskmates-sidecar file-write`, ADR-0014 amendment A5) and Admins delete them in Files; neither path goes through a bot's hook.

4. **The refusal says where the bot may write.** The deny reason names the path, whose directory it is (a teammate's or the uploads area), that it is read-only to this bot, and the bot's own directory as the place to write (copy the file there to change it). Each refusal is a `log` event `{source: "bot_dirs", op: "write_refused", toolName, toolUseId, path, area}` in the run's ledger. The per-bot system prompt states the same rule up front.

5. **A guard against mistakes, explicitly not a security boundary.** The hook reads the literal tool input. It does not follow symlinks, expand variables or globs, see writes made by a script, an interpreter (`python -c`, `node -e`), a build tool, a subprocess, a later `cd` made by an earlier tool call, or a browser download, and every bot runs as the same Unix user with write permission on every directory. Anything that must not be writable by a bot still goes in a second workspace (ADR-0004 decision 5). Code comments, the Gateway and sidecar docs and AGENTS.md say this. OS-level isolation between bots (per-bot Unix users or a sandbox) is a later decision, not this ADR.

6. **What stays shared.** The browser, its profile, cookies and login state; the rest of `/work` outside `bots/` and `uploads/` (an existing shared checkout, a team area); bot homes and `/tmp`; process environments; other bots' transcripts. A bot's deliverables stay in its own directory, where its teammates can read them. In shared mode only decision 3 applies.

7. **Each bot clones its own code; the platform prepares no worktree.** ADR-0036's `worktreeRepo` is removed: the workspace setting and its column (a forward migration drops `workspace_workdir_settings.worktree_repo`), the `StartRunRequest.worktreeRepo` field, the sidecar's `git worktree` preparation and its `git` dependency, and the UI field. A `PUT /api/workspaces/:id/workdir` that sends `worktreeRepo` is a `validation` error (an unknown setting). Run rows that froze a `worktreeRepo` before the upgrade keep it in `config_json` as history; it is ignored. The per-bot prompt tells a bot to clone or copy a repository it works on into its own directory and to hand work back by a branch, a patch or a message, never by writing into a teammate's checkout.

8. **The lane notice stays.** ADR-0036 decision 6's note is still useful: a bot's interactive and background runs share its one directory, and nothing in decision 2 separates them. Its text no longer mentions a worktree. It stays a workspace setting, off by default.

9. **A thread's SDK session follows the bot into its directory.** The SDK keys stored transcripts by working directory (`$CLAUDE_CONFIG_DIR/projects/<cwd with every non-alphanumeric character replaced by '-'>/<session id>.jsonl`). When a per-bot run resumes a session that exists only under the shared `/work` key, the sidecar copies that transcript to the bot directory's key before the query and logs `{source: "workdir", op: "session_carried"}`, so existing threads keep their context across the switch in decision 1. Best effort: a failed copy is a warning and the SDK behaves as it would without it.

10. **Relation to earlier decisions.** ADR-0004 decisions 1, 4, 5 and 6 stand, and decisions 2, 3 and 7 stand for the browser, cookies, logins and everything outside decision 2 and 3's paths. ADR-0004 amendment 1 decisions 10, 11 and 13 stand (the platform creates no worktree; the mode is recorded per run; lane awareness is ADR-0036 decision 6). ADR-0036 decisions 1 (mode and lane notice), 3 (freeze at first start, without `worktreeRepo`), 6 and 9 stand. The test strategy's §11 row "No access control between bots" now reads: no rejection branch whose reason is another bot's ownership, except this ADR's directory guard.

## Alternatives considered

- **OS-level isolation now (per-bot Unix users, mount namespaces).** A real boundary, but it changes the image, the supervisor, file ownership of every existing workspace and how the browser and shared tools run. The owner deferred it ("后面再说").
- **Refuse every write outside the bot's own directory.** Simpler to state, but bots need their homes (memory, diary), `/tmp`, caches and existing shared checkouts; refusing those breaks runs for no gain against the observed collisions, which were bot-to-bot. The owner's rule names other bots' directories and uploads; this ADR refuses those.
- **An L2 approval instead of a refusal.** It would put a human in front of a mistake the bot can fix itself by writing in its own directory, against the owner's direction to minimize approvals.
- **Keep the shared-repo worktree beside the guard.** A shared `.git` behind every worktree is a shared write surface the guard cannot see (`git -C` into a teammate's worktree writes the common object store and refs); a clone per bot keeps each bot's repository in its own directory.

## Consequences

- The AGENTS.md rules "Do not build access control between bots", "Bots are separated by…" and the default grouping text change: directories are the one exception, as a soft guard. Everything else stays shared and unguarded.
- Existing stable workspaces switch to per-bot at the next release; a bot's earlier files in the shared `/work` stay where they are and stay writable. Threads keep their SDK session through decision 9; unverified in a real container.
- A bot rename gives the bot a new directory; the old one becomes read-only to every bot, the renamed one included, until a person moves it.
- A team that wants a shared checkout everyone writes into chooses shared mode; per-bot teams integrate by branch, patch or message.
- Strategy change shipped without the paired campaign, by owner decision. Every run still records `botWorkdir` and `botWorkdirSource` in `runs.config_json`, so a later `evals/compare.ts` campaign can attribute results to the mode.
