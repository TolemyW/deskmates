# ADR-0002: The sidecar is the SDK host process, and risk tiers map onto SDK primitives

Date: 2026-09-20
Status: Accepted
Source: S0 spike results, `docs/design/s0-spike-results-2026-09-20.md`

## Context

Design v0.2 draws the sidecar as a component that "forwards" each tool call and decides whether to execute it or suspend for approval. The S0 spike showed that the Claude Agent SDK already exposes exactly the interception points needed, inside the process that calls `query()`. A separate forwarding layer would add a moving part and gain nothing.

## Decision

1. **The sidecar is the Node.js process inside the bot container that calls `query()`.** There is no proxy between the agent loop and its tools.

2. **Risk tiers map onto SDK primitives:**

   | Tier | Mechanism |
   |---|---|
   | L0 read-only, L1 reversible write | `PreToolUse` hook returns `permissionDecision: "allow"` |
   | L2 external side effect, human online | `canUseTool` callback blocks until the Gateway relays the decision or the short-wait timeout (default 5 min) passes |
   | L2, timeout or human offline | `PreToolUse` hook returns `permissionDecision: "defer"`; the query ends and reports its session id; the run is marked `waiting_approval`; the process may exit |
   | Approval arrives later | Gateway starts a new run with `resume: sessionId`; the SDK replays the deferred call through the hook, which now returns `allow` or `deny` |

   Verified across two separate processes in S0 test-b.

3. **SDK state lives on the bot's persistent volume.** The sidecar sets `CLAUDE_CONFIG_DIR=/home/bot/.claude`, `settingSources: []`, and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Session transcripts under that directory are what `resume` reads, so they must survive container restarts.

4. **Model credentials enter the sandbox as two environment variables:** `ANTHROPIC_BASE_URL` and a short-lived `ANTHROPIC_AUTH_TOKEN` (Bearer). The gateway tested in S0 rejects `x-api-key`. Subscription OAuth tokens cannot be forwarded through a third-party base URL (403), so the Gateway holds the upstream credential and issues per-run tokens.

5. **The Gateway prices tokens itself.** The SDK reports `costBasis: "unknown"` for non-Anthropic models. The `runs` table stores per-model input, output, cache-read, and cache-creation token counts; `cost_usd` is computed from a Gateway price table.

6. **Reasoning output is a ledger event.** Models behind the gateway emit `thinking` content blocks. `RunEvent.kind` includes `thinking` so replay does not drop it.

7. **The model is a deployment setting, not a design constant.** `DEFAULT_MODEL` and `CHEAP_MODEL` come from the environment. Section 10 feasibility ratings in design v0.2 assumed Claude-class models; they are re-baselined on the deployed model at M0 acceptance.

## Consequences

- `@deskmates/sidecar` is the only package that imports the Agent SDK.
- Design v0.2 sections 2, 3.5, 3.8, 4, and 5 are read with this ADR applied; a v0.3 will fold it in once the model path is decided.
- The two-lane scheduler runs two sidecar `query()` calls in the same container, each with its own session, sharing `/work` and the browser lock.

## Definitions added on review (2026-09-20)

The decisions above use three phrases that had no fixed meaning. These are the meanings; each is a default to be calibrated, not a finding.

- **Human online.** A human is online for a run when, at the moment the L2 call reaches `canUseTool`, at least one operator client subscribed to that workspace's approval feed has a live SSE or WebSocket connection or a heartbeat within the last 60 s. Channel adapters (M3) count as online only if the channel can deliver an approval prompt and receive the reply. Otherwise the human is offline and the hook defers at once instead of waiting 5 min.
- **Short-lived token.** `ANTHROPIC_AUTH_TOKEN` is issued per sidecar process, not per logical run. TTL default 4 h (`MODEL_TOKEN_TTL_SECONDS`). The Gateway revokes it when the run reaches a terminal or parked state; `resume` starts a new process with a new token. The token is opaque to the sidecar and never appears in the ledger.
- **Unknown model in the price table.** `cost_usd` is stored as NULL, the run still succeeds, and the ledger gets a `pricing_missing` event naming the model. Cost reports show the run as unpriced rather than zero.

## Amendment 1 (2026-09-21): the short wait lives in the `PreToolUse` hook

Found while implementing M0 against `@anthropic-ai/claude-agent-sdk` 0.3.278 (`sdk.d.ts`, `PermissionResult`, `HookJSONOutput`). S0 test-b verified the live wait in `canUseTool` and the `defer` return from the hook as two separate experiments; it never composed them. They cannot be composed as decision 2 describes:

- The SDK runs the `PreToolUse` hook once, **before** `canUseTool`.
- Only the hook can return `permissionDecision: "defer"`. `canUseTool` returns `{behavior: "allow"} | {behavior: "deny"}` and nothing else.

So a wait placed in `canUseTool` can end in allow or deny but never in a parked run. Decision 2's table is replaced by:

| Tier | Mechanism |
|---|---|
| L0 read-only, L1 reversible write | `PreToolUse` hook returns `permissionDecision: "allow"` |
| L2, human online | the **hook** posts the approval request and blocks, polling the Gateway, until the decision arrives or the short wait (default 5 min) elapses; on a decision it returns `allow` or `deny` |
| L2, timeout or human offline | the hook returns `permissionDecision: "defer"`; the query ends and reports its session id; the run is marked `waiting_approval`; the process may exit |
| Approval arrives later | unchanged: the Gateway starts a new run with `resume: sessionId`; the SDK replays the deferred call through the hook, which consumes the human's decision and returns `allow` or `deny` |
| `canUseTool` | a fail-closed backstop: anything that reaches it without a hook decision is denied and logged. It is registered so the SDK never falls through to its own interactive prompt |

Consequences:

- The hook's SDK `timeout` must exceed the short wait; the sidecar sets it to `shortWaitSeconds + 60`.
- "Human online" (Definitions above) is decided by the Gateway when the approval request arrives, not "at the moment the L2 call reaches `canUseTool`". If the human is offline the Gateway answers `defer` at once and the hook parks the run without waiting.
- A hook that blocks for minutes is verified only against the fake SDK (T1) and for seconds against the real one (S0 test-b short-wait, 20 s). A spike that blocks a real hook for the full 300 s is owed before M1 acceptance; if the SDK kills long hooks regardless of `timeout`, the fallback is to shorten the live wait and defer earlier, not to move the wait.
- AGENTS.md "Risk tiers" and `packages/sidecar/README.md` are reworded to match. Design v0.3 §3.5 and §5 step 4 are read with this amendment applied.

### Recorded gap: page content is not yet wrapped as untrusted

AGENTS.md requires browser and external tool output to be wrapped as untrusted before it enters model context. In M0 the sidecar wraps bot-authored thread messages and webhook bodies, but Playwright MCP tool results reach the model raw: the SDK executes MCP tools itself and hands the result straight to the model, and `PreToolUse` sees only the input. There is no `PostToolUse` rewrite of results in 0.3.278.

Decision: the wrap will be done by a **stdio proxy in front of the Playwright MCP server**, owned by the sidecar. The proxy forwards JSON-RPC unchanged except that every `tools/call` result's text content is wrapped as `<untrusted source="page:<host>">…</untrusted>` with any embedded closing tag neutralised, the same treatment bot messages get today. This keeps rule 1 of this ADR (no process between `query()` and tool execution) because the proxy is on the MCP side of the SDK, not between the SDK and its tools, and it is the only point that sees every page-derived result. Alternatives rejected: a system-prompt instruction alone (no boundary at all); patching `@playwright/mcp` (forks the pinned dependency). The injection corpus (T3, test strategy §3.4) is the test that closes it.

Closed 2026-09-22 (M1 gap batch): the proxy is `deskmates-sidecar mcp-proxy`, which the sidecar puts in front of `playwright-mcp` in the SDK's MCP server config. "Neutralised" is stronger than the bot-message wrapper's regex: the wrapped body has every `<`, `>` and `&` replaced by its HTML entity, so it contains no `<` character at all and no closing tag of any spelling can exist inside it, whatever a tolerant reader would accept. The ledger keeps the raw result, because the sink records the SDK's `tool_result` and the wrapper exists only in model context. The same proxy takes the ledger screenshots (test strategy §7) after every page-changing browser action, which is why it is one process and not two.

## Amendment 2 (2026-09-22): approvals are thread messages, and any member may decide

M0 shipped the approval path as a stub that denies every L2 call. M1 makes it real. Design v0.3 §3.5 names the decision options (Allow once / Always / Deny) and the rule dimensions; it does not say where an approval request lives or who may answer it. This amendment fixes both, keeping the hook mechanics of amendment 1 unchanged.

A1. **An approval request is a message in the run's thread.** The Gateway posts it as a `system` message whose body carries the proposed action: the tool name, the target host where there is one, the arguments as the hook saw them, and the human's original instruction (the message that woke the run). It never carries page content, tool results or anything else the model derived from a site: the approver decides on what the bot proposes to do and what it was asked to do, and page text is the injection vector approvals exist to catch. A decision is recorded on the request (`approvals` row) and echoed into the thread; the run's ledger keeps an `approval` event for the request, the decision, and every rule change.

A2. **Any member of the thread may decide.** A human decides from the operator UI (an inbox of pending approvals, and the same card inline in the thread). A bot decides through an `approval_decide` sidecar tool with `{approvalId, decision, reason}`; the Gateway accepts it only from a run whose bot is a member of the thread the request was posted in, and records which bot decided. Who the approver is (the human, or a "security officer" bot the operator adds to a thread with a `SOUL.md` written for the job) is usage, not product: a deciding bot is a soft boundary of the same kind as SOUL, working directory and grouping (ADR-0004), not a security boundary, and the docs say so. Membership is the whole test: the requesting bot is a member too, so in a one-member thread it may decide its own request from a later run (which is why the deferral note in ADR-0006 calls the approval path a soft boundary). Authorisation and wake are different things: posting the request wakes every *other* member of the thread on the interactive lane, exactly as a human message would, so a deciding bot sees the request as an unseen `system` message and answers with `approval_decide` while the requester's run is still in its short wait, or after it has parked. The requesting bot is not woken by its own request; its run is the one waiting. A bot's decision inside the short wait resolves the live wait like a human's; after a defer it resumes the parked run like a human's.

A3. **Decision order: risk tier → matching rule → thread.** The hook classifies the call (amendment 1). L0 and L1 never reach the broker. For L2 the Gateway first looks for a stored rule on the bot; a matching `allow` rule answers `allow` and a matching `deny` rule answers `deny` at once, with an `approval` event saying which rule, and nothing is posted to the thread. Only an unmatched L2 request becomes a thread message and starts the short wait. The three decisions are Allow once (answers this request only), Always (answers it and stores an `allow` rule) and Deny (answers it; storing a `deny` rule is a separate operator action). A rule is `(botId, toolName, targetOrigin, argumentPattern)`; the origin and the pattern are globs with `*` as the only wildcard. Rules are listed and deleted from the operator API; a store or delete is an `approval` ledger event on the run it came from (the run whose request was answered with Always, or the run whose `approval_decide` stored it), and a rule created or deleted by an operator outside any run records only its `createdBy` on the row. The timeout, offline and resume behaviour of amendment 1 is unchanged: the deferred call resumes with `resume: sessionId` and the decision applies to that `toolUseId` only.

**Stable matching across runs.** A browser click carries no URL and its `ref` changes on every snapshot, so a rule built from the raw input would never match twice. The sidecar therefore derives two fields on every `ToolAction`: `targetOrigin` for a browser tool is the origin of the page the run last navigated to (tracked in the hook from every navigation input), and `argumentPattern` is the stable part of the arguments: for a browser click the side-effect phrase that made it L2 (`*submit*`), for a shell command its program and subcommand (`git push*`). An Always decision stores `(toolName, targetOrigin, argumentPattern)` from the action it answered; a later call matches when its own origin and summary fit those globs. A call with no known origin never matches a rule that names one, so the safe direction is to ask again.

**Resume keeps the ledger whole.** A resumed run is a second sidecar process of the same run row (`runs.attempt` counts them), and the sidecar's event counter restarts at 1 in every process. Redelivery detection is therefore keyed on `(run, attempt, seq)`; the `StartRunRequest` carries `attempt` and every `SidecarEvent` echoes it. A decision may arrive while the sidecar is timing out or already exiting: the Gateway records it against the approval whatever the run's state, `run_ended(deferred)` then finds the decision already there and the run is resumed at once; a second decision for the same approval is `409 invalid_transition`; a parked run whose approval was decided is resumed by the scheduler exactly once, including after a Gateway restart, because the resume is the transition `waiting_approval → running` inside one scheduling pass. Events the Gateway itself appends to a run (`resumed`, `decided`, rule changes) carry the run's current `attempt`, so the ledger agrees with itself.

**The decision survives a stale snapshot.** Found in the first M1 T3 run: a resumed run is a new sidecar process and therefore a new Playwright MCP session, and a browser `ref` is local to a snapshot of that session. The SDK replays the deferred click with the old process's `ref`, the click fails, the model snapshots and clicks again, and that retry is a fresh L2 call, so "the decision applies to that `toolUseId` only" meant the decision never applied to a browser action. Rule: the resume decision is consumed by the replayed call or, when that call's result is an error, by the first later call in the same process whose stable dimensions `(toolName, targetOrigin, argumentPattern)` equal the deferred action's; then it is spent, and it never survives the process. The `approval` event records which call consumed it (`consumedBy: replay | retry`). For the origin to be known before the resumed process navigates, the parked process reports `currentOrigin` in `run_ended(deferred)`, the Gateway keeps it in `resume_payload`, and the `approval` trigger of the resume carries it together with the deferred action's dimensions.

**A parked run holds its thread.** A parked run does not occupy its bot's lane (ADR-0005), but it does own the `(bot, thread)` SDK session it will resume. A run queued for the same bot and thread therefore starts only after the parked run has resumed and ended; otherwise two processes would open one session, which decision 3 forbids. Runs of the same bot in other threads, and of other bots, are unaffected.

Consequences:

- `packages/contracts` gains the `approval_decide` tool in the sidecar protocol, the `Approval` and `ApprovalRule` shapes, and an `approval` message body shape for the thread. The `approval` `RunEvent` kind already exists.
- Posting a message into a thread from a run, which ADR-0005 places in M2 as `thread_post`, is pulled forward only as far as the Gateway needs to post the request and echo the decision; mention routing, caps and the group UI stay in M2.
- ADR-0006 being deferred, the decide route is unauthenticated like every operator route; that ADR's deferral note records the accepted consequence.

## Amendment 3 (2026-10-12): approvals in unattended workspaces

Status: Accepted (owner-signed 2026-10-17, issue #3: "ADR-0002 amendment 3 (A4–A11): signed. A6 (Always from a stable target) and the per-workspace tier override of A5 may be built."); Proposed from 2026-10-12 until then. Amendments 1 and 2 stay in force except where a decision below names the sentence it replaces. The sign-off does not revive text a later amendment replaced: amendment 4 still replaces A11 where both speak, and amendment 6 D7 still sets A7's default to 60 minutes.

Found in the long-horizon campaign of 2026-10-11 (four peer GLM-5.3 bots, no chief, release v0.5.0 to v0.5.3) and recorded in issue #54; corroborated by the v0.5.6 knowledge-base campaign of the same day and the v0.5.6 trial of 2026-10-12. Amendment 2 assumed a human who reads the thread. With nobody present:

- A2's wake made approvals the main source of runs: 7 of the first 8 thread runs were woken by an "Approval needed" notice and 1 by the human kickoff. The campaign team's own export showed 20 approval-woken runs, 16 of them silent. A woken bot took the notice for its instruction and raised its own approval, and the card showed the previous notice as "Instruction", nesting notices inside notices.
- The SDK `Agent` tool is in no tier table, so it falls through to the unknown-tool default and is L2. Gating the spawn adds no safety: every tool call inside the subagent still passes our `PreToolUse` hook, whose input carries `agent_id`. 4 of the first 10 approvals were `Agent` spawns for read-only exploration. `ListAgents({})` parked a coordinator the same way on 2026-10-12.
- "Always" from the UI stored the exact, truncated argument summary as `argumentPattern`. For free-text tools such as `Agent` that rule can never match again, so "Always" meant "once".
- A request either waited forever (`waiting_approval` has no expiry) or was approved by a teammate on the grounds that the human was away. Approvals from cron runs have no thread and notified nobody.

The campaign team proposed reminders that re-post the request into the thread and wake its members again (their ADR-0002 amendments 3 and 4). The independent review found that this multiplies the wakes above and posts into paused threads whose wakes never launch; it is not adopted.

External practice (issue #54, read 2026-10-11) agrees on five points: deterministic rules first; an optional reviewer in the middle that never sees tool results or the agent's own text; fail closed or to a human; an override covers one exact action; unattended requests expire (Grok Bot: about 10 minutes, and the action does not run). Every vendor says the reviewer is not a security boundary. GitHub Copilot's coding agent structurally forbids a requester from approving its own request.

A4. **Approval notices are routing-inert.** An approval request, its decision echo, its expiry and every reminder are `system` messages that wake no member. This replaces A2's sentence "posting the request wakes every other member of the thread on the interactive lane". Members see the request in their next delivery, marked as an approval notice (the sidecar renders a `system` message carrying an approval attachment as `[system: approval notice]`), and may decide it with `approval_decide` then. An approval notice is never a run's trigger or its instruction: the "waking instruction" on a card is the originating human message, found by following the requesting run's wake chain past bot messages and past `system` messages that name a run (a delegation outcome or continuation notice), so notices never nest. When the chain reaches no human message, the card shows the bot message that woke the run, and never a `system` message; a cron or webhook run shows none. The only run a request affects is the requesting run, resumed on decision or expiry. ADR-0016 decision 3 (a continuation request wakes its delegator) is unchanged: it wakes one named bot that asked for the work.

A5. **Tiers come from a curated table, and subagent spawns are L1.** The sidecar's tier table lists every tool of the pinned SDK and MCP servers on purpose: SDK `Agent`/`Task` are L1, because each tool call inside the subagent passes the hook with `agent_id` set; SDK read-only discovery tools such as `ListAgents` are L0; `tty_session` input that is a complete shell line is tiered by the shell rules. The ledger records a spawn's `description`, `prompt` and `agent_type`, and the card of an L2 call made inside a subagent shows its `agent_type`. An operator may override a tool's tier per workspace; the override is an operator action recorded with `createdBy`, never a bot action. A tool in no table is still L2, so new tools fail closed, but the request is labelled `unclassified` on the card and in the `approval` event, so an unknown tool is visible instead of silently treated as risky.

A6. **"Always" is built from a stable target.** The rule an Always decision proposes is the tool plus a stable target, by tool kind: the origin for browser and HTTP tools, a path prefix for file tools, the program and subcommand for shell (as A3 already does in the sidecar), the `agent_type` for subagent spawns. It is never the displayed argument summary. The human sees the proposed matcher and may edit it before saving. The Gateway refuses to store a rule that does not match the action it answers, or whose pattern ends in the truncation marker; it warns when a pattern contains no wildcard on a free-text field, because such a rule matches only this action again.

A7. **An unattended request expires to deny.** A pending L2 request that nobody decides within `approval_expiry_minutes` (per-workspace knob, default 15, a guess; Grok Bot uses about 10) is denied with `decided_by = system:expiry`. The expiry is an `approval` ledger event and a visible card state. The model receives: "Nobody approved this within N minutes. It was not done. Do not try to reach the same effect another way; report what is blocked, then continue with other work or end." The requesting run resumes as on any deny. Continuation requests keep ADR-0016's 24-hour window. The knob is the column `workspaces.approval_expiry_minutes` (a whole number from 1 to 1440), read and changed with the automatic-approval setting (`GET`/`PUT /api/workspaces/:id/auto-approval`, field `expiryMinutes`) by an Owner or Admin, each change one `workspace.approval_expiry_set` audit row. The window counts from the request's creation and covers tool and egress requests, including one still waiting for its automatic review (a verdict after the expiry is `review_late`). The scheduler's periodic pass settles expired requests, so an expiry lands within one sweep interval (60 s) of its deadline.

A8. **Reminders go to humans, never to bot wakes.** Before a request expires, one reminder goes to the operator UI's approval inbox and to the human channels configured for the workspace (ADR-0017, ADR-0019). No reminder is a thread message that wakes a bot, and nothing reminds a bot. Mechanism: when a third of the window is left (five minutes before a 15-minute expiry; the fraction is a guess), the Gateway records `approvals.reminded_at` once, appends an `approval` event `reminded`, re-publishes the approval to the inbox and posts one routing-inert `system` message carrying the approval attachment into the request's thread, which is how a channel bound to that thread relays it to its human. A bot may read that line in its next delivery like any notice (A4); it is never woken by it.

A9. **Threadless approvals reach a human.** A request from a run with no thread (cron, webhook) is posted, routing-inert, in the requesting bot's private chat (ADR-0024's canonical private chat) and appears in the operator inbox. It expires by A7. A threadless continuation request (ADR-0016) is posted the same way. The approval row records that private chat as its thread, so its card, decision echo, reminder and expiry land there; the run itself stays threadless.

**Implementation status (2026-10-14).** A4, A7, A8 and A9 are implemented as written, still Proposed: the owner has not signed off amendment 3. The values `approval_expiry_minutes = 15` and "a third of the window left" are proposed defaults.

**Implementation status (2026-10-17, issue #3, at sign-off).** Also implemented: A10 (`approvals/bot-decision.ts`) and A5 except the per-workspace operator tier override (the curated table with `Agent`/`Task` L1, `ListAgents` L0, `tty_session` lines tiered as shell, the `unclassified` label and the subagent's `agent_type` on the card). Not implemented at sign-off: A5's tier override and A6; an Always decision still stores the sidecar's `argumentPattern` or, when it gave none, the argument summary verbatim (`matcherFromAction` in contracts). A7's default is 60 minutes since amendment 6 D7.

**Implementation status (2026-10-17, after sign-off).** A6 and A5's per-workspace operator tier override are implemented; every decision of this amendment is now built. How they were read where the text leaves a choice:

- A6, the stable target per kind (`matcherFromAction` in contracts): the sidecar's stable `argumentPattern` with the origin beside it when it derived one (shell program and subcommand, a click's side-effect phrase, the hash patterns of amendment 5 C4 and of `tty_session`, the connector and integration patterns); else a file tool's directory prefix (the path up to its last `/`); else the origin. The subagent type is carried as the pattern `agent <type>: *` over a new spawn summary `agent <type>: <description>` (the SDK's `subagent_type`; `default` when absent). For a tool A6 names no kind for (an SDK tool such as `SendMessage`, an unclassified MCP tool) the sidecar adds `inputSha256`, the SHA-256 of the input, set only when the action has no pattern, path or origin; a rule bound to it matches that exact input and nothing else, which is the narrowest stable target, and it carries the warning below. An action with no stable target at all (one recorded before A6 with only a summary) gets no proposal: Always is refused with `rule_no_stable_target` unless the human writes the matcher.
- A6, the checks (`checkAlwaysRule` in contracts, `approvals/always-rule.ts`): refusals are 400 `validation` with `details.reason` `rule_pattern_truncated` or `rule_does_not_match_action`, run before anything is decided, so the request stays pending. The warning (`exact_arguments`) is raised for an `argumentPattern` without `*` unless it is the sidecar's own pattern for the answered action (the integration pattern `integration:<service> action:<id>` is a structured field, not free text); an input-hash rule warns `exact_input`. The rule routes (`POST /api/bots/:id/approval-rules`, `PATCH /api/approval-rules/:id`) refuse the truncated pattern and return the same warnings. The web card shows the proposal as editable fields and runs the same checks while the human types; an unchanged proposal sends no matcher.
- A6, compatibility: rules stored before A6 are not migrated and match exactly as before; only new rules are built from the stable target.
- A5, the override: table `workspace_tool_tiers` (one row per tool, none by default), `GET`/`PUT`/`DELETE /api/workspaces/:id/tool-tiers[/:toolName]` (read by a Member, changed by an Owner or Admin; operator routes, so never a bot action), `createdBy` `human:<actor>` on the row and one `workspace.tool_tier_set` audit row per change. A run's first start freezes its workspace's overrides as `toolTierOverrides` in `runs.config_json` and the `StartRunRequest`, only when there are some, so a workspace without overrides gets exactly the request and row it got before; a resume sends the recorded set and never a newer one. The sidecar applies the override in the hook, the `canUseTool` backstop and the ledger's `tool_call.riskLevel`; it is a deliberate tier, so the tool is no longer `unclassified`. The hard denies run before the tier and are never overridden. `connector_submit` and `integration_execute` are refused as override targets, because ADR-0012 and ADR-0013 tier them by their own policies. A5 names no UI, so there is no web control yet; setting an override in a workspace is an approval-rule change for that workspace in the sense of AGENTS.md.
- Not built: the T3 `acceptance/m1-approvals` extension to `Agent` (an `Agent` spawn asks only under an override raising it to L2; the T1 cases below cover that path with the fake SDK).

A10. **No self-approval.** `approval_decide` is refused when the deciding bot is the requesting bot, or when the request came from a run the deciding bot delegated (it appears upstream in the requesting run's wake chain, ADR-0016 amendment 1 decision 7). A bot may decide `allow_once` or `deny`; `allow_always` from a bot is refused, so only humans store rules. This replaces A2's sentence that in a one-member thread the requesting bot may decide its own request from a later run, and A3's rule store "from a run whose `approval_decide` stored it". A deciding teammate remains a soft boundary, as A2 says: this removes the obvious rubber stamp, it does not make bots a security boundary.

A11. **An approval reviewer is optional, opt-in per workspace, and scheduled by the Gateway.** The Gateway never calls a model. When the workspace enables review, an L2 request still pending after `approval_review_after_seconds` (default 120, a guess) gets one review run: a run row first, attributed to the requesting bot for accounting, with `REVIEW_MODEL` from the environment and the policy version frozen in `config_json`. The sidecar runs it as a reviewer job: a fresh SDK query with no session, no browser, no workspace files, no SOUL or memory, and one structured-verdict tool. Its inputs are the proposed action (tool, tier, target, arguments), the human-authored messages of the thread including the originating instruction, the workspace's operator-written policy and the existing rules; never page content, tool results, bot-authored text, or an ADR-0028 summary. Verdicts are `allow_once`, `deny` or `escalate`; never Always. A hard-deny list (credentials and cookies, payments, messages to external humans, egress widening, deleting what the run did not create, sending workspace data to a new origin) can only be escalated, never allowed. An error or timeout escalates. Three consecutive reviewer denials in one run send its later requests to humans only. A verdict is recorded with `decided_by = reviewer:<model>`, its tokens and the policy hash. Enabling review is a strategy change and is measured with `evals/compare.ts` against human decisions on recorded requests, false negatives reported.

**Order.** Tier, then stored rule (A3), then the thread and humans; the reviewer, when enabled, after its delay; expiry last. A decision from any source settles the request once; a later one is `409`.

**Relation to ADR-0028.** ADR-0028's summary is presentation: it explains a long request to a human and never gates or decides. That stays true. The reviewer does not read the summary, the summary never reads a verdict, and both are separate background jobs. A6's matcher and A11's verdict are shown on the same card beside the summary, each labelled with its source. ADR-0028 decision 3's rule that summary output changes no action, matcher or decision is unchanged.

Alternatives considered for this amendment:

- **Remind by waking the thread** (the campaign team's escalation sweep). Each reminder is another round of mostly silent runs, and a reminder into a paused thread creates wakes that never launch. Rejected.
- **Keep the unknown-tool fallback and add `Agent` to an allowlist.** Fixes one tool; the next SDK or MCP release has the same problem. A5 makes the table deliberate and the unclassified case visible.
- **No expiry; wait for a human.** What exists today: a request can hold a run and a cron entry indefinitely. Rejected.
- **A reviewer on by default.** It is a model making safety decisions; it ships off and is measured before anyone relies on it.
- **Forbid bots from deciding at all.** Stronger than the evidence asks for and against A2's usage model (a security-officer bot). A10 removes self-approval and Always only.

Consequences (amendment 3):

- The wake path of `approvals/broker.ts` posts without routing; the `approval_decide` route gains the A10 checks; `approvals` gains `decided_by` values `system:expiry` and `reviewer:<model>`; the workspace gains `approval_expiry_minutes` and the review knobs.
- `contracts` gains the `unclassified` request label, the stable-target matcher shape and the reviewer verdict.
- `packages/sidecar` gains the curated tier table, the reviewer job mode and a T2 shape test against the pinned SDK's tool list.
- Bot SOULs that relied on being woken by an approval to decide it must be woken some other way; that is a strategy change and is measured.
- Issue #54 items 3 and 4 (readable cards) are covered by ADR-0028 and A4; item 7 (`tty_session` file ownership) is not covered here.

## Amendment 4 (2026-10-14): workspace automatic approval with an independent reviewer

Status: B1, B2 and the boundary in B3 are owner decisions (issue #54, 2026-10-13). B3's protected list and B4 to B7 were Proposed and are Accepted under owner delegation (2026-10-17) as amendment 6 changed them (B1 replaced by the approval mode, B3's browser and no-human-instruction exclusions removed, B6's threshold five). Still pending and not accepted by this: the paired `evals/compare.ts` measurement of reviewer verdicts against recorded human decisions (reviewer agreement and false-negative rate; no real-model review has been measured), and a reviewer model distinct from the actor's. Amendment 3 was owner-signed on 2026-10-17; this amendment replaces its A11 where both speak, and leaves A4 and A6 to A9 as they are. Amendment 6 (owner-decided 2026-10-14) replaces B1 with the approval mode, removes B3's browser and no-human-instruction exclusions, and raises B6's threshold to five.

The owner rejected a notification-only first slice: unattended workspaces need a real answer, and that answer is an independent AI reviewer the workspace switches on. The owner confirmed one workspace-wide setting beside the network policy, applying to every bot and subagent; that explicitly requested routine actions (uploading a named file, sending a named message, pushing a development branch) may be judged by AI and run directly; and that permanent deletion, permission expansion and other protected high-risk actions stay with a human. Automatic review never overrides a network denial or widens egress. Browser-action review is deferred with #78 (owner, 2026-10-13) and is not part of this amendment.

B1. **One workspace setting, off by default, changed by an Owner or Admin.** `workspaces.auto_approval` is a boolean, `false` for every new workspace and for every workspace that existed before it. It is shown and changed beside the network policy in the workspace settings, through `GET`/`PUT /api/workspaces/:id/auto-approval`; a Member, a Guest or a `member` principal gets `403`. It applies to every request of every bot in the workspace, including calls made inside a subagent. Each change writes one `workspace.auto_approval_set` audit row with `before` and `after` in the same transaction; setting the current value again writes nothing.

B2. **Every approval decision is in the audit record.** A human's, a bot's, a stored rule's, a reviewer's and a `system:` decision each write one `approval.decide` row in the transaction that records the decision (ADR-0031 decision 11), with the actor label as stored in `decided_by`. A page to browse the record comes later.

B3. **What the reviewer may see, and what it never decides.** With the setting on, an L2 request that no stored rule answered (A3) goes to the reviewer at once; there is no human-first delay (this replaces A11's `approval_review_after_seconds`). These requests are not eligible and go to humans exactly as without the setting: egress asks (ADR-0020; review never adds a host), continuation requests (ADR-0016), browser tools (deferred, #78), tools no tier table names (`unclassified`, A5), a run whose wake chain reaches no human-authored message, and the protected actions: permanent deletion (`rm`, `rmdir`, `shred`, `unlink`, `find -delete`, `git clean`, `git reset --hard`, `git branch -D`, `git push --force` or `-f` or `--delete`, SQL `DELETE`/`DROP`/`TRUNCATE`), permission expansion (`sudo`, `su`, `chmod`, `chown`, `chgrp`, `setfacl`, `usermod`, `useradd`, `passwd`, `visudo`, a write to `authorized_keys` or `sudoers`), and actions that carry a credential (a secret-shaped field the broker scrubbed). The list is deterministic, in `approvals/auto-review-policy.ts`, and checked before any model is asked; a protected action the model would allow is never sent to it.

B4. **The reviewer is a model job, and the Gateway still calls no model.** A review is a run, row first: `runType = approval_review`, attributed to the requesting bot for accounting, with the approval id, the action's hash, the review policy version and the model frozen in `config_json`, on the workspace's default model. The sidecar runs it as a short model job (ADR-0023 amendment 1): a fresh query with no session, no SOUL, no memory, no browser, no files, no tools, one turn, 60 seconds. Its input is a package the Gateway builds: the requesting bot's name, the action (tool, tier, target origin, argument summary and pattern, file path, the input as the hook saw it, after the secret scrub) and the originating human instruction, found by following the requesting run's wake chain past bot messages to the first human-authored message. It never contains a tool result, page text, a bot-authored message, SOUL, memory or an ADR-0028 summary. The model returns `{"verdict": "allow_once" | "deny" | "escalate", "reason": "..."}`. The Gateway accepts a verdict only while the approval is still pending and its action hash matches the frozen one; `allow_once` and `deny` settle it with `decided_by = reviewer:<model>` like any other decision (the hook gets `allow` or the deny reason, a parked run resumes); the reviewer never answers Always. `escalate`, an unparseable reply, a failed or timed-out job, and any refusal settle nothing: the request is posted to its thread for humans (A1/A2), with an `approval` event `review_escalated` naming why. A verdict that arrives after another decision is dropped with an event `review_late`; it never overwrites.

B5. **Review does not queue behind the bot it reviews.** While its review is pending a request is not posted to the thread, wakes nobody, and the requesting run waits live whether or not a human is online; when the short wait ends first the run parks and the verdict resumes it as a human decision would. A review run starts without waiting for its bot's lane (the actor holds that lane while it waits), bounded to two concurrent reviews per workspace; it holds no lane, session or browser lock itself.

B6. **Three reviewer denials in a row hand the run to humans.** When the last three reviewer verdicts on one run were all `deny`, that run's later requests skip review and go to humans; a human decision on the run resets nothing automatically, the next run starts fresh.

B7. **Review is charged and bounded like any run.** Its tokens are the workspace's (ADR-0032); a budget park or a capacity wait holds the review run like any other, and its request is then answered by a human or by the eventual verdict, never allowed by default.

Not decided here: routing-inert notices (A4), expiry (A7), reminders (A8) and threadless requests (A9), which amendment 3 decides (owner-signed 2026-10-17). Also proposed for later, and not accepted by the 2026-10-17 delegated review: a reviewer model distinct from the actor's (`APPROVAL_REVIEW_MODEL`); an operator-written review policy text in the package; tracing a cron task's operator-written prompt as the originating instruction (since answered by amendment 6 D3's `cron_prompt` label); a paired `evals/compare.ts` measurement of reviewer verdicts against recorded human decisions before relying on the setting in production. Turning the setting on is a strategy change in the sense of AGENTS.md.

Alternatives considered for this amendment:

- **Notification-only first slice.** Rejected by the owner: it leaves the unattended stall in place.
- **Human first, reviewer after a delay (A11).** Keeps the run stalled for the delay in the case the setting exists for; a human can still decide while the review runs, and the first decision wins.
- **Reviewer in the Gateway.** The Gateway never calls a model (AGENTS.md); the existing model-job path already gives a recorded, tool-free, attributable run.
- **Let the reviewer answer Always.** Rejected: only humans store rules (A10), and a verdict covers one exact action.

Consequences (amendment 4):

- Migration `…-workspace-auto-approval.sql` adds the column and seeds the audit action.
- `contracts` gains the `approval_review` model job and the verdict parser; `packages/sidecar` gains its prompt; `approvals/auto-review.ts` queues and settles reviews; the scheduler lets a review run start past its bot's lane.
- The web workspace settings gain the toggle beside the network policy; the approval card shows `reviewer:<model>` as the decider.

## Amendment 5 (2026-10-14): effect coverage for generic browser code

Status: Accepted under owner delegation (2026-10-17) as a design behind the knob, and **not in force by default**: `BROWSER_CODE_APPROVAL` stays `name-v1`. Accepting the design is not switching it on: a deployment moves to `effects-v1` only after the paired evaluation of C6 and the owner lifting the #78 deferral, neither of which this acceptance gives. Changed on acceptance: amendment 6 made browser actions eligible for review, so C6's expected effect reads per approval mode (in `automatic` an `effects-v1` code call goes to the reviewer first, in `approve_all` it is allowed by the mode, in `manual` it parks on a human), and the C6 comparison is reported per approval mode. Issue #78 found the gap; the owner deferred new browser-operation restrictions on 2026-10-13 ("do not implement ... new generic-JavaScript gates ... in this phase"), so every decision below is implemented behind the knob `BROWSER_CODE_APPROVAL`, whose default `name-v1` keeps today's tiers byte for byte. Switching a deployment to `effects-v1` needs the owner's sign-off and, being an approval-rule change, a paired evaluation (C6). Amendments 1 to 4 stay in force; B3's "browser tools are not eligible for review" was replaced by amendment 6 D3.

Issue #78 measured the pure tier function on string inputs only: `browser_file_upload` with a local path is L2, while `browser_run_code_unsafe` calling `setInputFiles` on the same path, `browser_evaluate` sending a same-origin POST and generic code clicking a "Delete" button are all L1. The table tiers the two code tools by their name (`BROWSER_WRITE_TOOLS`) and the click heuristics read `element`, `text`, `key`, `method` and `submit`, never `code` or `function`. The same holds for `playwright-cli eval` and `run-code` driven from the shell, which the shell rules see as a harmless program. A model therefore gets a weaker approval boundary for the same external effect purely by choosing the generic tool. No end-to-end bypass was demonstrated; the managed egress proxy, origin tracking and result redaction are separate defences and stay as they are.

A keyword scan of JavaScript cannot establish what code does: names can be computed, strings decoded, code loaded at run time. The rules below are therefore a guard rail in the sense of ADR-0020's tool-level egress check, not a security boundary, and the docs must not call them one. Their job is narrower: tool choice alone must not lower the tier of an effect the named tools already ask about, and code the scan cannot read must not be assumed harmless.

C1. **Code is tiered by the effects it may have, never below the named tool for the same effect.** Under `effects-v1` the body of `browser_run_code_unsafe` (`code`), `browser_evaluate` (`function`), and `playwright-cli eval` / `run-code` given on a shell line (the argument after the subcommand) is scanned for these effect classes, each a fixed lower-case label: `upload` (`setInputFiles`, file choosers, assigning `.files`, `DataTransfer`), `submit` (`.submit(`, `requestSubmit`), `network` (`fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, `EventSource`, Playwright `request` APIs), `navigation` (`goto`, `location` assignment or `assign`/`replace`, `window.open`; a navigation inside code cannot get the hook's allowlist check, so it asks), `download` (download events, `saveAs`), `clipboard`, `storage` (cookies in any form, `localStorage`, `sessionStorage`, `indexedDB`, `storageState`, Cache Storage), `routing` (`route`, `unroute`, `routeFromHAR`, extra headers, HTTP credentials), and a `click <phrase>` when the code interacts (`click`, `dblclick`, `tap`, `press`, `check`, `dispatchEvent`, `selectOption`) and names one of the side-effect phrases the named click already uses. Any one of them makes the call L2. Code with none, such as reading text, counting rows or querying the DOM, keeps L1: passive inspection does not gain approval noise.

C2. **Code the scan cannot read fails closed.** A body that is missing or not a string, that does not compile as a JavaScript expression (checked with `node:vm` compilation only; nothing is executed), or that uses dynamic code or obfuscation (`eval`, `Function`, `import(`, `require(`, string-built property access such as `window['fe' + 'tch']`, `\x`/`\u` escapes, `String.fromCharCode`, `atob`, `addInitScript`, `exposeFunction`/`exposeBinding`) is L2 with the label `opaque`. `run-code --filename=<file>` is `opaque` too: the hook does not read the file. A browser code tool is never `unclassified`; it is in the table.

C3. **The named Playwright CLI subcommands that mirror an L2 MCP tool are L2.** Under `effects-v1` a shell line running `playwright-cli` (directly or through the same wrappers the shell rules already unwrap) with `upload`, a cookie, `localstorage`, `sessionstorage` or `state-` subcommand, or `route`/`unroute`, is L2, as `browser_file_upload`, the storage tools and `browser_route` are. Other subcommands keep the shell tier they have today.

C4. **The approval card names the effects, and Always binds to the exact code.** For an L2 browser code call under `effects-v1` the action's `argumentSummary` is `page code: <labels> sha256:<hex>`, the labels sorted and deduplicated, the hash over the code text, so the card shows why it asks in a stable form; the input itself is still on the action. A shell line running an effectful `playwright-cli` command gets the same form, prefixed by the start of the command and hashed over the whole command line. The label list is shortened, never the hash, so the summary stays within the 200-character card limit and the pattern always matches it. `argumentPattern` is `* sha256:<hex>`, as for `browser_cli_workflow`: an Always rule or a replay decision (amendment 2, stale snapshot) covers that code on that origin and nothing else. An effect class is never a rule pattern on its own: "allow any upload code" would be the blanket grant #78 warns against.

C5. **One knob, recorded on every run, and the default is today's behaviour.** `BROWSER_CODE_APPROVAL` is `name-v1` (default, tiers by tool name as before this amendment) or `effects-v1`. The Gateway records `browserCodeApproval` in `runs.config_json` on every run and sends `browserCodeApproval: "effects-v1"` in the `StartRunRequest` only when it is set, so a sidecar under `name-v1` receives exactly the request it received before. The hook, the `canUseTool` backstop and the ledger's `tool_call.riskLevel` read the same tier.

C6. **Switching to `effects-v1` is a strategy change.** Expected effect: some browser runs that today run code unasked will park on a human (browser tools are outside automatic review, B3), mainly runs that upload through code, post through `fetch` or navigate with `goto`. Before a deployment switches, `evals/compare.ts` compares `effects-v1` with `name-v1` on a paired deskbench run, per duration bucket and per approval mode (amendment 6), reporting task success, approvals per run and the share of code calls that asked; the switch also needs the owner's sign-off on deferring #78 no longer.

Alternatives considered for this amendment:

- **All generic code L2.** Simple and sound, but it turns every DOM inspection into an approval while browser capability is the owner's priority; rejected for the default and left as a possible later step.
- **A restricted read-only evaluate interface.** The issue's preferred long-term shape; the owner declined it for this phase.
- **Turn it on now.** Contradicts the owner's deferral of 2026-10-13; the knob lets it be measured first.

Consequences (amendment 5):

- `packages/sidecar/src/browser-code-effects.ts` holds the scan; `risk-tier.ts` and `tool-action.ts` take the policy as an option; `contracts` gains `BrowserCodeApproval` on the start request; the Gateway reads the knob in `config/browser.ts`.
- `packages/sidecar/README.md`'s known gap "After a denied Submit click ... `browser_evaluate` is rated L1" stays true under `name-v1` and is narrowed under `effects-v1`.

## Amendment 6 (2026-10-14): the workspace approval mode

Status: owner-decided (2026-10-14), except the ordering in D4 that was marked Proposed, which is Accepted under owner delegation (2026-10-17): a stored `deny` rule answers before the mode, because it follows the broker order stated below (tier, stored rule, mode, expiry) and a stored deny is a person's explicit answer for that exact action. The owner's direction for the whole batch: minimise human intervention and unnecessary approvals, by bots or humans. This amendment replaces amendment 4's B1 (the boolean), the browser and no-human-instruction exclusions of B3, B6's threshold of three, and amendment 3 A7's default of 15 minutes. Amendments 1 to 5 stay in force everywhere else; amendment 5 is unchanged (its knob still defaults to `name-v1`), except that a browser action is now eligible for review.

The question a workspace answers is no longer "is the reviewer on" but "who answers an L2 request that no stored rule answered": a person, an independent AI reviewer first, or nobody because the workspace allows everything gated. That is one setting with three values. The order inside the broker stays tier, then stored rule (A3), then the mode, then expiry.

D1. **One per-workspace approval mode: `manual | automatic | approve_all`.** `workspaces.approval_mode` replaces `workspaces.auto_approval`. The migration maps an existing `auto_approval = 1` to `automatic` and everything else to `manual`, then drops the boolean. A new workspace starts in `automatic`. An Owner or Admin changes it through `PUT /api/workspaces/:id/auto-approval` with `{"mode": ...}` (the legacy `{"enabled": true|false}` still means `automatic|manual`); a Member, a Guest or a `member` principal gets `403`, and any member reads it with `GET`. Each change writes one `workspace.approval_mode_set` audit row with `before` and `after` in the same transaction; setting the current value again writes nothing. The workspace detail page shows the three choices; while the mode is `approve_all`, a marker saying so is visible in the workspace detail header and in the header of every chat of that workspace.

D2. **`manual`: every request goes to the thread.** Exactly amendment 2 with amendment 3's notices, expiry and reminders: nothing is reviewed and nothing is allowed by the mode.

D3. **`automatic`: the reviewer may also review unattended runs and browser actions.** An L2 request no rule answered goes to the reviewer first (B4, B5 unchanged), with two exclusions of B3 removed. A run whose wake chain reaches no human-authored message is reviewed against the text that started it, and the package labels where that text came from: `human_message`, `scheduled_task` (the human message a task schedule posts, ADR-0021), `cron_prompt` (the operator-written cron prompt), `webhook_body` (external, untrusted data the reviewer must not take as an instruction to widen anything) or `welcome_prompt`; a run with none of these still goes to humans (`no_instruction`). Browser actions, the Playwright MCP tools and the Playwright CLI from a shell, are eligible. Still decided only by humans in this mode: egress asks (review never adds a host), continuation requests, tools no tier table names (`unclassified`), actions that carry a credential, permanent deletion and permission expansion, with the deterministic lists of B3 unchanged. The review policy version becomes 2.

D4. **`approve_all`: every gated action is allowed without asking anyone.** An L2 request no rule answered is allowed at once: the approval row is created already decided `allow_once` with `decided_by = mode:approve_all`, one `approval.decide` audit row, and an `approval` ledger event `mode_allowed`; nothing is posted, nobody is woken, no reviewer runs. Deletion, permission expansion, credential-bearing, unclassified and browser actions are included. An egress ask in a locked workspace is allowed and its host is added to the allowlist by the one existing answered-ask writer (`replaceEgressAllowlist`, the same path as "Allow this site", actor `mode:approve_all`) before the run continues, and the approval is recorded as `allow_always` by `mode:approve_all`; a host the allowlist cannot take (none, or not a public hostname) goes to humans as before. Accepted under owner delegation (2026-10-17), first proposed: a stored `deny` rule still answers before the mode, because it is a person's explicit answer for that exact action.

D5. **What `approve_all` never changes.** Hard denies are decided before any request reaches the broker and stay as they are: private addresses, IP literals and unreadable URLs in the tool-level egress check (ADR-0020), the cloud metadata address, cross-workspace refusals, and the secret scrub of every stored action (`secret-shaped.ts`). The workspace budget (ADR-0032) and the loop breaker (ADR-0005 amendment 5) remain the backstop. The mode is a soft setting of the same kind as the rest of the approval path, not a security boundary.

D6. **Turn-exhaustion continuations under `approve_all`.** Within the continuation limit the run froze at its first start (ADR-0016 amendment 2, default 2), a continuation request is decided `allow_once` by `mode:approve_all` as it is created, and the scheduler resumes the run; the notice still says what happened but asks nobody. Past the limit the run no longer fails outright: the request goes to the reviewer, whose package carries the instruction (D3's labels), the handoff path, the count and the limit. `allow_once` continues once more, `deny` stops the run as a human Stop would, and `escalate`, an unreadable reply or a failed review posts it to the thread, where a person may continue or stop it. A run without a resumable session fails as before. Under `manual` and `automatic` continuations are unchanged.

D7. **Expiry default 60 minutes, the reminder at 40.** A pending request in `manual` or `automatic` expires after `approval_expiry_minutes`, whose default becomes 60 (still 1 to 1440 per workspace); the one reminder still goes out when a third of the window is left, at 40 minutes. Existing workspaces still on the old default of 15 that never changed it (no `workspace.approval_expiry_set` audit row) move to 60. Continuations keep their own window.

D8. **The decider is visible.** An approval card, its thread echo and the inbox name `mode:approve_all` as the decider like any other actor label, so a reader can tell a mode allowance from a person's.

Alternatives considered for this amendment:

- **Keep the boolean and add a second boolean for approve-all.** Two switches have four states, one of them meaningless (approve all with review off or on); one mode with three values says what happens.
- **Approve-all without the hard denies.** Private addresses and IP literals are not approvals; they are refused before any approval exists, and widening them would be a network change, not an approval change (ADR-0020).
- **Approve-all continuations without a cap.** The workspace continuation limit already exists; past it a reviewer decides, so a run that is stuck does not continue forever on the mode alone.

Consequences (amendment 6):

- Migration `…-workspace-approval-mode.sql` adds `approval_mode`, maps and drops `auto_approval`, moves untouched 15-minute expiries to 60, and seeds `workspace.approval_mode_set`; `workspaces.ts` creates a workspace with the 60-minute expiry.
- `contracts` gains `ApprovalMode`, `APPROVAL_MODE_ACTOR` and the mode on `WorkspaceAutoApproval`; `approvals/auto-review-policy.ts` loses the browser exclusion; `approvals/auto-review.ts` resolves the labelled instruction, queues continuation reviews, and opens the breaker at five; the broker answers `approve_all`; `run-lifecycle.ts` decides or reviews a continuation by the mode; the sidecar's reviewer prompt reads the instruction label and the continuation case.
- The web workspace detail section becomes a three-way choice, and an approve-all marker appears in the chat and workspace headers.
- AGENTS.md's L2 risk-tier rule names the mode.
