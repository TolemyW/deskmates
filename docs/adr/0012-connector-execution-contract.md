# ADR-0012: Connectors execute through a typed validate/submit/receipt contract held by the Gateway

Date: 2026-09-29
Status: Accepted (product owner, 2026-10-10; the connector-postgres service has shipped on the stable deployment since v0.3.x). Originally proposed (drafted for the product owner; refines design v0.3 §3.8 "MCP service" and §7 "Database MCP server", and answers the open decision "Database MCP server identity"). Narrowed by ADR-0013 on 2026-09-29: this contract covers receipted execution only; ordinary SaaS actions go through the integration runtime of ADR-0013. Amended by ADR-0026 on 2026-10-11: receipt immutability applies while its owning workspace or bot exists; an explicitly confirmed permanent deletion from Trash is the sole deletion exception.
Source: `docs/design/m3-vendordb-workflow-v2-2026-09-29.md` (three-layer conclusion, product P0), `docs/design/m3-vendordb-longrun-2026-09-28.md`, `docs/design/vendordb-postgresql-compatibility-findings-2026-09-29.md`. Builds on ADR-0002 (risk tiers in the `PreToolUse` hook) and ADR-0004 (no access control between bots).

## Context

Design §3.8 gives a connector the shape "MCP service: registered in the Gateway registry, registered into a bot's sidecar per its definition; the workspace gets an MCP endpoint and a short-lived token". Design §7 names the database MCP server as the built-in connector, reached with "a service identity issued by the Gateway", and leaves how that identity is issued and rotated as an open decision.

Two VendorDB compatibility campaigns ran the database scenario without a connector, through a temporary host adapter: bots wrote request files into the shared workspace, a host process validated and executed them and copied receipts back. What went wrong is recorded per layer in the workflow revision: submissions were mutated after review, rejected submissions were counted as coverage, a request collision could not be attributed from files afterwards, SQL shape errors consumed execution slots, and bots spent turns on `cp`/rename recipes to keep receipt mirrors consistent. What went right in the second campaign was exactly the host-side discipline: a dry preflight that returns a content hash, exclusive submission of a previously validated body, frozen first submissions, and authoritative receipts on the host. The product conclusion was a P0: a formal connector execution contract with advertised capabilities, structured validate/submit/status/receipt operations, idempotency and authoritative versioned receipts; SQL parsing and engine rules belong to the connector, and the Gateway handles registration, credentials, approval, routing and ledger attribution.

The thin-core rules constrain the shape: the Gateway never interprets a payload, never calls a model, holds no plaintext credential in its database, and the workspace holds no long-lived upstream credential. Nothing inside a workspace is hidden from its bots, so a connector credential placed in the container is a workspace-level secret.

## Definitions

- **Connector**: an operator-registered external service that executes submissions on a system of record (a database, a ticketing API, a report generator). Identified by a connector id, scoped to one workspace.
- **Submission**: a bot-authored body, opaque to the Gateway, with a content hash (sha256 of the canonical JSON).
- **Validation**: a connector's dry check of a submission, with no side effect, returning a validation id bound to the content hash, an `effect` class per operation, and a human-readable summary.
- **Receipt**: the connector's authoritative, versioned record of one submission's execution, stored by the Gateway.
- **Effect class**: `read` (no state change), `reversible` (a change the connector can undo or that has no external effect), `external` (anything else). Maps to risk tiers L0, L1, L2.

## Decision

1. **Every connector speaks one HTTP contract typed in `contracts`.** `POST /describe` returns the capabilities document (name, version, supported operations with their effect class, limits, the JSON schema of a submission, and a human-readable "what this connector does not support"). `POST /validate` takes a submission and returns `{validationId, contentHash, valid, effect, summary, errors[]}` where `errors` are field-specific and typed. `POST /submit` takes `{validationId, contentHash, idempotencyKey}` and returns a receipt. `GET /status/:receiptId` and `GET /receipt/:receiptId` read back. A connector that parses SQL, checks PostgreSQL rules or shapes result rows does so behind this contract; the Gateway forwards bodies and stores receipts without reading inside them.

2. **The Gateway is the only caller of a connector.** A connector's credential lives in the Gateway Secrets Store; the workspace never receives it and never receives the connector's endpoint. The sidecar reaches a connector through `/internal/runs/:id/connectors/:connector/*`, authenticated with the run token like the model proxy. That run token is the bot's service identity for the connector; it is issued per run and expires with it, which answers the open decision: no separate database identity is issued or rotated. This changes design §3.8's "MCP endpoint and short-lived token in the workspace" for connectors; the reasons are the credential rule and item 4.

3. **The bot-facing surface is five sidecar MCP tools.** `connector_describe(connector)`, `connector_validate(connector, submission)`, `connector_submit(connector, validationId, contentHash, idempotencyKey?)`, `connector_status(connector, receiptId)`, `connector_receipt(connector, receiptId)`. They are offered to a run only for connectors named in the bot's `connectors` list, which stays a prompt-level choice and not access control: any bot in the workspace may name any of the workspace's connectors. Results enter model context wrapped as untrusted external tool output; the ledger keeps the raw result.

4. **Receipts are authoritative and live in the Gateway.** Every `submit` produces a receipt row keyed by receipt id, carrying connector id, workspace id, run id, bot id, content hash, validation id, idempotency key, status (`accepted`, `running`, `succeeded`, `failed`, `rejected`), a result reference, the connector's receipt version and timestamps. Receipts are immutable while their owning workspace or bot exists; a status change is a new version. ADR-0026 permanent deletion is the sole exception: only its transaction-scoped, exact workspace-or-bot lifecycle guard may delete the receipt and versions. Ordinary `DELETE` remains rejected, and the guard disappears on commit or rollback. A workspace file that mirrors a receipt is a convenience the connector or a bot may write; it is never the truth, and a bot's claim about a submission is checked against the receipt, not the file.

5. **Submit is bound to a prior validation and is idempotent.** `submit` is refused unless the validation id exists, belongs to the same connector and content hash, and is younger than the validation TTL (900 seconds, a guess, calibrated on the first live campaign). A second `submit` with the same connector, content hash and idempotency key returns the existing receipt and executes nothing. A submission whose content differs from what was validated is refused with a typed error naming the hash mismatch. The connector sees a body exactly once per idempotency key.

6. **Risk tier follows the validated effect class, decided in the hook.** `describe`, `validate`, `status` and `receipt` are L0. `submit` is L0 when the validation's effect is `read`, L1 when `reversible`, L2 when `external`; the `PreToolUse` hook reads the effect from the Gateway's stored validation, never from the tool input. An L2 approval request carries the connector id, the content hash and the connector's summary from validation, never the submission body, matching ADR-0002's "proposed action, never page content". A stored Always rule may match on connector id and effect class.

7. **Every connector call is attributed in the ledger.** The `tool_call` and `tool_result` events of the five tools carry connector id, and for submit the validation id, content hash and receipt id, so coverage and collisions are computed from the ledger and receipts, not reconstructed from files. Attribution is by run and bot; it is a soft boundary like every bot boundary.

8. **Connector endpoints are outside the egress allowlist.** The workspace does not reach the connector; the Gateway does. An operator registering a connector supplies its URL and credential through the operator API; the URL is subject to the same non-public address rules as the managed egress proxy only if the operator marks it public. A connector on a private network is reachable because the Gateway, not the workspace, calls it; this is the one path a workspace has to a private service, and it exists only through a registered connector.

## Alternatives

- Keep connectors as MCP servers the sidecar attaches to directly (design §3.8 as written): rejected; the credential or its short-lived token enters the container, receipts have no authoritative home, and the ledger sees only opaque tool calls.
- Let the Gateway validate SQL or domain rules: rejected; that is the thin-core violation the campaigns warned against, and it couples every engine's rules to the control plane.
- Keep the file-based host adapter: rejected; it is what produced mutations, collisions and mirror drift. Its discipline (hash, dry preflight, frozen submissions, host receipts) is what item 4 and item 5 keep.
- Auto-approve `submit` for any connector an operator registered: rejected; registration says the service is real, not that a given submission is reversible.

## Consequences

- `packages/contracts` gains `connector.ts`; the Gateway gains a `connectors` module (registry, validations, receipts, proxy routes) and migrations; the sidecar gains `connector-tools.ts` and hook rules; `testkit` gains a fake connector. The operator UI gains a connector registration page later.
- A real database connector (the existing database MCP server, or an adapter in front of VendorDB and PostgreSQL) is a separate component that implements the HTTP contract; it is not part of the Gateway and not part of this ADR. The temporary host adapter from the campaigns is the reference for its behaviour.
- Bots lose the ability to "just copy a file into requests/"; the tools are the only path. That is intended: the model no longer carries shell-copy correctness.
- The validation TTL and the per-connector limits in the capabilities document are guesses until the first live campaign.
- Open: whether long-running submissions need a push notification to the run (today the bot polls `connector_status`), and whether a receipt should be able to wake a thread (would touch ADR-0005; not decided here).
