# ADR-0035: A bot publishes a running workspace service on its own origin, opened by signed-in members

Date: 2026-10-14
Status: Proposed (issue #123. The issue fixes the constraints: access by the signed-in person only, no inherited operator credentials or operator-API authority, only explicitly published ports, revocation, no cross-workspace or cross-tenant routing, the Files preview stays offline, a thin Gateway. Every concrete mechanism below, the roles in decision 3, the limits in decision 1, the configuration names and the choice not to audit opening an app are engineering proposals awaiting owner review.)

## Context

A bot can write an HTML/JavaScript application and run its backend inside the workspace container, but nobody outside the workspace can use it. The Files preview renders HTML in an opaque, script-less frame on purpose (ADR-0014 A3 decision 21). The workspace container has no published port: its network is internal (ADR-0006 decision 3), and Docker ignores port bindings on such a container (ADR-0006 amendment 1). The only inward path is the egress proxy's fixed relays for the screens, published on host loopback and consumed only by the Gateway's screen proxy (ADR-0022 amendment 1, C7). A `localhost` link from a bot points at the reader's own computer.

The owner asks for: a bot builds an app, starts it, posts a link, and the operator opens it in their own browser and uses frontend and backend together, without takeover or tunnelling (issue #123).

The hard part is the browser, not the network. The operator UI authenticates with a session cookie and a CSRF token on one origin (ADR-0006 amendment 4). Any page that runs on that origin, or that can read cookies scoped to it, holds the operator's authority. Application content is untrusted: a bot wrote it, possibly after reading prompt-injected pages.

## Decision

1. **A publication is an explicit Gateway record made by a bot tool.** `app_publish { port, label }` (L1: a Gateway-side record whose audience is the workspace's own signed-in members) writes an `app_shares` row: workspace, port, label, the publishing bot and run, `active` or `revoked`. It is offered only when the deployment configures app sharing (decision 2), and then every run's config carries `appShareVersion: 1`. The port is a TCP port in the workspace container, 1024 to 65535, never one of the screen relay ports 6080 to 6086. Publishing a port that already has an active publication returns that publication with its label updated; at most 10 publications are active per workspace. The tool answers with the application URL, which the bot posts in chat. A human cannot publish in this version.

2. **Every publication has its own origin, on a listener of its own.** `APP_SHARE_BASE_URL` (for example `http://apps.localhost:8790`) and `APP_SHARE_OPERATOR_URL` (the operator UI's public origin) turn the feature on; both or neither must be set. A publication's URL is `<scheme>://<label>.<base host>:<port>/`, where the label is the publication's 32-character random hex id. The Gateway serves these on a third listener, `APP_SHARE_PORT` (default 8790) on `APP_SHARE_BIND` (default `127.0.0.1`), which serves nothing else: a request whose `Host` is not exactly a known label under the base host is 404 (this also defeats DNS rebinding). The base host must be a DNS name, must not equal the operator host, and must not be a parent of it; the Gateway refuses to start otherwise.

   Why not a path: under `/apps/<id>/` on the operator origin, application script is same-origin with `/api` and can read the CSRF token; under one shared application origin, one workspace's app can read another's responses with the person's grant. Why not only a different port: cookies are scoped by host, not port, so a port-separated app shares the operator cookie jar. A separate host per publication gives each app its own origin, storage and cookie jar. On `*.localhost`, browsers resolve every label to loopback, so local and SSH-tunnelled deployments need no DNS; a LAN or public deployment needs a wildcard DNS name, ideally on a registrable domain other than the operator's, and HTTPS in front.

3. **Only a signed-in person with a Member role or higher in the publication's workspace opens it.** Guests, the operator token and service principals cannot: the app runs in a browser and its backend acts in the workspace. Entry is a handshake: the UI page `#/apps/<share id>?ws=<workspace id>` calls `POST /api/workspaces/:id/app-shares/:shareId/open`, which issues a one-use ticket valid 30 seconds, bound to the publication, the person's session and tenant; the page submits it in a form `POST` to `<app origin>/__deskmates/enter`, never in a URL (ADR-0006 amendment 4 decision 10). The app listener accepts the ticket only with `Origin` equal to `APP_SHARE_OPERATOR_URL`, sets a host-only `deskmates-app` cookie (`__Host-deskmates-app` on HTTPS; HttpOnly, SameSite=Lax, Path=/) naming an in-memory grant of 12 hours, and redirects to the requested path. Every later request rechecks the grant, the publication's state, that the session is still signed in and in the tenant, and the person's role in the workspace. A request without a valid grant gets a page linking to the entry page on the operator UI. Grants live in Gateway memory: a Gateway restart signs every app out, and the person reopens it from Deskmates.

4. **The Gateway reaches the port through the egress proxy's app relay; the workspace publishes nothing.** The proxy container gains one fixed relay on container port 6090, published on host loopback with an ephemeral host port like the screen relays (ADR-0006 decision 6). A connection must first send `DESKMATES-APP/1 <key> <port>\n`; the key is 32 random hex characters the provider generates for each proxy container and keeps in the proxy's environment, which bots cannot read; the target host is the fixed workspace container name, never taken from the request. The relay answers `OK\n` and pipes bytes, or `ERR <reason>\n` and closes: on a wrong key, a port outside 1024 to 65535 or in 6080 to 6086, or a refused connection. The Gateway connects only for an active publication's port, so the published list is enforced by the Gateway from its database and the infrastructure ports are refused twice. CDP (9222) and VNC (5900 and up) listen on the container's loopback and cannot be reached over the workspace network at all. The application must listen on `0.0.0.0`; a loopback-only service reports as not running. No per-app host port mapping is ever created.

5. **The forwarded request carries no Deskmates credential, and the response cannot plant one.** The Gateway removes every `deskmates-*` and `__Host-deskmates-*` cookie from the forwarded `Cookie` header and drops hop-by-hop headers; the operator's session cookie never reaches the app host in the first place (decision 2). From the response it drops any `Set-Cookie` naming a Deskmates cookie and strips the `Domain` attribute from the rest, so an app's cookies stay host-only. An unsafe method (anything but `GET`, `HEAD`, `OPTIONS`) and every WebSocket upgrade must carry `Origin` equal to the publication's own origin when `Origin` is present; anything else is 403. The Gateway adds no CSP of its own to app content: the app is isolated by origin, and the operator UI never frames it (the UI opens it in a new tab with `noopener`). `Cache-Control` and the app's own headers pass through.

6. **WebSocket and server-sent events are supported.** An upgrade passes the same grant and Origin checks, then the Gateway writes the request to the relay and pipes bytes both ways. Responses stream without buffering, so SSE works. Long-lived connections close when the publication is revoked, the session is signed out, or the workspace is archived.

7. **The process belongs to the workspace, not to the run or the Gateway.** The bot starts the service detached (`setsid`/`nohup ... &`) so it outlives the run's process; the Gateway never starts, restarts or supervises it. The publication survives the run, a Gateway restart and an upgrade. A stopped service, a stopped or restarted container, or a proxy from before this image is reported honestly: the list probes each active publication through the relay (`available` / `unavailable`) and a request answers 502 with a page saying the app is not running. After a container restart a bot must start the service again; the same URL then works. A recreated proxy has a new key, read on attach like the screen addresses.

8. **Revocation is immediate and audited.** `DELETE /api/workspaces/:id/app-shares/:shareId` (Admin or Owner) marks the row `revoked`, drops its grants and closes its open connections in the same request; afterwards the URL is 404. Publishing (`app_share.publish`, actor the bot, with the run) and revoking (`app_share.revoke`, actor the person) are audit records written in the same transaction (ADR-0031 decision 11). Opening an app is access, not configuration, and is not audited. Archiving or purging the workspace ends access the same way; rows are deleted with the workspace.

9. **Routing never crosses a workspace or tenant.** A label resolves to exactly one row; the grant names that row; the role check is in that row's workspace; the operator routes are nested under the workspace (`/api/workspaces/:id/app-shares...`), pass the route guard for that workspace (another tenant's workspace is its uniform 404), and answer a publication of another workspace exactly like a missing one (404). The relay address and key come from that workspace's sandbox handle only.

10. **Unchanged.** The Files HTML preview stays opaque and offline (ADR-0014 A3 decision 21). Egress rules are untouched (ADR-0009, ADR-0020, ADR-0027): the relay carries only inbound connections to the workspace container, and the app's own outbound calls still pass the proxy's policy. The Gateway proxies bytes and never calls a model.

## Alternatives considered

- **Publish the port on the workspace container, or one host port per app.** Docker ignores bindings on an internal-only container, and a non-internal network would undo ADR-0006 decision 3. A host port per app is also a new loopback surface per app.
- **Serve the app under a path of the operator origin.** Rejected: same-origin script has the operator's authority (decision 2).
- **One shared app origin with a path per publication.** Rejected: apps of different workspaces would share an origin and the person's grant.
- **A ticket in the URL.** Rejected by ADR-0006 amendment 4 decision 10; the form POST keeps it out of history, logs and referrers.
- **An allowed-port file in the proxy, reloaded like the egress policy.** Not needed: the relay key means only the Gateway can use the relay, and the Gateway reads the published ports from its database. A policy reload closes every proxy connection, which would also cut app sessions.
- **Anonymous or external sharing.** Out of scope; a separate product decision.

## Consequences

- One more listener and two more settings when the feature is on; with them unset nothing changes, including the tool list.
- The egress proxy image gains `app-relay.mjs` and port 6090; workspaces whose proxy predates it report their publications as unavailable until the proxy is recreated.
- A plain-HTTP deployment on one parent domain gives each app its own origin, but an app can still set a cookie for the parent domain that a sibling app receives. Deskmates's own cookies are protected by name filtering and, on HTTPS, the `__Host-` prefix; app-to-app cookie integrity on plain HTTP is best effort.
- A Member can open an app a bot published from another person's private chat in the same workspace: a workspace is one trust domain (ADR-0004), and publications are workspace records.
