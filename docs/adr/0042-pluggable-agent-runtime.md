# ADR-0042: A second agent runtime (OpenAI Agents SDK), selected per bot, behind the same hook

Status: Proposed (engineering choices awaiting owner review). Decision 1 records the owner's request of 2026-10-16: a switchable Claude Agent SDK / OpenAI SDK runtime so the two can be compared. Everything else is how that request fits the existing rules.

## Context

The sidecar is the Claude Agent SDK host process (ADR-0002 decision 1): `query()` runs the loop, a `PreToolUse` hook plus `canUseTool` intercept every tool call, and the Gateway's model proxy forwards only the Anthropic Messages protocol (`/v1/messages`). Every bot, model job and summary runs through that one runtime.

The owner wants to compare it with an OpenAI-based runtime on the same product: same bots, same tools, same approvals, same ledger, so that `evals/compare.ts` can pair runs that differ in the runtime knob only. The agent-loop portability spike of 2026-09-22 (`docs/design/agent-loop-portability-spike-2026-09-22.md`) showed with a deterministic provider that the OpenAI Agents SDK can park for approval, exit its process and resume the pending tool action in another process, and ended with: "Proceeding to a production adapter requires an ADR changing the current SDK-specific boundary." This is that ADR.

Two OpenAI runtimes were considered. The **Codex SDK** (`@openai/codex-sdk`) is the closer analogue of the Claude Agent SDK: a CLI subprocess with built-in shell and file tools, persisted threads and auto-compaction. But it exposes no per-tool interception point: policy is a sandbox mode and an approval policy, and MCP servers come from its config file. The `PreToolUse` gate (egress, browser lock, risk tiers, the short wait, `defer`) could not be applied to its built-in tools, which breaks ADR-0002 decision 2 and ADR-0020. The **OpenAI Agents SDK** (`@openai/agents`, TypeScript) has no built-in file or shell tools, but every tool is a function the sidecar defines, so the existing hook can judge every call; it has `needsApproval`, a serialisable `RunState` with `approve`/`reject`, MCP servers, sessions, `maxTurns`, and a `ModelProvider` that takes a base URL and key. The portability spike used it. It is the runtime chosen here.

What the OpenAI Agents SDK does not have, and the sidecar therefore provides itself: the file and shell tools (`Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`, `LS`), compaction, the `Skill` tool and subagents, a fallback model, and the per-turn usage stream.

The sidecar's existing structure makes the switch small. Every SDK runtime function is injected through `SidecarDeps` (`deps.ts`); the hook is an ordinary async function that takes `{tool_name, tool_input, tool_use_id}` and returns allow, deny or defer; the in-process `deskmates` tools are an MCP server instance; the browser is a stdio MCP server; and the run loop consumes a stream of SDK-shaped messages (`assistant`, `user`, `result`, `system/init`). A second runtime that yields the same message shapes and calls the same hook leaves the ledger, approvals, taint tracking, screenshots and handoffs untouched.

## Decision

1. **The runtime is configuration, frozen per run.** `AgentRuntime` is `"claude-agent-sdk"` (the default and today's behaviour) or `"openai-agents"`. A bot carries an optional `runtime`; `DEFAULT_RUNTIME` in `.env` sets the installation default. The Gateway resolves `run.config.runtime` (recorded) → `bot.runtime` → `DEFAULT_RUNTIME` at run start, writes it into `runs.config_json` beside the frozen models, and keeps it on resume, exactly like the models (ADR-0023 decision 1). `StartRunRequest.runtime` carries it to the sidecar. A run row therefore attributes its runtime without reading the bot, which is what a paired comparison needs. (Owner request, 2026-10-16.)

2. **One gate for both runtimes.** The sidecar's `PreToolUse` hook stays the single interception point (ADR-0002 decision 2). The OpenAI runtime calls that same function before every tool call, with the Agents SDK call id as the tool-use id, and maps its answer: `allow` runs the tool; `deny` returns the reason to the model as the tool's result; `defer` pauses the run through the SDK's `needsApproval` interruption, serialises the `RunState` into the bot's home directory and ends the run as `deferred` with the approval and tool-use ids, as the hook already records. The egress allowlist, network grants, browser lock, bot-directory guard, risk tiers, connector and integration tiering, the short wait and the approval ledger events are the hook's and need no second implementation. `canUseTool` has no equivalent and none is needed: a function tool the sidecar defines cannot run without passing its own `execute`.

3. **Resume consumes the human's decision through the hook, like a replay.** A parked OpenAI run resumes in a new process from the serialised `RunState`. For each pending interruption the runtime calls the hook again with the same tool-use id; the hook's existing `pendingDecision` logic (ADR-0002 amendment 1) turns the `approval` trigger into allow or deny, and the runtime applies `state.approve` or `state.reject` with the reason and runs on. A decision given for another call is discarded by the hook as today. The retry-after-failed-replay rule (amendment 2) applies unchanged because it lives in the hook.

4. **Tools are the same tools, under the same names.** The in-process `deskmates` MCP server and the browser `mcp-proxy` stdio server are attached to the OpenAI runtime through MCP clients; each listed tool becomes a function tool named `mcp__<server>__<tool>`, as the Claude SDK names them, so the tier tables (`risk-tier.ts`), `tool-action.ts` and the SOUL guidance apply verbatim. The sidecar implements `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`, `LS` and `Skill` as function tools with the Claude SDK's parameter names (`file_path`, `content`, `old_string`, `new_string`, `command`, `pattern`, `path`, `skill`), so the same tier rows, the directory guard, the image-withholding rule, the `skill_used` measurement and the handoff's written-file list hold. The proxy's untrusted wrapping of page text is unchanged because the same `mcp-proxy` process produces it; its images reach the model by decision 9. Not offered on this runtime: `Agent`/`Task`, `ListAgents`, `SendMessage`, `TodoWrite`, `MultiEdit`, `NotebookEdit`.

5. **The model proxy speaks both protocols, routed by upstream.** ADR-0039's `MODEL_UPSTREAMS` gains `protocol: "openai"`: an upstream that serves the OpenAI Chat Completions API. The proxy accepts `POST /v1/chat/completions` and forwards it only to a model whose upstream is `openai`, and `/v1/messages` only to an `anthropic` one; a mismatch is `503 model_upstream_missing` with the protocol named, never a translation. The frozen-model check, the run token swap, budget admission, timing and the `model_requests` row are the same; usage is read from the OpenAI shape (`prompt_tokens`, `completion_tokens`, `prompt_tokens_details.cached_tokens`, and the final streamed chunk's `usage`), and `image_url` parts count as image blocks. The sidecar reaches it with `OPENAI_BASE_URL = <model proxy>/v1` and the per-run token as the API key, inside the sidecar process: the OpenAI runtime starts no subprocess, so ADR-0002 decision 4's environment allowlist is not involved.

6. **Sessions are per runtime.** The OpenAI runtime keeps its own transcript as a file session in the bot's home directory (`~/.deskmates/openai-sessions/<id>.json`) and returns its id as `sdkSessionId`; `bot_sessions` records which runtime a session belongs to, and a bot started on the other runtime begins a new session instead of resuming a transcript it cannot read. Usage is reported cumulatively per session, so the Gateway's per-session delta accounting (`ledger/usage.ts`) prices the OpenAI runtime the same way. There is no compaction on this runtime in this version: a long thread ends on `maxTurns` or the model's context, and the run row says which.

7. **Model jobs and summaries run on the bot's runtime.** Vision probes, approval reviews, memory jobs, status inquiries and presentation summaries are one tool-free turn; on the OpenAI runtime that turn is one Chat Completions request through the same proxy (`runtime/openai/model-job.ts`), composed into the same `RunEnded`. A bot on the OpenAI runtime therefore needs both its model and its cheap model on `openai` upstreams; the Gateway refuses to save a bot whose runtime and either effective model do not match the registry's protocol.

9. **The model stream, images and compaction are carried, not dropped.** The Agents SDK's raw stream becomes the Claude SDK's `stream_event`s, so the reply preview (ADR-0037) and the per-turn `turn_usage` events work unchanged. A tool's image reaches the model as a user message right after that call's result (Chat Completions tool messages are text only); it lives in the process, not in the session file. The `Skill` tool is a function tool over the run's materialised skill set. Compaction (`summary-v1`) is off unless `DESKMATES_OPENAI_MAX_CONTEXT_TOKENS` is set: when the last response's prompt was over it, the items older than a six-item tail are summarised by the same model in one extra call and replaced by one user message; the history is archived beside the session file and the run ledgers a `compact_boundary`. The knob is recorded on the run row like the Claude path's. Turning it on is a strategy change (decision 8).

8. **The runtime is a strategy knob, not a better loop.** Switching a bot to `openai-agents` is a strategy change in the sense of AGENTS.md: it is measured with `evals/compare.ts` on a paired run, one knob, per duration bucket, before anyone calls one runtime better. The recorded `runtime` in `config_json` is what pairs the runs.

## Alternatives considered

- **Codex SDK as the second runtime.** Rejected above: no per-tool gate, so the risk tiers and approvals could not be enforced on its built-in tools.
- **A raw OpenAI client with a hand-written loop.** Would reimplement what the Agents SDK already gives (tool loop, interruptions, serialisable state, MCP, sessions) and the spike had already verified the SDK's park/resume behaviour.
- **Translate Anthropic requests to OpenAI in the proxy** so the Claude SDK could drive an OpenAI model. A protocol translation inside the control plane, with lossy tool and image semantics, and it would not give an OpenAI *runtime* to compare against.
- **Select the runtime per workspace.** A bot is where the model is chosen (ADR-0023); the comparison the owner wants is two bots side by side, so the bot is the unit here too.

## Consequences

- `packages/contracts` gains `agent-runtime.ts` (`AGENT_RUNTIMES`, `AgentRuntime`, `isAgentRuntime`); `BotDefinition.runtime`, `StartRunRequest.runtime`.
- `packages/gateway`: `config/runtime.ts` (`DEFAULT_RUNTIME`), `bots.runtime` and `bot_sessions.runtime` columns, the bot routes accept `runtime`, `run-lifecycle` freezes it, `model-upstreams` admits `protocol: "openai"`, the model proxy forwards `/v1/chat/completions` by protocol and reads OpenAI usage.
- `packages/sidecar` depends on `@openai/agents` and `@modelcontextprotocol/sdk` as well as the Claude Agent SDK; it remains the only package that imports an agent SDK (ADR-0002 decision 1 is read as "the sidecar hosts the agent runtimes"). `runtime/openai/` holds the runtime, the file and shell tools, the file session and the Claude-shaped message adapter; `real-deps.ts` wires it.
- `packages/testkit` gains a scripted OpenAI Chat Completions server for T1 tests.
- `images/workspace` preinstalls the two packages.
- Known gaps in this version, to be closed by later decisions: no subagents (`Agent`/`Task`, which need a hook per subagent carrying `agent_id`, ADR-0002 amendment 3 A5) and no fallback model on the OpenAI runtime; images are not persisted in the session; compaction is a fixed-tail summary, not the Claude SDK's.
