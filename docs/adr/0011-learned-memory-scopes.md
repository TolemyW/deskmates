# ADR-0011: Bots maintain what they learn; humans own the rules

Date: 2026-09-29
Status: Accepted (product owner, 2026-09-29, by ordering Phase 4 to be built and tested from the UI; supersedes the per-item human review of learned memory in design v0.3 §3.1 and §3.6 and in the M2 B5 flow)
Source: `docs/design/m3-context-and-memory-plan-2026-09-29.md` Part B and `docs/design/m3-context-memory-research-2026-09-29.md` §3 and §5. Builds on ADR-0004 (the workspace is the trust boundary) and ADR-0002 (the sidecar wraps untrusted input).

## Context

Today a bot's memory is `MEMORY.md`, the diary and the global knowledge base. Design §3.1 says the agent may append to `MEMORY.md`; the M2 B5 flow made that stricter: the run summary's `memorySuggestions` land in `memory_suggestions` as `pending`, and a human applies each one. Knowledge proposals wait for a human the same way. So every learned item costs a click, the review queue grows with use, and what a bot learns about the workspace (a field length limit, an engine difference) is filed under that bot only. The knowledge base is global while ADR-0004 makes the workspace the trust boundary.

The two VendorDB campaigns (`m3-vendordb-longrun-2026-09-28.md`, `m3-vendordb-workflow-v2-2026-09-29.md`) produced dozens of suggestions per campaign, most of them task state that should never have become permanent rules, and a few workspace facts every bot in the group needed.

The research survey graded the field's evidence: humans own rules, agents own notes (OpenAI, Anthropic, OpenClaw, Manus, Codex all do this); memory-injection attacks (MINJA, MemGhost, PMPA) go through the agent's authorized write path, so a rule that relies on the writing model's judgment of "is this an instruction" fails; masking and provenance work, LLM self-policing does not.

## Definitions

- **Scope**: one of `task` (a thread or campaign), `workspace`, `bot`, `rule`. A `rule` is SOUL, an approval rule, a risk tier, an egress entry or any sentence the human gave as a standing instruction.
- **Source kind**: `human`, `bot_self`, `other_bot`, `tool`, `page`, `webhook`.
- **Trust**: `trusted` or `untrusted`. Set by the sidecar from the run's taint, never by the model.
- **Taint**: a run becomes tainted the moment untrusted content enters its model context (a browser tool result, a webhook body, a message authored by another bot, a knowledge or memory entry that is itself untrusted). Every learned item the run writes after that moment is `untrusted`. Items written before it, or derived only from human messages, are `trusted`.
- **Authority**: `fact`, `preference`, `procedure`. Never `instruction`.
- **Imperative**: an item phrased as a standing instruction ("always", "never", "from now on", "ignore", "do not ask") or whose subject is a duty, an approval rule, a risk tier, an egress entry or a human rule. Detected by a deterministic classifier in the Gateway, not by the model.
- **Version set**: the exact set of memory entry versions injected into a run, recorded in `runs.config_json`.

## Decision

1. **Four scopes, four stores, one owner each.** Task state lives on the thread or campaign and is written automatically during the run. Workspace facts live in a workspace memory shared by every bot in that workspace and are written automatically. Bot experience lives in that bot's experience memory and is written only by background consolidation. Rules are written only by a human. No learned write of any scope can create, change or delete a rule.

2. **The agent writes memory by default; the human supervises quality.** A run's summary reports learned items with a proposed scope; the Gateway classifies, deduplicates and stores them without a human decision. The human views, edits, forgets and undoes. The one human gate is item 4.

3. **Provenance and trust are set by the sidecar.** Every entry records source run, source kind, trust, authority, and what it was derived from. Trust comes from the run's taint as defined above; the summary cannot raise it. Consolidation keeps the minimum trust of its sources and never merges across trust levels.

4. **The only human gate is "needs your confirmation".** An item goes there, and takes no effect until decided, exactly when it is an imperative, or it contradicts a rule or an existing trusted entry, or it would change a duty, an approval rule, a risk tier or egress. Everything else is applied on arrival. The existing `memory_suggestions` table becomes this queue.

5. **Untrusted memory is data, never prompt.** Untrusted entries are stored and returned by `memory_search`, wrapped the way browser output is wrapped, but never pinned into the first user turn and never promoted into bot experience or rules. A human may confirm an untrusted entry from the UI, which sets `trusted` with the human as source; this is optional supervision, not per-item review.

6. **Workspace facts carry validity intervals and are superseded, never overwritten.** Fields: `observed_at`, `valid_from`, `invalid_at`, `superseded_by`, `last_confirmed_at`, optional TTL. A contradiction closes the old interval and opens a new entry. Retrieval shows age and source.

7. **Every write is an immutable version.** Edits and consolidation produce new version rows; forget is a tombstone plus redaction of the body; undo restores a previous version. Raw candidates are kept beside merged results.

8. **Hot path and background are split.** During a run the sidecar writes task state, the diary, candidate notes and a pre-compaction flush through the SDK `PreCompact` hook. Consolidation into bot experience runs as a background-lane bot run, one per workspace at a time; the Gateway still never calls a model. Its result is applied automatically only when every source is trusted, otherwise it goes to the gate of item 4.

9. **Context gets a pinned index plus search.** Each run receives, in its first user turn, a budgeted index: the workspace memory summary and the bot's own experience. The rest is reached through a `memory_search` tool. The index budget is 200 lines total, split 120 workspace and 80 bot (a guess, calibrated in Phase 5 of the plan). The system prompt carries none of it, so it stays byte-identical across runs.

10. **Workspace memory never crosses a workspace.** Entries are keyed by `workspace_id`; `memory_search` and the pinned index of a run in workspace A never return an entry of workspace B. Promotion to the global knowledge base is a human action carrying provenance. Inside a workspace every bot reads the workspace memory; there is no access control between bots, only attribution ("learned by X from run Y").

11. **Task state ends as an episode.** When a thread or campaign closes, its task state is distilled into a searchable episode summary and is not injected into unrelated runs. Episodes are the input of consolidation.

12. **Replayable.** The version set injected into a run and the memory budgets in force are recorded in `runs.config_json`; trajectory replay restores that snapshot.

## What this supersedes

- Design §3.1: "MEMORY.md: the agent may append, humans may edit or delete" becomes: the agent's own file is replaced by the bot experience store and the pinned index; humans edit through the "Learned memory" page. `MEMORY.md` stays readable in the workspace as an export of the bot's trusted experience so existing SOUL text that mentions it keeps working.
- Design §3.6: "writes need human review" for the knowledge base stays for the global base; workspace memory is a new store below it with automatic writes.
- M2 B5: per-item review of `memorySuggestions`. The queue survives only as the confirmation gate of item 4.

## Alternatives

- Keep per-item human review: rejected; the queue grows with use and the vendordb campaigns show most items are task state that a human should never see.
- Let the writing model judge whether a page-derived note is safe to pin: rejected; MINJA, MemGhost and authority-collapse results all go through exactly that path.
- Access control between bots on workspace memory: rejected by design rule (ADR-0004); the workspace is the boundary.
- One flat store with tags instead of scopes: rejected; the scope decides the writer, the lifetime and the budget, and those differ.

## Amendment 1 (2026-09-29): when bots learn, what they never learn, and rules they cannot reach

### What was found

- Consolidation has no trigger. The implementation starts it only from the operator route (`packages/gateway/src/api/learned-memory-routes.ts`), so bot experience grows only when a human remembers to press a button. Decision 8 says where consolidation runs, not when.
- Decision 1 is not enforced for files. Every process in a workspace runs as root, and a shell write under `/home` is L1 (only the `Write`/`Edit` tools rate a path outside `/work` as L2, `sidecar/src/risk-tier.ts`). A bot can therefore change its own or another bot's `SOUL.md` with `echo >>`, and the sidecar reads that file when it assembles the next run's context.
- Survey of how OpenClaw and Hermes Agent decide to learn (`m3-context-memory-research-2026-09-29.md`, read at their 2026-09-29 main branches): both trigger learning by deterministic counters and let the model decide only the content; both learned the hard way that transient failures turn into lasting false beliefs ("negative claims about tools harden into refusals the agent cites against itself for months", Hermes); Hermes stores memory as declarative facts because "imperative phrasing gets re-read as a directive"; OpenClaw's provenance gate once dropped a whole memory file from bootstrap without saying so (issue #153426), and its memory was repeatedly truncated in silence.

### Decisions

A1. **Consolidation is triggered by Gateway counters, never by the model.** For each bot, the Gateway enqueues one consolidation run when all of these hold: at least 3 new closed-task episodes or 10 new experience candidates for that bot since its last consolidation; its workspace has had no running interactive run for 10 minutes; and the bot has not been consolidated in the last 24 hours. Runs that feed the counter are terminal `succeeded` or `silent` runs of any trigger kind except consolidation runs themselves; a resumed attempt of the same run counts once. The operator route stays as a manual trigger. The three numbers are guesses, recorded in the consolidation run's `runs.config_json` and calibrated like the index budget of decision 9.

A2. **Some things are never learned.** A learned item is discarded, with a `memory_skipped` ledger event naming the reason, when it is derived from any of: an egress block; a browser-lock wait or human takeover; an approval that was deferred, denied or timed out; a model-proxy, transport or sandbox error; a run that ended `failed`; or when it states that a tool, site or service does not work, is unreachable or is unsupported, unless a human said so. Session-local state (logged in or not, which page is open, which tab) is not learned either. The sidecar knows the first five from its own events and marks the items it derives after them; the negative-claim and session-state checks are a deterministic classifier in `contracts`, next to the imperative classifier. The summary instruction asks the model not to propose such items; the Gateway filter is the guarantee, and what it misses is measured, not assumed away.

A3. **Learned memory is stored and shown as dated declarative facts.** An entry reads as an observation with its subject, date and source ("2026-09-29, run X: VendorDB returned OK for a duplicate-key INSERT that PostgreSQL rejects"), not as an instruction. The pinned index renders entries under "Observed facts" with age and source, never as a bulleted list of things to do. The summary instruction asks for this form; an item that still arrives as an imperative goes to the gate of decision 4, unchanged.

A4. **Nothing is left out silently.** Every run's ledger gets one `memory_index` event: entries considered, pinned, left out because untrusted, left out because of the budget, and the budget itself. When the index exceeds its budget, whole entries are left out by rank and counted; no entry is cut in the middle. The run view and the "Learned memory" page show these counts ("4 untrusted workspace facts not pinned; reachable through memory_search").

A5. **Rule files are written from the Gateway's copy before every run.** The Gateway keeps the canonical body of each bot's `SOUL.md` (versioned, as `soul_version` already counts) and the `MEMORY.md` export. The sidecar writes both from the `StartRunRequest` before it assembles context, hashes them again when the run ends, and reports a difference as a `rule_file_modified` event with a redacted diff, shown in the UI. The modified file never reaches a later run, because the next run writes the canonical copy first. This makes decision 1 hold for files a shell can reach; it is not a security boundary inside the modifying run, which has already sent its system prompt.

### Consequences of the amendment

- The scheduler gains a consolidation trigger (a periodic check of the three counters per bot); the manual route is unchanged.
- The sidecar's taint tracking gains the A2 event marks; `contracts` gains the do-not-learn classifier with its own T0 table.
- The summary instruction and the pinned-index rendering change: this is a strategy change and goes through the paired comparison of the plan, not only replay.
- The Gateway starts storing SOUL bodies, not only their version; the operator SOUL route writes the Gateway copy first. `StartRunRequest` gains the two canonical bodies.

## Amendment 2 (2026-10-13): newer facts replace older ones silently

Source: issue #85 and its owner comment "Confirmed memory recency policy: silent automatic supersession" (2026-10-13), which overrides the conflict-review part of the issue body. Status: the policy (silent supersession, one current value per fact, history kept, undo through versions) is the owner's decision. The ordering formula in A9 is the engineering proposal the owner asked to see; it has not been separately approved.

### What was found

- Decision 4 sent every learned item that contradicts a trusted entry to "needs your confirmation". The owner rejected that queue for ordinary facts: a newer value of the same fact should simply become current, without a prompt, a pending badge or a confirmation.
- Contradiction was a word-overlap heuristic (`contradicts`, Jaccard at least 0.6 plus a polarity or number difference). It had no notion of "the same fact", so it could not keep one current value per fact, and it treated `PostgreSQL 15` and `PostgreSQL 16` as one subject.
- Order was ingestion order. A summary that arrived late (a long run, a redelivery) replaced a newer observation merely because it arrived last.
- A duplicate refreshed `last_confirmed_at`, so a copy extended an entry's TTL like a confirmation, and the extra source was not recorded.
- The pinned index recorded its version set, but `memory_search` hits a run received were not recorded anywhere.
- The Observations and Learned memory screens asked for 100 gated items and ignored `nextCursor`; search returned at most 20 entries with no sign that more matched. Item 101 and match 21 were dropped silently (#113 inventory).

### Decisions

A6. **An ordinary fact conflict is not a gate.** Decision 4 loses "contradicts an existing trusted entry". An item still goes to "needs your confirmation" when it is an imperative, a duty change, contradicts a rule, or (decision 8) is a consolidation result with an untrusted source. Everything else applies on arrival, including a new value for a fact that has a trusted current value. The `contradicts_trusted` reason stays readable on rows gated before this amendment; those rows are not resolved, approved or deleted automatically.

A7. **The fact key.** Two notes state the same fact when they are in the same store (workspace, scope, and the bot for `bot` scope or the thread for `task` scope) and have the same fact key. The key is a deterministic function in `contracts` of the body: the set of content words (stemmed, stopwords and negations removed). A number written right after a capitalised name or a condition word (`version`, `v`, `release`, `build`, `rev`, `api`, `since`, `before`, `after`, `until`) is a condition and is part of the key, so `PostgreSQL 15` and `PostgreSQL 16` are different facts. Dates and times written in ISO form are dropped. The other numbers and the polarity are the fact's value. A body with no content word has no key and is never superseded. Candidates and episodes have no key. This is a heuristic: a false key match closes an unrelated fact and a missed one leaves two current values, and both are measured (A14), not assumed away.

A8. **One current value per fact key, written atomically.** A note is current when it is not forgotten, its interval is open and it is not distilled into an episode. A partial unique index allows one current note per (store, fact key). The decision (find the current value, order, insert, close the loser, record the receipt) runs in one SQLite transaction. A learned write is idempotent per (source run, item ordinal): a redelivered summary returns the earlier outcome and changes nothing.

A9. **Recency order (engineering proposal).** Each note has an effective time and its basis:
   - `source`: the time the sidecar stamped on the item (the wall-clock time of the turn it names), accepted only within the source run's lifetime, from the run's creation to the moment the Gateway receives it; a value outside that window is clamped to the window's edge.
   - `run`: the source run's creation time, when the item has no stamp (an older sidecar).
   - `human`: the time of a human decision (confirming a gated item, editing an entry).
   - `ingest`: the time the Gateway stored it, when there is nothing better.
   Text the model wrote, such as "as of 2027-01-01", is never used as a clock. The newer note wins by (effective time, ingestion time, entry id), compared in that order. The reason is recorded: `newer_effective_time`, `tie_later_ingestion` or `tie_entry_id`. A note older than the current value is stored already closed, pointing at the current value, with reason `older_arrival`: importing or redelivering an old observation never rolls the fact back. No case asks a human.

A10. **Equivalent duplicates consolidate, and copies are not corroboration.** A new item with the same key and the same value as the current note, at the same trust, adds a source row (run, ordinal, source kind, trust, effective time) to that note instead of a new entry. The note's effective time becomes the latest source time, so a later independent observation keeps the value current against a late older arrival. A copy never changes trust, authority, `last_confirmed_at` or TTL, and nothing counts sources as evidence. Duplicates never merge across trust levels: the same value at higher trust becomes a new current note (`equivalent_higher_trust`); at lower trust it is kept as closed history (`equivalent_lower_trust`).

A11. **Recency is not authority.** A newer untrusted value becomes current and stays untrusted: never pinned, returned by `memory_search` wrapped as untrusted, never promoted (decision 5). The trusted value it replaced leaves the index and the search results and remains in history. A learned write still cannot write a rule, change SOUL, an approval rule, a risk tier or egress (decision 1); the do-not-learn filter (A2) and the rule-contradiction gate run before ordering. Recency never makes a remembered instruction executable.

A12. **History and undo.** Superseding a note appends a `supersede` version to it (body unchanged), sets `invalid_at` and `superseded_by`, and writes a supersession receipt (closed entry, current entry, fact key, reason, both effective times, who decided). Raw sources stay attached to the entry that received them. Undo on a note whose latest version is `supersede` restores it: it becomes current again and the note then current for that key is closed with reason `undo_restore`. Forgetting the current note does not bring back an older one.

A13. **The run's memory is recorded exactly.** Every (entry, version) supplied to a run, through the pinned index or a `memory_search` result, is recorded with how it was supplied. The pinned set stays in `runs.config_json` for replay (decision 12). Supersession changes entry rows and appends versions; it never edits a recorded version or a run's record, so a running or replayed run keeps the snapshot it was given. Search and the pinned index return current notes only.

A14. **Predeclared paired evaluation; not run.** Silent supersession is a strategy change. Before it is called better it gets a paired comparison under `docs/design/measurement-2026-09-20.md`: the amendment-1 behaviour (baseline) against this amendment (treatment), one knob, a memory-off arm, per duration bucket, on `deskbench-memory-v1` plus a recency fixture set (value updates, late older arrivals, equal and missing times, future-dated model claims, untrusted overwrites of trusted facts, near-identical facts with different conditions). Metrics: current-value recall (G-RECALL), stale-use rate (an answer or action relying on a superseded value, G-STALE), poison success including removal of a trusted fact by an untrusted value (G-POISON), false-supersession and missed-supersession rates, and automatic replacements per session. Decision rule, fixed now: the treatment is kept when stale use falls and neither recall nor poison success is worse by more than the paired interval; any poison success on the fixtures is reported with its rule-of-three bound and goes to the owner. This amendment does not authorise a paid memory campaign, and no run of this evaluation is claimed.

A15. **Nothing is dropped from an operator list silently.** "Needs your confirmation" and learned-memory search page with the existing cursor contract and show "Load more" while a next page exists; a count shown for a partly loaded list says it is partial.

### Consequences of the amendment

- `memory_entries` gains `fact_key`, `effective_at` and `effective_basis`; new tables `memory_entry_sources`, `memory_supersessions` and `run_memory_versions`. Existing notes get their key and effective time on first use; two current notes of one key found then are ordered by A9 with reason `backfill`.
- `LearnedItem` gains a sidecar-only `observedAt`; the sidecar stamps each item with the time of the turn it names.
- New poisoning surface: a page can now remove a trusted fact from the pinned index by stating a newer contradicting value of the same key. The value it inserts is untrusted and unpinned, so the bot loses the fact rather than gains the attacker's, and it can find both through search and history. The owner accepted replacement without confirmation; this cost is what A14 measures as poison and stale-use, and it is the first candidate for a follow-up decision if the evaluation shows harm.
- The operator UI shows no conflict prompt. Superseded notes are visible with history shown, with their sources, receipt and a restore (undo).

## Amendment 3 (2026-10-14): categories, review groups, batch dispositions and topics

Source: issue #85 body (phase 1), its owner comments of 2026-10-13 ("Entry-centered memory UX clarification" and "Confirmed memory recency policy"), and the remaining `#113` slice K2 (surfaces 18 to 21 of `docs/design/pagination-coverage-2026-10-13.md`). Status: A16, A17, A20 and A23 apply decisions the owner already made (decision 1 stores, amendment 2, the #113 contract) and are engineering decisions. A18, A19, A21 and A22 are **proposed**: the owner has not decided whether bounded batch confirmation belongs in the first phase, nor whether the default landing view is the entry list or topic grouping. They are built so the owner can try them; they are not accepted until decided.

### What was found

- The four categories the issue names (task history, workspace observations, bot experience candidates, rule proposals) are already the four stores of decision 1 plus the gate of decision 4, but no single function says which category a learned item goes to, so the issue's mixed-content fixture had nothing to run against.
- "Needs your confirmation" listed every gated row one by one. A bot that proposes the same standing instruction in ten runs produced ten rows, each a separate click, with no sign they were the same proposal.
- The operator entry list (`GET /api/workspaces/:id/memory`) and an entry's version list returned every row; the confirmation list clamped `limit > 100` to 100 and had no scope-bound cursor or total; search clamped `limit` to 50 and its cursor carried no scope (#113 surfaces 18 to 21).
- Nothing grouped entries by what they are about, so a workspace with hundreds of notes was one long list.

### Decisions

A16. **Four categories, decided without a model.** A learned item's category is a pure function in `contracts` (`memoryDisposition`) of its body, proposed scope, sidecar marks and the human rules in force: `skipped` (do-not-learn, A2, with its reason), `refused` (scope `rule`, decision 1), `rule_confirmation` (gated, decision 4 as amended by A6), else by scope `task_history`, `workspace_observation` or `experience_candidate`. The Gateway's learned write uses that function, so the category shown is the one applied. A contradiction with a trusted entry is a `workspace_observation` ordered by recency (A6), never a confirmation. The Gateway does not split a mixed statement into atomic items: the summary instruction asks for one fact per item, and a deterministic splitter would change meaning. Splitting is left to A22.

A17. **Equivalent gated items form one review group.** Every gated row carries a group key computed at gate time: its store (workspace, proposed scope, the bot for `bot` scope, the thread for `task` scope), its trust, and its fact key and value (A7); a body without a fact key uses its normalised body. Equivalent proposals from different runs share a key; a different value, condition number, scope, store or trust gives a different key, so materially different items stay apart. The pending queue can be read as groups: each with its item count, every distinct wording, every source run, and the newest and oldest time, paged with the cursor contract and an exact total of groups and of items. Grouping changes nothing about any item: each keeps its body, reasons, source and status, and an item is still decided only by a human. Rows gated before this amendment get their key the first time their workspace's queue is read.

A18. **Bounded batch dispositions on a group (proposed).** An Admin may decide a group in one action: `reject` (every pending item in it is rejected) or `merge` (the oldest pending item is applied exactly as a single apply is, a trusted note with the human as source; every other pending item of the group is marked applied to that same note and its run is added as a source of the note, which never raises trust, A10). One batch takes at most 50 items, oldest first; a larger group keeps its remainder pending and visible. A batch is always previewed first: the preview lists the exact items, their wordings and the effect, and returns a token derived from the item ids and their statuses. The commit names that token; when any item changed since the preview it is refused as `invalid_transition` and nothing is written. A commit is one transaction and idempotent per token: repeating it returns the first batch. Every committed batch is a `memory_review_batches` row with its items and an audit record (`memory.review_batch`). Batch actions decide only gated items; they never apply a backlog without a human command, never delete an item, never cross a workspace, and never change a rule, SOUL, an approval rule, a risk tier or egress.

A19. **Undo of a batch (proposed).** A batch is undone as a whole by an Admin, audited as `memory.review_batch_undo`, and only while every item is still as the batch left it. Undoing a `reject` returns its items to pending. Undoing a `merge` returns its items to pending, restores any note the merged note superseded (A12, reason `undo_restore`) and forgets the merged note (decision 7: tombstone and redaction). A merge whose item was consolidated into an existing note (A10) instead of creating one is not undoable as a batch: the note has a life of its own; it is changed through its own versions. Undo of an undone batch is refused.

A20. **Topics are deterministic tags.** Each note, candidate and episode has a topic, computed by a pure function in `contracts` (`memoryTopic`): the first name-like word of the body (a capitalised word that is not a stopword, or a word with a digit or an inner capital), else its first content word, lower-cased as the key and shown as first written. The operator entry list filters by topic and the Gateway returns topic counts of the entries that are not forgotten. A topic is a browsing aid, never a scope, a trust level or an access boundary, and it changes nothing a run receives. Rows written before this amendment get their topic the first time their workspace's topics are read.

A21. **Default landing view (proposed).** Until the owner decides, the Observations screen keeps the entry list as its landing view with a row of topic tags as filters above it, and shows "Needs your confirmation" as grouped exceptions with accurate group and item counts. Topic grouping as the landing view is the alternative the owner may choose; both read the same API.

A22. **Model help is a sidecar job, and is not built (proposed).** Topic labels better than A20 and splitting of mixed statements need a model. When built, each runs as a background model job on the existing model-jobs path (ADR-0023 amendment 1): a run row with its knob configuration, `CHEAP_MODEL` from configuration, usage recorded per run, bounded to one pending job per workspace, retried at most once. Its output is a proposal the Gateway validates deterministically; it can label or propose atomic wordings, never change trust, scope, category, a decision or a rule, and its proposals go to the gate like any learned item. Nothing in this amendment calls a model.

A23. **The four learned-memory lists page with the #113 contract.** Entries (surface 18): keyset cursor, 25 by default and 100 at most, ordered `observed_at DESC, id DESC`, filtered on the server by scope, bot, thread and topic. Search (19): rank order with an offset cursor bound to the workspace, query and scope, 20 by default and 50 at most, and the screen says "best matches". Needs your confirmation (20): keyset cursor `created_at DESC, id DESC`, 25 by default and 100 at most, with the exact pending total. Versions (21): keyset cursor `version DESC`, 25 by default and 100 at most, shown with "Load older". A limit outside the range and a cursor of another scope or filter are refused as `validation`, never clamped. The run-side `memory_search` tool is unchanged.

A24. **Measurement (predeclared, not run).** Grouping, categories and topics change what an operator sees, not what a run receives, so they are not a context strategy change. A merge is a human decision like a single apply. What is measured once there is traffic: queue duplication (gated items per group), review effort (human actions per resolved item), group errors (a group holding two materially different items, or one fact split across groups, found in review), batch undo rate, and provenance coverage (sources per merged note). The A14 paired evaluation remains predeclared and not run; this amendment does not authorise a paid memory campaign.

### Consequences of the amendment

- `memory_suggestions` gains `group_key`; `memory_entries` gains `topic`; new tables `memory_review_batches` and `memory_review_batch_items`; two audit actions.
- The confirmation route stops clamping its limit: a caller asking for more than 100 gets a 400. The entry list and the version list return a first page instead of everything; their callers in the web move in the same change.
- Phase 2 of #85 (freshness maintenance, revalidation scheduling, document drafts from observations) is not part of this amendment.

## Amendment 4 (2026-10-14): freshness, revalidation, document drafts and model organisation

Source: issue #85 phase 2 ("maintain knowledge and prepare documents") and the remainder of amendment 3 (A22: model topic labels and splitting of mixed statements). Status: A25, A26, A27, A29 and A33 are engineering decisions that apply existing ones (decision 6 intervals and TTL, decision 5 trust, decision 10 promotion by a human, amendment 2 recency, ADR-0023 amendment 1 model jobs). A28, A30, A31 and A32 are **proposed**: the freshness horizons are guesses, automatic rechecks are only specified, and the owner has not decided whether model labels and splits belong in the product. They are built behind an explicit Admin action so the owner can try them; nothing runs on its own except the deterministic sweep of A26.

### What was found

- Decision 6 gives notes TTL and `last_confirmed_at`, but nothing showed an operator which notes were old, about to expire or already expired. An expired note left the pinned index and search silently.
- Amendment 2's accepted poisoning surface (a newer untrusted value removes a trusted fact from the index) had no place where a human would notice it, other than reading each entry's history.
- Promotion of workspace memory to the tenant's Knowledge (decision 10) was possible only by retyping notes into a new proposal by hand, losing the link to the entries and their sources.
- A22 named model help for topics and splits but left it unbuilt; the deterministic topic of A20 is often the first capitalised word, and a summary item sometimes still states two facts.

### Decisions

A25. **Freshness is a deterministic function of an entry.** `memoryFreshness` in `contracts` reads a note's scope, trust, effective time, `last_confirmed_at`, TTL and whether it superseded a trusted note, and returns its reasons, most urgent first: `replaced_trusted` (an untrusted current note that closed a trusted one, A11), `ttl_expired` (its TTL ran out, so it already left the index and search), `ttl_expiring` (its TTL runs out within 7 days, or within half its TTL when that is shorter, so a renewed short TTL is not flagged at once) and `age` (the later of its effective time and its last human confirmation is older than the horizon: 90 days for workspace facts, 180 days for bot experience). Task notes and episodes are never flagged: task state ends as an episode (decision 11). A forgotten, distilled or superseded note has no reasons. The horizons and the expiring window are constants recorded on every flag row; they are guesses, like the index budget of decision 9.

A26. **"Needs revalidation" is a stored queue kept by a bounded sweep.** One row per flagged note in `memory_revalidations`, at most one open row per note (unique partial index), carrying its most urgent reason, the note version it was flagged at, the horizon in force and when. A sweep of one workspace flags new notes, updates the reason of open rows, and closes open rows whose note no longer qualifies, with the outcome `resolved` (edited, confirmed, renewed), `superseded` or `forgotten`; it never touches a note. It runs when the queue is read and from the scheduler's periodic pass at most once per workspace per hour; it is idempotent, so a restart or two sweeps produce the same rows and never a second open row or a second maintenance job. The queue pages with the #113 contract (keyset `flagged_at DESC, id DESC`, 25 by default, 100 at most) with exact totals per reason.

A27. **A human decides a flag; the queue changes nothing a run receives.** A flagged note stays in the pinned index and search exactly as before. An Admin may answer a flag with `still_true` (a `confirm` version of the note with `last_confirmed_at` now and trust unchanged: an untrusted note stays untrusted, decision 5; this renews TTL) or `dismiss` (the row is closed, the note unchanged; the same note version is not flagged again for the same reason). Forget, undo and confirm stay the entry's own actions and close the flag through the sweep. Each decision is audited (`memory.revalidate`). A copy of the same value (A10) never renews a note; only a human decision does. Withholding flagged notes from the pinned index, or marking them stale in it, would change what runs receive: it is a strategy change, not built, and needs the paired evaluation of A14 first.

A28. **Automatic rechecks are specified, not built (proposed).** A recheck would be a background-lane bot run asked to observe a flagged fact again. Before one is built the policy is fixed: off by default and opt-in per workspace; at most 3 rechecks per workspace per day and one pending at a time; no automatic retry; charged to the workspace budget (ADR-0032) like any run; its findings are ordinary learned items through decisions 3 and 4 and amendment 2, so a recheck never raises trust and a browsing recheck writes untrusted values; a recheck never decides a flag, it only adds observations. This amendment schedules only the deterministic sweep of A26.

A29. **Document drafts from observations are proposals a human publishes.** An Admin of a workspace selects 1 to 50 current notes of that workspace (workspace or bot scope) and a title. Every selected note must be trusted; an untrusted note is refused until a human confirms it (decision 5), so page text never reaches tenant Knowledge through this path. The Gateway composes the Markdown deterministically, without a model: the title, one dated line per note in effective-time order, each ending with a numbered citation, and a "Sources" list naming entry, version, source run, learned-by bot and effective time. The draft is stored as a pending Knowledge proposal of the workspace's tenant with one citation row per (entry, version). A draft may instead target an existing document at its current version: its body is that document with a new dated section appended, the review shows the difference, and approval writes a new version of that document only if it is still at the targeted version, otherwise it is refused as `invalid_transition`. Publication is the existing Admin review of a proposal (ADR-0022): never automatic, and rejecting a draft changes nothing in memory. A citation whose note changed after the draft is shown as changed. Creating a draft makes the selected wording visible to the tenant's proposal reviewers; that is the explicit human act decision 10 asks for.

A30. **Model organisation is a manual sidecar job (proposed).** An Admin may ask for `memory_organize` on a workspace. It is a model job on the ADR-0023 amendment 1 path: a run row first (background lane, of the workspace's oldest active bot, which only attributes it), `CHEAP_MODEL` from configuration, no tools, one turn, usage recorded per run, its knob configuration and input entry versions in `runs.config_json`. One pending job per workspace: a repeated request returns the pending one. No automatic retry and no schedule; a failed job is shown failed and may be asked for again. Its input is at most 40 current notes of workspace and bot scope, newest first, each body escaped and marked as untrusted data in the prompt. The Gateway never calls a model.

A31. **Model labels are browsing tags, validated and reversible (proposed).** The job returns labels for entry ids of its input. The Gateway keeps a label only when the id was in the input and the note is still at the version sent, and the label is 1 to 40 characters, at most 4 words, one line, without markup. A kept label replaces the note's topic (key lower-cased) with source `model` and the job's run; editing the body returns it to the deterministic topic of A20, and an Admin can reset every model label of the workspace at once. A label is a browsing aid like A20: never a scope, a trust level or an access boundary, and it changes nothing a run receives.

A32. **Model splits are proposals; accepting one is a human decision (proposed).** The job may propose splitting a note into 2 to 5 parts. The Gateway keeps a proposal only when every part is non-empty, shorter than the original, contains only words and numbers that appear in the original (so a split cannot add content), and is not classified as an imperative or do-not-learn item (A2); the parts are stored as a pending `memory_split_proposals` row with the note version it was made from. An Admin accepts or rejects it (audited `memory.split_decide`). Accepting, only while the note is still current at that version, closes the original with a `supersede` version and writes each part through the recency writer (amendment 2) in one transaction, with the original's store, trust, authority, source kind, source run and effective time, and `derived_from` naming the original: a part never has higher trust or a newer time than its original. An accepted split is undone as a whole, while every part is still as the split left it: the parts are forgotten (tombstone and redaction, decision 7) and the original reopened.

A33. **Measurement (predeclared, not run).** The queue, its decisions and drafts change what an operator sees, not what a run receives: not a context strategy change. Accepted splits and model labels change entries, and splits change what the pinned index and search can return; they therefore join A14's paired evaluation as one more knob (splits off against on) before they are called better. Measured once there is traffic: flagged notes per workspace and per reason, decisions per flag, share of `still_true` against forget or undo, drafts published against rejected, citation coverage (notes cited per published draft), label kept rate and split kept and accepted rates, and model-job tokens per workspace. No paid campaign is authorised by this amendment and no result is claimed.

### Consequences of the amendment

- New tables `memory_revalidations`, `knowledge_proposal_citations`, `memory_split_proposals` and `memory_split_parts`; `knowledge_proposals` gains `target_document_id` and `target_version`; `memory_entries` gains `topic_source` and `topic_run_id`; two audit actions.
- `ModelJobRequest` gains `memory_organize`; `memory_organize` joins the cheap-model job kinds and the model-job run types.
- The scheduler's periodic pass gains the hourly freshness sweep; it reads entries and writes only flag rows.

## Consequences

- The "Learned memory" page replaces the memory-suggestion review page: per workspace and per bot, showing content, scope, trust, authority, source and age, with edit, forget, undo and confirm. "Needs your confirmation" lists only gated items.
- `packages/contracts` gains the memory entry, version and scope types; the Gateway gains a `memory` module and migrations; the sidecar gains taint tracking, the `learned` summary field, `memory_search` and the `PreCompact` flush.
- Bot experience accumulates slowly by design: only trusted or human-confirmed sources feed it. A workspace whose bots only browse untrusted sites builds workspace facts and episodes, not experience, unless a human confirms items. That is the intended cost of item 5.
- The line budgets in item 9 are guesses; Phase 5 of the plan calibrates them with paired comparisons, one knob per experiment.
- Open: whether the pinned index is delivered in the first user turn or through a `UserPromptSubmit` hook's `additionalContext`; decided in Phase 3 by whichever keeps the system prompt byte-identical under SDK 0.3.278.
