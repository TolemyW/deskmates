# ADR-0046: Run observability as an append-only model behind pluggable sinks, with a built-in Grafana

Status: Accepted (under owner delegation, 2026-10-17; owner request of 2026-10-17), decisions 1 to 10 and amendment 1's decisions 11 to 17, with one change to decision 2. Decisions 5 and 2 take the recommendations the owner accepted on 2026-10-17: the lake uploader is an external service behind a forwarding sink, and the collector is a Gateway module. Change on acceptance: an external sink (`postgres`, `forward`) is refused at startup unless `OBSERVABILITY_PAYLOADS` is set explicitly, so sending tool results and thinking to an engine outside the host is a written choice, never a default; the built-in `sqlite` sink keeps the `full` default. Amendment 1's choices are accepted as written: the Viewer role (least privilege for provisioned dashboards), the CSRF exemption for the two relay patterns (a fixed list, the `Origin` check still in force, a `SameSite=Lax` cookie, nothing a Viewer can change), Live off, relayed requests spending the tenant's request budget (the conservative choice; the share one dashboard load spends is to be measured on the stable host before any exemption), and trusting the host's loopback (the host's processes already read the ledger). Implemented: phase 1, amendment 1 and amendment 2 (which brings decision 9 forward). Not implemented: phase 2 (`postgres`, `forward`, `images/obs-lake`, the silent runs and tasks dashboards). Pending: phase 1's acceptance (row counts equal to the demo collector's over the same ledger, and the kill tests on a live host), the T2 Grafana image test, and the stable-host checks.
Amendment 1 (2026-10-17, owner request "tier 2" of 2026-10-17): Grafana behind the Gateway's own sign-in, for the root account `admin` only; decisions 11 to 17 below. It supersedes decision 6's separate Grafana login, its port on the operator's network and its anonymous Viewer access, and decision 8's `OBSERVABILITY_GRAFANA_URL` as the browser's address; it brings phase 3's auth proxy forward.
Amendment 2 (2026-10-18, owner rulings A and B of 2026-10-18): Accepted (owner-decided) for its two rulings, the four focus dashboards (model latency, prompt cache, approvals, tool calls) on SQLite first and the failure retrospective on by default whenever an embedding service is configured, with the SQLite sink storing vectors; decisions 18 to 26 below. How each ruling is carried out (the split of Tools and approvals, the new views, contract version 2 with an in-place upgrade, the model on proxy spans, the `retrospective` corpus, five matches per failed run, the `OBSERVABILITY_RETROSPECTIVE=off` switch) is proposed with it for the owner's review. It brings decision 9 forward from phase 3. Implemented 2026-10-18 with the T0/T1 tests of its Verification table, which pass; not verified: Grafana rendering the five dashboards (the T2 `acceptance/grafana-image.container.test.ts` is updated and skips without Docker) and the retrospective against a real embedding service, both on the stable host.

## Context

The Gateway's ledger answers "what happened in this run": `runs`, `run_events` (18 kinds, `payload_json`), `model_requests`, `run_usage`, `tasks`, `approvals`, and since ADR-0042 `run_marks` and retention pruning of old events. It does not answer the questions an operator asks across bots and days: which runs fail and why, what a task cost, how a model's latency moved, which tools fail, how long humans take to decide, whether a failure has been seen before. The web UI has Costs (ADR-0032 amendment 1) and the run drawer (ADR-0042); neither is an analytics surface, and the ledger is the live write path with a retention window, so it should not become one.

A lab demo of 2026-10-15 and 2026-10-16 built that surface outside the product: a Python collector read the stable installation's ledger read-only by id watermark, buffered to JSONL, closed a batch every five minutes or 64 MB, wrote one Parquet file per table with Parquet field ids into the vendor's lake tables, registered each file with an idempotent commit token, kept a batch ledger as the data watermark, and six Grafana dashboards (agent runs, model performance, cache and context, tools and approvals, silent runs, tasks) read an `obs` schema of append-only snapshot tables and views (the scenario design "Observing agent runs on the vendor's database" of 2026-10-15, and its implementation record). Its first finding, that most failures were cheap-model jobs on a model the upstream did not serve, came from one dashboard in an afternoon. The owner wants that inside Deskmates: a built-in Grafana, the data engine pluggable, the built-in SQLite as the default, external PostgreSQL or the vendor's lake as options, and the file-upload path as a plugin.

What the demo got right is kept: an append-only model with snapshots and derived columns precomputed by the collector (dashboards then need no engine-specific date or JSON functions), batches with a ledger and idempotent commits, and dashboards that read views only. What changes is where the pieces live: the reader belongs to the Gateway, which owns the ledger; the writer belongs to a sink chosen by configuration; the vendor's constraints (field ids, column order, a list column last, no server-side binding) stay inside the one sink that needs them.

Rules this must respect: the control plane never calls a generative model (it may call the embedding service of ADR-0041); images preinstall everything; no runtime code download; the Gateway loads only release-bundled entry points through a versioned contract (ADR-0017 amendment 1); vendor and host names never enter a tracked file (the public mirror); nothing in `packages/` hardcodes a model name.

## Decision

1. **Observability is its own append-only model, fed from the ledger.** The `obs` model has the demo's schema v2 tables (`run_events` with derived tool, phase, duration and mark columns; `run_states`, `task_states`, `bot_states`, `workspace_states`, `thread_states` as change snapshots; `model_requests`, `run_usage`, `task_runs`; `ingest_batches`) plus three the demo lacked: `run_marks` (ADR-0042, the human label a retrospective is judged against), `run_summaries` filled from `run_activity_summaries` (ADR-0033) instead of a collector-made sentence, and `approval_decisions` with the wait the thread endured. Every table carries `batch_id`; views (`runs_latest`, `runs_named`, `tool_calls`, `phase_spans`, `model_request_timing`, `requests_named`, `run_metrics`, `approval_waits`, `watermarks`) are the only thing a dashboard reads. The ledger is never read by Grafana and never grows columns for the dashboards' sake.

2. **The collector is a Gateway module.** `packages/gateway/src/observability/` (a `create...Module`, env in `src/config/observability.ts`) reads `run_events`, `model_requests` and `run_usage` by their autoincrement id and the snapshot tables by `updated_at`, in short read transactions on the Gateway's own connection; computes the derived columns; buffers to a local JSONL spool under the data directory with the received watermark advanced only after fsync; closes a batch every `OBSERVABILITY_BATCH_SECONDS` (default 300) or `OBSERVABILITY_BATCH_BYTES` (default 64 MiB); hands the batch to the sink; advances the committed watermark and drops the spool only when every table of the batch is committed. It reads events before retention prunes them (ADR-0042 decision 6 prunes by days; a batch is minutes). It never calls a generative model. Payload policy is `OBSERVABILITY_PAYLOADS=full|derived` (default `full`: `payload_json` kept, truncated past 64 KB with the original size recorded, screenshots reduced to their size; `derived`: no payload bodies at all); the ledger's redaction has already run, so nothing reaches a sink that the ledger does not hold. An external sink (`postgres`, `forward`) is refused at startup unless `OBSERVABILITY_PAYLOADS` is set explicitly (added on acceptance, 2026-10-17). `OBSERVABILITY_SINK=` unset (the default for an existing installation until a release makes `sqlite` the default) means the module does not run.

3. **The engine is a sink behind a versioned contract.** `packages/contracts` gains `observability.ts`: `ObservabilityBatch` (one batch, per-table row arrays in declared column order, the batch id, source id ranges), `ObservabilitySinkManifest` (`id`, `version`, `contractVersion`, `engine`, `capabilities: { vectors: boolean, dialect }`) and `ObservabilitySinkRuntime` (`ensureSchema()`, `writeBatch(batch) -> { committed: string[] }`, `lastCommitted() -> batchId`, `close()`). A sink commits each table of a batch under the token `obs/<table>/<batch_id>`; replaying a committed token is a no-op, so a crash between tables is repaired by resending the batch. The Gateway's generic loader selects the sink by `OBSERVABILITY_SINK` from release-bundled entry points only (ADR-0017 amendment 1 reading). Three sinks ship: `sqlite` (default), `postgres`, and `forward`.

4. **The built-in sink is a second SQLite file, not the ledger.** `sqlite` writes `obs.sqlite` beside `gateway.sqlite` (`OBSERVABILITY_SQLITE_PATH`), WAL mode, one transaction per table per batch with `ingest_batches` carrying the commit token under a unique index; the views are SQLite SQL. It has its own retention, `OBSERVABILITY_RETENTION_DAYS` (default unlimited), independent of the ledger's. Grafana reads the file through the SQLite datasource plugin with the data directory mounted and the file opened read-only. `postgres` is the same tables and views in PostgreSQL SQL, written with batched inserts in one transaction per table per batch; `OBSERVABILITY_URL` is its DSN and is never logged.

5. **The lake uploader is an external service behind the `forward` sink.** `forward` POSTs each batch as newline-delimited JSON per table to `OBSERVABILITY_URL` with `Authorization: Bearer $OBSERVABILITY_TOKEN`, and treats the service's `{committed: [...]}` as the commit record; it holds no engine knowledge. The service is `images/obs-lake`, a Python program ported from the demo's collector back half: Parquet with field ids assigned by table ordinal (list columns last), one file per table per batch under the table's data directory with a manifest, registration by commit token, a spot check of one row per batch that stops ingestion on an all-NULL read, daily adjacent-file merge. It speaks the vendor's protocol only inside its own container, and its name and docs call the target `the lake` or VendorDB; the real product and host names live in the installation's `.env`. A second lake or warehouse is another service behind the same `forward` sink, not a Gateway change.

6. **Grafana is a release component.** `images/grafana` builds the pinned official image with the SQLite datasource plugin preinstalled (no plugin download at run time). `scripts/stable/stable.sh grafana init|start|stop|status` runs it as one container on the host network at `OBSERVABILITY_GRAFANA_PORT` (default 18700), with an admin password generated once into a 0600 file, analytics and update checks off, anonymous access as `Viewer` when `OBSERVABILITY_GRAFANA_ANONYMOUS=1`, and provisioning mounted from the active release: the datasource file for the selected engine and that engine's dashboards. Signing in with the Gateway's session (an auth proxy in front of Grafana) is a later amendment; until then Grafana is a separate login on the operator's network.

7. **Dashboards are one spec, generated per engine.** `packages/observability-dashboards/` (dev-only, imports nothing) holds the panel spec ported from the demo's generator and a dialect layer of five macros: hour bucket, median, regular-expression extract, time difference, JSON field. It writes `observability/grafana/<engine>/*.json` and the datasource files, which are committed and checked by a test that regenerates and diffs them (refreshed with `UPDATE_GENERATED=1`, never edited by hand). A query uses the views of decision 1 and the macros only; a panel that needs an engine-specific function is a defect in the spec.

8. **The operator sees the pipeline's state.** `GET /api/observability/status` (root only) reports the sink id and engine, the received and committed watermarks per table, the newest batch and its age, the spool size, and the last error. The web navigation shows an Analytics entry that opens `OBSERVABILITY_GRAFANA_URL` when it is set; the entry is hidden otherwise. The run drawer links each run to its Grafana run view by id when the URL is set.

9. **The retrospective is a later phase on the same model.** Run summary embeddings and nearest-successful-run matches (the demo's failure retrospective) are computed only when the sink declares `capabilities.vectors`, using the embedding service of ADR-0041 (recorded in `retrieval_calls`, so the control plane still calls no generative model) and ADR-0033's summaries as the text; `run_marks` are the labels that decide whether a match threshold is worth anything. Until then `run_summaries` holds the summary text without a vector.

10. **Observability is a measurement surface, not a control.** No Gateway decision reads the `obs` model; data flows one way, ledger to sink. A finding becomes a strategy change through `evals/compare.ts` as AGENTS.md requires, never through a dashboard threshold acting on its own.

## Alternatives considered

- **Point Grafana at the ledger.** The ledger is the write path, prunes events by days, holds no derived durations, and every engine-specific function the dashboards need would have to be SQLite's. Rejected: decision 1 and 4.
- **A separate collector process reading the ledger file, as the demo did.** Works, and is how the demo was verified; but it reads another process's WAL database, duplicates the ledger's row shapes outside the package that owns them, and needs its own deployment unit. The owner accepted the module (decision 2); the spool and watermark design is kept so the module can become a process later without a schema change.
- **A Node in-process lake plugin.** Would need a Parquet writer that sets field ids and a vendor client inside the Gateway's dependency tree; neither is verified. The Python back half is verified end to end. Rejected for now (decision 5); an in-process sink can be added behind the same contract if that writer is found.
- **Langfuse or an OpenTelemetry pipeline.** Rejected by the owner on 2026-10-15 for the demo (a second store, a second product); the ledger already carries what OTel GenAI does not (tasks, approvals, memory changes). An OTel exporter can be a fourth sink later.
- **Embedding Grafana in the web UI now.** Needs the auth proxy; deferred to an amendment (decision 6).

## Consequences

- `packages/contracts` gains `observability.ts`; `packages/gateway` gains `src/observability/`, `src/config/observability.ts`, the status route and its policy file; `packages/web` gains the Analytics entry and the run link; `scripts/stable/stable.sh` gains the `grafana` command; `images/grafana` and `images/obs-lake` are new images with their own content tags (runbook "image tags and artifact naming").
- A new dev-only package `packages/observability-dashboards` and a committed, generated `observability/` directory.
- The release workflow builds two more images; the stable host runs one more container (Grafana) and, with the `forward` sink, a second (the lake service).
- Data volume: the demo measured about 288 batch files per table per day on the lake; SQLite and PostgreSQL see one transaction per table per batch instead. `obs.sqlite` grows without bound unless `OBSERVABILITY_RETENTION_DAYS` is set.
- Privacy: with `OBSERVABILITY_PAYLOADS=full`, tool results and thinking blocks leave the ledger for the sink; an installation that sends them to an external engine is sending business data there. The default is `full` because the demo's value came from reading payloads; the switch exists so an installation can say otherwise.

Rollout: phase 1 is decisions 1 to 4 and 6 to 8 with the `sqlite` sink and the two dashboards the demo used most (agent runs, tools and approvals), accepted when the module's row counts per table equal the demo collector's over the same ledger and a kill at each of spool, batch close and commit loses and duplicates nothing; phase 2 adds `postgres`, `forward` with `images/obs-lake`, and the remaining four dashboards; phase 3 is decision 9 and the auth proxy.

## Amendment 1 (2026-10-17, owner request of 2026-10-17): Grafana behind the Gateway's sign-in

Decision 6 left Grafana a separate login on the operator's network: its own admin password, a port that any host on that network could reach (workspace containers included, through the host's bridge address, since it ran on the host network on every interface), and an optional anonymous Viewer. The obs model holds every workspace's runs and, under `OBSERVABILITY_PAYLOADS=full`, tool results, which no workspace role covers; that is why the status route, the Analytics entry and the run link are the root's alone (decision 8). The owner asked on 2026-10-17 that Grafana itself be visible only to the root account `admin`, signed in to Deskmates ("tier 2"). The Gateway already relays a workspace UI with a credential it holds and the browser never sees (the noVNC proxy, ADR-0022 amendment 1); this is the same shape for HTTP. The Gateway stays thin: it forwards bytes, never reads the obs model, and calls no model.

11. **Grafana listens on the host loopback only, under `/analytics/`.** `stable.sh grafana start` runs it with `GF_SERVER_HTTP_ADDR=127.0.0.1`, `GF_SERVER_ROOT_URL=http://127.0.0.1:<OBSERVABILITY_GRAFANA_PORT>/analytics/` and `GF_SERVER_SERVE_FROM_SUB_PATH=true`, still on the host network so that the Gateway's systemd unit reaches it. Nothing off the host reaches it, and neither does a workspace container, which reaches the host through its network's gateway address. `OBSERVABILITY_GRAFANA_URL` is now the Gateway's upstream, not the browser's address: an `http` origin whose host is loopback (`127.0.0.1`, `::1` or `localhost`), with no path. The Gateway refuses anything else at startup, so a decision 6 value naming the host's network address fails loudly instead of sending the identity header across a network.

12. **Grafana trusts the Gateway's header, and its only user is a Viewer.** Grafana runs in `auth.proxy` mode: header `X-WEBAUTH-USER`, property `username`, whitelist `127.0.0.1, ::1`, auto sign-up into the main organisation with the role `Viewer`. The Gateway only ever names `admin`, so that is the one user. Viewer is the least privilege that serves the purpose: the datasource and dashboards are provisioned from the release and generated by decision 7, never edited in Grafana, and a Viewer opens every dashboard and runs its panel queries; editing, Explore and administration are unavailable, and Explore would need Editor in a later amendment. No initial Grafana administrator is created (`GF_SECURITY_DISABLE_INITIAL_ADMIN_CREATION=true`), so there is no Grafana password and `grafana/admin-password` is retired; the login form, the sign-out menu, basic authentication, sign-up and anonymous access are off. `OBSERVABILITY_GRAFANA_ANONYMOUS` is retired: `stable.sh grafana` refuses any value other than empty or `0`, with a message naming this amendment, rather than ignoring it. There is no break-glass sign-in, because none is needed: `start` and `status` read `/analytics/api/health`, which Grafana answers without one. A Grafana state directory from decision 6 (it holds `admin-password`, and its database holds `admin` as Grafana's server administrator, whom the header would then sign in) is refused by `init` and `start` until the operator removes it. Any process on the host's loopback can send the header; the host's own processes are already inside the Gateway's trust boundary (they can read the ledger file), so this widens nothing.

13. **The Gateway relays `/analytics` and `/analytics/*` on the operator listener, to the root's own session only.** The routes are an operator route family with a route-policy file like every other, under a new policy access `root_session`: a signed-in browser session of the protected account `admin`. No session is the operator listener's ordinary 401; any other person, an Owner included, is 403 `root_only`; the operator credential and a service principal are 403 and a run token 401, so no bearer credential ever reaches Grafana. Unsafe methods need a same-origin `Origin`, as on every operator route, but not the session's CSRF header, because Grafana's own frontend cannot send it. That exemption is a fixed list of these two route patterns in the operator authentication hook; the session cookie is `SameSite=Lax`, the `Origin` check still refuses a cross-site request, and Grafana's Viewer role (decision 12) leaves nothing a forged request could change. With `OBSERVABILITY_GRAFANA_URL` unset the relay answers 404. Every relayed request spends the tenant's request budget, as every root route does.

14. **The relay forwards bytes and asserts one identity.** It removes from the request the hop-by-hop headers, every `X-WEBAUTH-*` header the client sent, `Authorization`, the Gateway's session and pre-login cookies (other cookies pass), the CSRF and tenant selector headers, `Origin` (already checked; Grafana sees its own host), and `Forwarded`, `X-Forwarded-*` and `X-Real-IP`, so that Grafana's whitelist sees the loopback peer and never a client-asserted address; then it sets `X-WEBAUTH-USER: admin`. Path and query pass unchanged, since Grafana serves the same sub path. Status, headers and body stream back untouched except for the hop-by-hop headers and a `Location` on the upstream origin, which becomes its path. Bounds: 30 seconds to the response headers, 60 seconds of inactivity in either direction, request bodies of at most 16 MiB (413). An unreachable or silent upstream is 502 `analytics_unavailable`, whose body names no address.

15. **Grafana Live is off.** `GF_LIVE_MAX_CONNECTIONS=0`, and the relay upgrades no WebSocket. The provisioned dashboards refresh by polling, so Live adds nothing they use, and relaying it would need a second admission path for upgrades, the larger option.

16. **The web opens Analytics on its own origin.** `GET /api/config` returns `analyticsUrl: "/analytics/"` when `OBSERVABILITY_GRAFANA_URL` is set and null otherwise; the internal address is reported only by the root-only status route. The Analytics entry and the run drawer's link use it and still open a new tab: Grafana is a whole-page application with no way back into the operator UI, and a run opened from the drawer should not discard the drawer. The Vite development server proxies `/analytics` to the operator listener beside `/api`.

17. **Private chats stay `derived`.** Only the root sees Grafana now, but a private chat is readable only by its person, the root included (AGENTS.md, ADR-0022 amendment 6 W7), so a run in a private chat still sends no payload body, summary or chat title into the obs model under any payload policy (decision 2). Restricting Grafana to the root is not a reason to relax that.

## Amendment 2 (2026-10-18, owner rulings A and B of 2026-10-18): four focus dashboards on SQLite, and the failure retrospective switched on

The owner answered two questions on 2026-10-18. A: "SQLite first; the dashboards are mainly for model latency, cache hit rate, approvals and tool calls." B: "Switch it on first, do it together with A, and see how it works." Phase 1 shipped two dashboards (agent runs; tools and approvals) and left decision 9, the retrospective, to phase 3. This amendment brings the four focus areas and decision 9 forward on the `sqlite` engine; `postgres`, `forward` and the silent runs and tasks dashboards stay in phase 2. The v0.7.3 acceptance found a band of model requests whose provider reported no cache tokens, which a cache panel read as a 0 % hit rate; decision 20 is the rule that keeps that from recurring.

18. **Five dashboards, SQLite first.** The sqlite engine ships Agent runs (unchanged uid and run view), Model latency, Prompt cache, Approvals and Tool calls. Tools and approvals is split into the last two and its uid `deskmates-tools-approvals` retires. Phase 2's "model performance" and "cache and context" are these two; silent runs and tasks stay in phase 2. The dashboard provider already reads the whole `dashboards/` directory, so `stable.sh grafana` needs no new provisioning entry.

19. **New views, and percentiles as plain SQL.** The sqlite schema gains the views `model_latency` (one row per model proxy request with its time to headers, time to first byte and body time), `request_cache` (one row per model request with its cache status), `approval_requests_named` (every approval request with its decision, if any) and `failure_matches` (decision 25); `approval_waits` gains `decider_group` and `phase_spans` gains `model`. `OBSERVABILITY_VIEWS` lists them, and dashboards still read views only. Percentiles (p50, p90, p95, p99) use the nearest-rank method written with `row_number()` and `count(*)` windows and integer arithmetic, which every engine spells the same, so they are one helper, `packages/observability-dashboards/src/percentiles.ts`, and not a sixth macro: decision 7's five macros stay five.

20. **Cache tokens a provider did not report are "not reported", never zero.** `request_cache.cache_status` is `refused`, `no_usage` (no usage landed), `not_reported` (usage landed without a cache-read count), `hit`, `write` (cache creation only) or `miss` (both reported as 0). `reported_prompt_tokens` and `cache_read_share` are null unless the cache-read count was reported, so a share is computed over reporting requests only and a not-reported request never counts as a miss. Every cache panel shows the not-reported requests as their own band or column.

21. **A model proxy span names the request's model.** `PhaseTimingSample` gains an optional `model`: on the proxy's spans, the model the proxy sends upstream, after any rewrite. The collector writes it into the existing `run_events.model` column and `phase_spans` exposes it; a span recorded before this amendment falls back to the run's model in `model_latency`. No table or column of the obs model changes for this.

22. **Pending approvals are in the model; contract version 2.** A fact table `approval_requests` holds one row per approval when it is created (no decision columns), read from `approvals` by `(created_at, id)`, so a pending approval is a request without a decision row and its age is a dashboard computation. An expired approval is a decision by `system:expiry` (ADR-0002 amendment 3), whose `decider_group` is `expired`; `human` covers the `human:` and `user:` deciders, `closed` the other `system:` ones, and `reviewer`, `rule`, `mode` and `bot` are their own groups. A new table bumps `OBSERVABILITY_CONTRACT_VERSION` to 2. The sqlite sink upgrades a version 1 file in place, since version 2 only adds tables and changes no version 1 column; a file of any other version is still refused.

23. **The retrospective is on by default when an embedding service is configured (ruling B).** It runs when the selected sink declares `capabilities.vectors` and ADR-0041's `EMBEDDING_URL` and `EMBEDDING_MODEL` are set; `OBSERVABILITY_RETROSPECTIVE=off` turns it off, and without an embedding service it does nothing and calls nothing. The `sqlite` sink now declares `vectors: true`: it stores one L2-normalised little-endian float32 BLOB per run and embedding model in `run_vectors` (ADR-0041 decision 3's format; no SQLite extension) and the matches in `retrospective_matches`, behind `ObservabilitySinkRuntime.vectors`. The sink stores and returns vectors; cosine similarity, a dot product of normalised vectors, is computed in the Gateway module, brute force over one workspace, inside ADR-0041 decision 11's stated scale.

24. **What is embedded, and how calls are recorded.** In `finished_at` order, each ordinary run (no `runType`) that ended `succeeded` or `failed`, with its Activity summary as ADR-0033 shows it: the verbatim outcome when it fits, else the ready summary of the run's current source version. A pending summary holds the walk for at most 15 minutes, after which the run is skipped; a failed summary or an empty text is skipped. A run in a private chat is never embedded, so it is never matched and never offered as a match (decision 17). Every embedding request goes through ADR-0041's `EmbeddingClient` and writes one `retrieval_calls` row with corpus `retrospective`, purpose `index`, the workspace's tenant and no run id (the run's tools did not cause it); a migration widens the corpus check. `OBSERVABILITY_PAYLOADS` does not change what is embedded: the sink holds the vector and the similarity, never the text, and under `derived` the dashboard shows no summary text because the obs model has none.

25. **Matches.** When a failed run is embedded, its five most similar succeeded runs of the same workspace embedded so far under the same embedding model are stored with their similarity and rank. A run marked wrong (ADR-0042) is never offered: it is left out when matches are computed, and `failure_matches` drops a match whose run has been marked wrong since. Matches are computed once per failed run and source version; they are not recomputed when later successes arrive.

26. **Thresholds are display filters; measurement only.** Similarities are stored unfiltered. The dashboard's minimum similarity is a dashboard variable that filters what is shown and nothing else (decision 10); no Gateway decision reads `run_vectors` or `retrospective_matches`, and the module reads back only the vectors it wrote, to score them. The status route reports whether the retrospective runs, its embedding model, its position and its last error.
