# ADR-0040: Look/OCR and speech-to-text as bounded operations proxied by the Gateway

Date: 2026-10-14
Status: Accepted (in part; owner-decided 2026-10-14, owner decisions 8, 9 and 15): a look/OCR operation on a vision model, used by models that cannot see images, for images and scanned PDFs; ASR through whisper; `poppler-utils` in the workspace base image; endpoints and credentials at installation level only, in the Gateway's `.env`; no automatic retry or cross-destination fallback; no per-message selection; automatic probes for vision only (none for look/OCR or ASR); local services priced as known zero. Proposed engineering choices awaiting owner review: the tool names and parameters, the Gateway-side adapter (decision 3), the size, page and duration bounds, offering the tools to every run of an installation that configures them (decision 2), the text-layer threshold (decision 5), and keeping operation spend out of `budget_charges` and the Costs page in this version (decision 9). Issue #115; design `docs/design/multimodal-models-2026-10-14.md` §7 option A.

## Context

The design for issue #115 found that Deskmates has one model surface, the agent's text loop, and no path at all for OCR or speech recognition (§3.7, gaps G5 to G7). ADR-0023 amendments 2 and 3 withhold images and PDFs from a run whose model cannot see: the model is told it cannot view them and must not guess. That removes confabulation but leaves a blind model with no way to read a screenshot, a scanned contract or a photo of a receipt. An audio file (an upload, a voice note) cannot be read by any run.

On 2026-10-14 the owner set up local services on the internal host tos-00 (`172.17.120.16`, reachable from the stable host, no authentication): a vision model `qwen3.5-9b-vl` behind an Anthropic `/v1/messages` route (port 8005) and faster-whisper behind an OpenAI-compatible `/v1/audio/transcriptions` route (port 8007). The owner approved a look/OCR tool on the vision model used automatically by blind models, and ASR through whisper.

The design compares five runtimes (§7.1) and recommends option A for provider-backed operations: a sidecar tool asks a Gateway operation proxy, which forwards to the configured service. Option C (the Gateway calls a model on its own) breaks the thin-core rule; option B (a local engine in the image) needs model weights in the image. The 2026-09-28 protocol check showed that one model can read an image over one route and not another (§3.5), so the route is configuration, not an assumption.

## Decision

1. **Two operations, sidecar-initiated, Gateway-proxied.** `look` (describe an image, or transcribe its text) and `asr` (speech to text) are the operations. A sidecar tool reads the input from the workspace and posts it to `POST /internal/runs/:runId/operations/look` or `/operations/asr`, authenticated by the run's token like every other internal route; another run's token is refused. The Gateway forwards exactly one request to the configured service and returns the text. The Gateway never starts an operation on its own, never fetches a URL a model wrote, and never retries: the proxy makes one upstream call per request, the sidecar tool makes one request per page or file, and the bot may call the tool again, which is a new recorded operation. No automatic fallback to another service exists (owner decision 15).

2. **Installation configuration only, and a tool exists only when its service is configured.** `VISION_OPERATION_URL` and `VISION_OPERATION_MODEL` turn on `look`; `ASR_OPERATION_URL` and `ASR_OPERATION_MODEL` turn on `asr`. Each pair is set together or not at all, and the Gateway refuses to start otherwise. Optional per service: `*_OPERATION_AUTH_TOKEN` (sent as `Authorization: Bearer`; kept in Gateway memory, never stored, never sent to a sandbox), `*_OPERATION_PRICE_USD` (decision 8). `VISION_OPERATION_PROTOCOL` is `anthropic-messages` (default) or `openai-chat`. The run config of every run carries `operations: { look?: { model, endpointSha256 }, asr?: { model, endpointSha256 } }` when a service is configured, and the run's sidecar is offered `image_describe` and `audio_transcribe` accordingly. No workspace or bot setting selects or disables a service in this version; the design's per-workspace enablement (§6.1) is not built.

3. **The Gateway holds the adapter; the sidecar sends a normalized request.** The sidecar sends `{ mode, question?, mediaType, data (base64), unit, source }` for `look` and `{ mediaType, data, fileName, language?, durationSeconds?, source }` for `asr`. The Gateway builds the one upstream body from a fixed template: for `look`, a single user turn with one image block and a fixed instruction per mode (`ocr`: transcribe all text exactly, keep reading order, say when there is none; `describe`: describe the image, answering the question when given), `max_tokens` 2048, temperature 0, no tools, no system prompt from the run; for `asr`, a multipart form with `file`, `model`, `response_format=verbose_json` and the optional `language`. A run token therefore buys one bounded operation, never a free-form call to the vision model; prompt text, page content or a file name cannot change the destination or the model.

4. **Inputs are checked before any spend, on both sides.** The sidecar resolves the path with `realpath` and accepts only a regular file under `/work/`, `/home/` or `/tmp/` (never `/profile`), refuses links that leave those roots, and sniffs the media type from the bytes: PNG, JPEG, GIF or WebP images up to 10 MiB, PDF up to 50 MiB; WAV, MP3, OGG, FLAC, WebM or MP4/M4A audio up to 25 MiB, which `ASR_OPERATION_MAX_BYTES` may lower. The Gateway decodes and re-sniffs the bytes, rechecks the sizes, the mode, a question of at most 2000 characters and a language of two or three lower-case letters, and refuses anything else with `validation` or `payload_too_large` without calling the service.

5. **PDFs: the text layer first, then one rendered page per call, bounded.** `image_describe` on a PDF reads its page count with `pdfinfo` and takes `pages` (for example `"1-3"` or `"2,5"`, default the first 5) up to 10 pages per call. In `ocr` mode each page is first read with `pdftotext -layout`; a page with at least 16 non-space characters returns its text layer with no model call, and a page with less is rendered with `pdftoppm -png -r 150` and sent to `look` as one `page`. In `describe` mode every requested page is rendered and sent. `poppler-utils` (`pdfinfo`, `pdftotext`, `pdftoppm`) is installed in the workspace base image (owner decision 8). The tool result labels each page as text layer or vision.

6. **Audio is bounded by size and, where the bytes say, by duration.** `audio_transcribe` computes the duration of a WAV file from its header and refuses one longer than `ASR_OPERATION_MAX_SECONDS` (default 1800) before any spend. For other formats the size bound applies and the duration is the one the service reports; Deskmates does not decode compressed audio. The result carries the transcript, the detected language and the duration when the service reports them; absent values are said to be unknown, never invented.

7. **Results are untrusted data.** The tool result is wrapped as `<untrusted source="operation:look">` or `operation:asr`, entity-escaped like page text: OCR text and transcripts may carry injected instructions and converting modality never raises trust. The run's ledger keeps the raw tool result; the wrapper exists only in model context. The tools are L0 (read-only): they read a workspace file and send it to a service the installation operator configured.

8. **Every forwarded or refused call is recorded with its own unit.** An `operation_requests` row per call holds workspace, run, attempt, operation, mode, model, `endpoint_sha256`, status (`succeeded`, `failed`, `refused`), error code, unit (`image` or `page` for `look`, `audio_second` for `asr`), quantity (1 for an image or a page; seconds for audio, NULL when unknown), whether the quantity was `computed`, `provider`-reported or `unknown`, input bytes and SHA-256, input and output tokens when the service reports them, latency and `cost_usd`. `cost_usd` is `quantity × *_OPERATION_PRICE_USD` when the price is set (zero is a known zero, owner decision 9) and NULL when it is not, or when the quantity is unknown; never a guess. A refused call never reached the service and has no quantity. No input bytes, output text or credential is stored.

9. **Budget admission, but no budget charge yet.** A run whose workspace budget is exhausted (ADR-0032) is refused with `budget_exhausted` before the service is called; the run is parked by its next model call as before. Operation cost is not yet added to `budget_charges` or shown on the Costs page: the configured services are local and priced zero, and mixing units into those views needs the design's §8 work. This is a known gap for a priced service.

10. **No probes for these operations.** Neither operation is probed automatically or on page render (owner decision 15). The vision probe of the chat model (ADR-0023 amendments 1 and 2) is unchanged. Whether a service reads text correctly is measured only by a separately authorized evaluation.

11. **A run that withholds images is pointed at `look`.** When `image_describe` is offered, a withholding run's prompt section on images (ADR-0023 amendment 2, decision 12) adds that the tool reads images and scanned PDFs as text; the deny notice for an image `Read` and for a PDF `Read` names the tool and the path to pass. The tool works the same on every run; on a withholding run its answer is the only view of the image, as text from a separate service (design §13 D9, owner decision 9). A run whose model can see keeps the SDK `Read` of images and PDFs and is offered the tool as well.

## Alternatives considered

- **The sidecar builds the upstream body and the Gateway only swaps the credential**, as the model proxy does for the chat loop (design §4, principle 1). Rejected for these operations: it would let a run token buy free-form calls on the vision model with any prompt and any `max_tokens`, and the Gateway would have to validate an arbitrary Messages body instead of building a fixed one. The adapter is small and protocol-specific, and the Gateway still only forwards a call the sidecar asked for.
- **OCR through the chat model's own image input (design option E).** Unavailable exactly where it is needed: a withholding run's model cannot see.
- **A local OCR engine or speech model in the workspace image (option B).** Grows every workspace image and needs model weights there; the owner chose the tos-00 services.
- **An idempotency key per SDK tool-use id (design §7.3).** The in-process MCP tool handler in SDK 0.3.278 does not receive the tool-use id, so a replayed call after a resume buys a second operation. With no automatic retry and local zero-priced services this is accepted for now.
- **Per-workspace enablement and a service registry in the database (design §5.2, §6.1).** Deferred: the owner fixed credentials at installation level and there is one service per operation.

## Consequences

- A blind model can read screenshots it saved, photos, scanned PDFs and audio files as text; its answer depends on the vision and speech services' accuracy, which nothing in this ADR measures.
- Images, PDF pages and audio leave the workspace container for the configured service. On the stable deployment that is an internal host; an installation that configures an external provider sends workspace files there.
- Two new tools appear in the tool list of every run on an installation that configures the services, which is a framework change for behavioural fingerprints; installations without the variables are unchanged byte for byte.
- `operation_requests` grows by one row per call; the Costs page and budget do not see it yet (decision 9).
- Channel voice notes are not yet stored as workspace files, so `audio_transcribe` reaches them only once a channel or upload puts them in `/work`.
