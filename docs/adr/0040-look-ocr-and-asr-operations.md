# ADR-0040: Look/OCR and speech-to-text as bounded operations proxied by the Gateway

Date: 2026-10-14
Status: Accepted (in part; owner-decided 2026-10-14, owner decisions 8, 9 and 15): a look/OCR operation on a vision model, used by models that cannot see images, for images and scanned PDFs; ASR through whisper; `poppler-utils` in the workspace base image; endpoints and credentials at installation level only, in the Gateway's `.env`; no automatic retry or cross-destination fallback; no per-message selection; automatic probes for vision only (none for look/OCR or ASR); local services priced as known zero. The engineering choices that awaited owner review (the tool names and parameters, the Gateway-side adapter of decision 3, the size, page and duration bounds, offering the tools to every run of an installation that configures them in decision 2, and the text-layer threshold of decision 5) are Accepted under owner delegation (2026-10-17). Noted on acceptance: decision 2 changes the tool list of seeing runs on an installation that configures a service, so the stable host's first such release must compare behavioural fingerprints before and after (pending); OCR and speech accuracy remain unmeasured (decision 10). Decision 9's "no budget charge yet" is replaced by amendment A (owner-decided 2026-10-17: operation spend in `budget_charges` and on the Costs page, no estimate for an operation unit). Amendment B (2026-10-17) adds text-to-image as a third operation, `image_generation`, owner-decided in principle; its engineering choices are Accepted under owner delegation (2026-10-17), live verification against a real image service pending. Issue #115; design `docs/design/multimodal-models-2026-10-14.md` §7 option A.

## Context

The design for issue #115 found that Deskmates has one model surface, the agent's text loop, and no path at all for OCR or speech recognition (§3.7, gaps G5 to G7). ADR-0023 amendments 2 and 3 withhold images and PDFs from a run whose model cannot see: the model is told it cannot view them and must not guess. That removes confabulation but leaves a blind model with no way to read a screenshot, a scanned contract or a photo of a receipt. An audio file (an upload, a voice note) cannot be read by any run.

On 2026-10-14 the owner set up local services on the internal GPU host (on the LAN, reachable from the stable host, no authentication): a vision model `qwen3.5-9b-vl` behind an Anthropic `/v1/messages` route (port 8005) and faster-whisper behind an OpenAI-compatible `/v1/audio/transcriptions` route (port 8007). The owner approved a look/OCR tool on the vision model used automatically by blind models, and ASR through whisper.

The design compares five runtimes (§7.1) and recommends option A for provider-backed operations: a sidecar tool asks a Gateway operation proxy, which forwards to the configured service. Option C (the Gateway calls a model on its own) breaks the thin-core rule; option B (a local engine in the image) needs model weights in the image. The 2026-09-28 protocol check showed that one model can read an image over one route and not another (§3.5), so the route is configuration, not an assumption.

## Decision

1. **Two operations, sidecar-initiated, Gateway-proxied.** `look` (describe an image, or transcribe its text) and `asr` (speech to text) are the operations. A sidecar tool reads the input from the workspace and posts it to `POST /internal/runs/:runId/operations/look` or `/operations/asr`, authenticated by the run's token like every other internal route; another run's token is refused. The Gateway forwards exactly one request to the configured service and returns the text. The Gateway never starts an operation on its own, never fetches a URL a model wrote, and never retries: the proxy makes one upstream call per request, the sidecar tool makes one request per page or file, and the bot may call the tool again, which is a new recorded operation. No automatic fallback to another service exists (owner decision 15).

2. **Installation configuration only, and a tool exists only when its service is configured.** `VISION_OPERATION_URL` and `VISION_OPERATION_MODEL` turn on `look`; `ASR_OPERATION_URL` and `ASR_OPERATION_MODEL` turn on `asr`. Each pair is set together or not at all, and the Gateway refuses to start otherwise. Optional per service: `*_OPERATION_AUTH_TOKEN` (sent as `Authorization: Bearer`; kept in Gateway memory, never stored, never sent to a sandbox), `*_OPERATION_PRICE_USD` (decision 8). `VISION_OPERATION_PROTOCOL` is `anthropic-messages` (default) or `openai-chat`. The run config of every run carries `operations: { look?: { model, endpointSha256 }, asr?: { model, endpointSha256 } }` when a service is configured, and the run's sidecar is offered `image_describe` and `audio_transcribe` accordingly. No workspace or bot setting selects or disables a service in this version; the design's per-workspace enablement (§6.1) is not built.

3. **The Gateway holds the adapter; the sidecar sends a normalized request.** The sidecar sends `{ mode, question?, mediaType, data (base64), unit, source }` for `look` and `{ mediaType, data, fileName, language?, durationSeconds?, source }` for `asr`. The Gateway builds the one upstream body from a fixed template: for `look`, a single user turn with one image block and a fixed instruction per mode (`ocr`: transcribe all text exactly, keep reading order, say when there is none; `describe`: describe the image, answering the question when given), `max_tokens` 2048, temperature 0, no tools, no system prompt from the run; for `asr`, a multipart form with `file`, `model`, `response_format=verbose_json` and the optional `language`. A run token therefore buys one bounded operation, never a free-form call to the vision model; prompt text, page content or a file name cannot change the destination or the model.

4. **Inputs are checked before any spend, on both sides.** The sidecar resolves the path with `realpath` and accepts only a regular file under `/work/`, `/home/` or `/tmp/` (never `/profile`), refuses links that leave those roots, and sniffs the media type from the bytes: PNG, JPEG, GIF or WebP images up to 10 MiB, PDF up to 50 MiB; WAV, MP3, OGG, FLAC, WebM or MP4/M4A audio up to 25 MiB, which `ASR_OPERATION_MAX_BYTES` may lower. The Gateway decodes and re-sniffs the bytes, rechecks the sizes, the mode, a question of at most 2000 characters and a language of two or three lower-case letters, and refuses anything else with `validation` or `payload_too_large` without calling the service.

5. **PDFs: the text layer first, then one rendered page per call, bounded.** `image_describe` on a PDF reads its page count with `pdfinfo` and takes `pages` (for example `"1-3"` or `"2,5"`, default the first 5) up to 10 pages per call. In `ocr` mode each page is first read with `pdftotext -layout`; a page with at least 16 non-space characters returns its text layer with no model call, and a page with less is rendered with `pdftoppm -png -r 150` and sent to `look` as one `page`. In `describe` mode every requested page is rendered and sent. `poppler-utils` (`pdfinfo`, `pdftotext`, `pdftoppm`) is installed in the workspace base image (owner decision 8). The tool result labels each page as text layer or vision.

6. **Audio is bounded by size and, where the bytes say, by duration.** `audio_transcribe` computes the duration of a WAV file from its header and refuses one longer than `ASR_OPERATION_MAX_SECONDS` (default 1800) before any spend. For other formats the size bound applies and the duration is the one the service reports; Deskmates does not decode compressed audio. The result carries the transcript, the detected language and the duration when the service reports them; absent values are said to be unknown, never invented.

7. **Results are untrusted data.** The tool result is wrapped as `<untrusted source="operation:look">` or `operation:asr`, entity-escaped like page text: OCR text and transcripts may carry injected instructions and converting modality never raises trust. The run's ledger keeps the raw tool result; the wrapper exists only in model context. The tools are L0 (read-only): they read a workspace file and send it to a service the installation operator configured.

8. **Every forwarded or refused call is recorded with its own unit.** An `operation_requests` row per call holds workspace, run, attempt, operation, mode, model, `endpoint_sha256`, status (`succeeded`, `failed`, `refused`), error code, unit (`image` or `page` for `look`, `audio_second` for `asr`), quantity (1 for an image or a page; seconds for audio, NULL when unknown), whether the quantity was `computed`, `provider`-reported or `unknown`, input bytes and SHA-256, input and output tokens when the service reports them, latency and `cost_usd`. `cost_usd` is `quantity × *_OPERATION_PRICE_USD` when the price is set (zero is a known zero, owner decision 9) and NULL when it is not, or when the quantity is unknown; never a guess. A refused call never reached the service and has no quantity. No input bytes, output text or credential is stored.

9. **Budget admission, but no budget charge yet.** A run whose workspace budget is exhausted (ADR-0032) is refused with `budget_exhausted` before the service is called; the run is parked by its next model call as before. Operation cost is not yet added to `budget_charges` or shown on the Costs page: the configured services are local and priced zero, and mixing units into those views needs the design's §8 work. This is a known gap for a priced service. (Replaced by amendment A, decision 12: operation spend is now charged and shown.)

10. **No probes for these operations.** Neither operation is probed automatically or on page render (owner decision 15). The vision probe of the chat model (ADR-0023 amendments 1 and 2) is unchanged. Whether a service reads text correctly is measured only by a separately authorized evaluation.

11. **A run that withholds images is pointed at `look`.** When `image_describe` is offered, a withholding run's prompt section on images (ADR-0023 amendment 2, decision 12) adds that the tool reads images and scanned PDFs as text; the deny notice for an image `Read` and for a PDF `Read` names the tool and the path to pass. The tool works the same on every run; on a withholding run its answer is the only view of the image, as text from a separate service (design §13 D9, owner decision 9). A run whose model can see keeps the SDK `Read` of images and PDFs and is offered the tool as well.

## Alternatives considered

- **The sidecar builds the upstream body and the Gateway only swaps the credential**, as the model proxy does for the chat loop (design §4, principle 1). Rejected for these operations: it would let a run token buy free-form calls on the vision model with any prompt and any `max_tokens`, and the Gateway would have to validate an arbitrary Messages body instead of building a fixed one. The adapter is small and protocol-specific, and the Gateway still only forwards a call the sidecar asked for.
- **OCR through the chat model's own image input (design option E).** Unavailable exactly where it is needed: a withholding run's model cannot see.
- **A local OCR engine or speech model in the workspace image (option B).** Grows every workspace image and needs model weights there; the owner chose the GPU-host services.
- **An idempotency key per SDK tool-use id (design §7.3).** The in-process MCP tool handler in SDK 0.3.278 does not receive the tool-use id, so a replayed call after a resume buys a second operation. With no automatic retry and local zero-priced services this is accepted for now.
- **Per-workspace enablement and a service registry in the database (design §5.2, §6.1).** Deferred: the owner fixed credentials at installation level and there is one service per operation.

## Consequences

- A blind model can read screenshots it saved, photos, scanned PDFs and audio files as text; its answer depends on the vision and speech services' accuracy, which nothing in this ADR measures.
- Images, PDF pages and audio leave the workspace container for the configured service. On the stable deployment that is an internal host; an installation that configures an external provider sends workspace files there.
- Two new tools appear in the tool list of every run on an installation that configures the services, which is a framework change for behavioural fingerprints; installations without the variables are unchanged byte for byte.
- `operation_requests` grows by one row per call; since amendment A the budget and the Costs page read it.
- Channel voice notes are not yet stored as workspace files, so `audio_transcribe` reaches them only once a channel or upload puts them in `/work`.

## Amendment A (2026-10-17): operation spend in the budget and on the Costs page

Status: Owner-decided (2026-10-17, issue #6 owner rulings, "Operation costs: change ADR-0040 decision 9. All three together"). Replaces decision 9's "no budget charge yet"; admission (decision 9's first sentence) is unchanged. Design `docs/design/multimodal-models-2026-10-14.md` §8.4, §8.5 and D6.

### What changes

Decision 9 kept operation cost out of `budget_charges` and the Costs page because every configured service was local and priced zero. The owner ruled the three parts together: operation spend counts against the workspace budget, operations appear on the Costs page from the same receipts, and a unit with no compatible price has no estimate and shows as unpriced, as a model row does.

### Decision

12. **Operation spend is charged to the budget from `operation_requests`, the operation's receipt.** A run's spend (`runSpend`, ADR-0032 decision 3) adds every forwarded operation row of the run (status `succeeded` or `failed`; a `refused` row never reached the service and charges nothing): a row with `cost_usd` adds it to known USD; a row whose quantity is unknown (a failure, or a service that reported no duration) adds one to the unmeasured count; a row with a quantity but no configured price adds one to the unestimated count. The proxy charges the run right after it records each forwarded call, and the two existing charge moments (a model response's usage, the final usage) now include operations too, so the append-only difference rule is unchanged and one operation is never charged twice. Weekly spend and the cumulative ceiling therefore include operations, and admission (decision 9, ADR-0032 decision 5) refuses the next operation and the next model call of an exhausted workspace the same way. A row is priced once, when it is recorded (`cost_usd`, decision 8); a later price change re-prices nothing.

13. **No estimate for an operation unit (design D6).** The `avg-unit-price-v1` estimate (ADR-0032 decision 4, ADR-0039 decision 7) stays a token estimate: operation prices are never in its population, an operation row is never priced from token prices, and no average is taken across images, pages and audio seconds. An operation row without a price is unpriced and unestimated, and its quantity, when known, stays visible in its own unit.

14. **The Costs page reads the same rows.** The money fields of every Costs total (`knownCostUsd`, `usageCount`, `pricedUsageCount`, `unpricedUsageCount`, `unestimatedUsageCount`, and so `costStatus`) add the forwarded operation rows of the selected runs, with the same filters (the run's day, workspace and bot; a model filter matches the operation's model). The token fields never include an operation's tokens. Totals, the daily chart and the rankings by bot and by workspace therefore include operations; the ranking by model stays the chat models'; a new ranking `by=operation` (money only; one entry per operation and model, labelled `look · <model>`) lists them; Activity rows stay one token row per day, bot and model. An entry or total with no price and no estimate shows "Unpriced", the label model rows use, never zero. The usage view adds one tile per operation unit present in the range (images, PDF pages, audio minutes), each with its call count and how many calls had an unknown quantity; units are never summed with each other or with tokens. Cost alerts (ADR-0018) read the same totals, so their money and unpriced-usage rules see operations as well.

15. **Overshoot gains one term per operation in flight.** ADR-0032 decision 8 is extended: a call admitted under the limit completes and is charged even when it crosses it, so the bound adds, per operation in flight, its own maximum: one image or page at the vision price, or `ASR_OPERATION_MAX_SECONDS` at the audio price (the duration of a compressed file is known only from the service). An unpriced operation adds no measurable spend and is shown as unpriced coverage.

## Amendment B (2026-10-17): text-to-image as a third operation

Status: Owner-decided in principle (2026-10-17, issue #6 owner ruling: "Text-to-image: a local service, like look and asr: a third operation under ADR-0040 pointed at a self-hosted model on the installation's GPU host, configured in `.env`, priced as known zero"). The operation name, request shape, image location, tier and bounds below were this amendment's proposed engineering choices and are Accepted under owner delegation (2026-10-17): the fixed request template keeps a run token from buying a free-form call, `url` answers are never fetched, the images land in the bot's own directory by exclusive create, and L1 matches what the tool does (new files in the bot's own directory, a call to an operator-configured service). Implemented with T0/T1 tests against a fake upstream; no real image service was reachable, so live verification is pending on the stable host. Design `docs/design/multimodal-models-2026-10-14.md` §5.1 (`image_generation`), §7.2 to §7.5, D1, D2 and D7.

### Context

Look and asr turn workspace files into text. The owner wants the reverse for images: a bot asks a self-hosted text-to-image model on the installation's GPU host for a picture (a diagram sketch, an illustration, a mock-up) and gets a file it can use. Like the other two, it must not let a run token buy free-form calls, must not let a prompt choose the destination, and must leave the output where the bot's work belongs.

### Decision

16. **`image_generation` is a third operation, sidecar-initiated and Gateway-proxied like the other two.** The sidecar tool `image_generate` posts to `POST /internal/runs/:runId/operations/image_generation` with the run's token; another run's token is refused. Decision 1 applies unchanged: one upstream call per request, no retry, no fallback, the Gateway never starts a generation on its own and never fetches a URL.

17. **Installation configuration only, off unless configured.** `IMAGE_OPERATION_URL` and `IMAGE_OPERATION_MODEL` turn it on; they are set together or not at all, or the Gateway refuses to start. Optional: `IMAGE_OPERATION_AUTH_TOKEN` (Bearer, Gateway memory only, never sent to a sandbox), `IMAGE_OPERATION_PRICE_USD` (USD per generated image; empty is unpriced, `0` is a known zero, as decision 8 and ADR-0039 decision 5 require: no zero is inferred), and `IMAGE_OPERATION_DEFAULT_SIZE` (default `1024x1024`, within the size bounds of decision 19). The owner's ruling "priced as known zero" is met by `IMAGE_OPERATION_PRICE_USD=0` in the stable deployment's `.env`. When configured, every run's config carries `operations.image_generation: { model, endpointSha256 }` and the run's sidecar is offered `image_generate`; without it, runs are unchanged byte for byte. No model name is in `packages/`.

18. **The upstream protocol is the OpenAI-compatible `POST /v1/images/generations`.** It is the interface most self-hosted image servers implement; no particular server is verified here. A base URL gets `/v1/images/generations` appended; a URL already ending in it is kept. The Gateway builds the one body from a fixed template: `{ model, prompt, n, size, response_format: "b64_json" }`, with the configured model whatever the request says. It accepts only `data[].b64_json` items, with an optional `revised_prompt`; an answer whose items carry only a `url` is `answered_malformed` and the URL is never fetched. A run token therefore buys one bounded generation, never another endpoint or parameter.

19. **The request is bounded on both sides before any spend.** The sidecar sends `{ prompt, size?, count? }`. Prompt: 1 to 4000 characters. Size: `<width>x<height>`, each side 256 to 2048 and a multiple of 64 (the Gateway default when absent). Count: 1 to 4 images, default 1. The Gateway rechecks all three and refuses anything else with `validation` and no upstream call. Each returned image is decoded, must sniff as PNG, JPEG or WebP, and is at most 16 MiB; a malformed, oversize or unknown image fails the whole call as `answered_malformed` (recorded, decision 8). The Gateway reads the pixel size from the image header (PNG, JPEG, WebP) and returns `{ operationId, model, images: [{ mediaType, data, bytes, sha256, width, height }], revisedPrompt, usage }`; a size it cannot read is `null`, never guessed. Timeout: 300 s per call.

20. **The image lands in the bot's own directory.** The sidecar writes each image to `/work/bots/<bot>/images/<UTC time>-<operation id suffix>-<n>.<png|jpg|webp>` (ADR-0038 decision 1: a bot's work belongs in its own directory; the same path is used in shared mode). It creates the directory, refuses one that resolves outside the bot's directory (a link), and creates each file exclusively, so nothing is ever overwritten. The tool result lists each path with media type, pixel size, bytes and SHA-256. A generated image is an intermediate file in the workspace; it enters Files only through an explicit delivery (ADR-0014 amendment A4, ADR-0021 amendment 2).

21. **Tier L1, no approval.** `image_generate` writes new files only in the bot's own directory, which is a reversible workspace write, and sends model-written text to a service the installation operator configured, as `image_describe` sends files (decision 7). It is not an external side effect on the world, so the hook allows it as L1 in every approval mode. The workspace's egress allowlist does not apply: the destination is installation configuration that the Gateway reaches, the sandbox never sees its URL or token, and no prompt can change it.

22. **Budget and records as for the other operations.** Admission (decision 9) refuses an exhausted workspace before the service is called. A row in `operation_requests` records the call with operation `image_generation`, unit `image`, quantity = the number of images returned (`computed`), or unknown on a failure, input bytes and SHA-256 of the prompt text, latency and `cost_usd` = quantity × `IMAGE_OPERATION_PRICE_USD`. The call is charged and shown on Costs as amendment A says; the overshoot term of one call in flight is its count × price. The prompt text and the images are not stored by the Gateway.

23. **Output text is untrusted; the vision policy is untouched.** A `revised_prompt` the service returns is wrapped as `<untrusted source="operation:image_generation">` and entity-escaped. The tool result carries no image block, so a run's vision policy (ADR-0023 amendment 2) decides as for any image file: a run whose model can see may `Read` the file to check it; on a withholding run the `Read` is denied with the usual notice, and the tool result says the run cannot view the image and, when `image_describe` is offered, names it as the way to check the image as text. A successful generation says nothing about whether the image matches the prompt.

24. **No probe; quality unmeasured.** Like decision 10, nothing is probed automatically or on page render. Whether the configured model draws what is asked is measured only by a separately authorized evaluation.

### Alternatives considered (amendment B)

- **Return the image as an image block in the tool result.** Rejected: it would bypass the vision policy for withholding runs and put up to 64 MiB into the model context; a path is enough for a seeing run to `Read` it.
- **Let the Gateway write the file.** Rejected: the Gateway never writes into a workspace's filesystem on a run's behalf; the sidecar already runs as the bot inside the container.
- **Accept `url` answers and fetch them.** Rejected: the Gateway would fetch an address an upstream wrote (decision 1).
- **Price unset means zero for a local service.** Rejected: no zero is inferred (ADR-0039 decision 5); the stable `.env` states the zero explicitly.
- **L2 with approval.** Rejected: the effect is a new file in the bot's own directory and a call to an operator-configured local service, like `image_describe`.
