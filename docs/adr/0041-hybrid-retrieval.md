# ADR-0041: Hybrid retrieval for Knowledge and learned memory

Date: 2026-10-14
Status: Accepted for decisions 1, 3 to 9 and 11 (owner-decided 2026-10-14: hybrid Knowledge and memory search with bge-m3 and a reranker on the local GPU-host services, priced as known zero). Decision 2 (the Gateway calls embedding and rerank services itself) and the numeric defaults of decision 6 are proposed: engineering choices awaiting owner review. Decision 10 records what is not yet evidence.

## Context

Knowledge documents (tenant-wide, ADR-0011 decision 10, ADR-0022 P2) and learned memory (workspace-scoped, ADR-0011) are searched with SQLite FTS5 and `bm25`. Runs reach them through two tools: `knowledge_search` (top 5, `GET /internal/runs/:id/knowledge/search`) and `memory_search` (top 10, at most 20, `GET /internal/runs/:id/memory/search`); operators page the same rank in the Knowledge and memory screens. The pinned memory index of a run's first turn (decision 9) is not a query and is not touched here.

FTS5 finds words, not meaning. A run asking "how do we back up the database" misses a note that says "pg_dump runs nightly", and the `unicode61` tokenizer keeps a run of CJK characters as one token, which is why `memory_search` already falls back to a substring scan. AGENTS.md lists "Knowledge base search: FTS5 first (recommended) or database vectors from day one" as an open decision.

On 2026-10-14 the owner set up local model services on the GPU host (10.20.50.16, reachable from Testbox, no authentication) and approved hybrid Knowledge and memory search with bge-m3 and a reranker, priced as known zero (owner decisions, item 9). The services were probed once from the workstation on 2026-10-14 (no generation, no cost):

- ollama 0.x at `:11434`, model `BAAI/bge-m3:latest` (gguf F16, 566.7 M parameters, 1024 dimensions, 8192-token context). `POST /api/embed {model, input: string[]}` returns `{model, embeddings: number[][], total_duration, load_duration, prompt_eval_count}`; vectors come back L2-normalised.
- vLLM 0.8.5.post1 at `:8899`, served model `bge-reranker-v2-m3`. Its OpenAPI document lists `/rerank`, `/v1/rerank` and `/v2/rerank` with `RerankRequest {model?, query, documents: string[], top_n?, truncate_prompt_tokens?}`; a call returns `{id, model, usage: {total_tokens}, results: [{index, document: {text}, relevance_score}]}`, sorted by score.
- A probe of six short documents against four queries (English and Chinese) gave cosine 0.59 to 0.69 for the matching document, 0.50 to 0.54 for a related one and 0.33 to 0.42 for unrelated ones; a Chinese query found the English note at 0.59. One probe, not an evaluation.

AGENTS.md says of the control plane: "The Gateway does registration, scheduling, approvals, messaging, ledger, secrets, egress rules. It never calls a model." Model work (summaries, probes, generation) runs in the sidecar as an attributable run or job (ADR-0023 amendment 1). Embedding a text or scoring a (query, text) pair is a call to a model, so the boundary has to be decided before anything is built.

## Decisions

1. **Off unless configured; off is exactly today.** `EMBEDDING_URL` and `EMBEDDING_MODEL` enable vectors and are set together or not at all; `RERANK_URL` and `RERANK_MODEL` enable reranking and are set together or not at all. Either may be set without the other. Configuration lives only in `.env` (`config/retrieval.ts`); nothing in `packages/` names a model. With none of the four set, `knowledge_search`, `memory_search` and the operator search routes run the same FTS5 functions as before this ADR and return byte-identical results, no vector table is read and no background indexer runs.

2. **The Gateway calls embedding and rerank services directly; generation stays out (proposed).** The thin-control-plane rule exists so the Gateway never reasons: it never generates text, never follows instructions found in content, never holds a long-lived upstream model key, and never lets a model decide anything that gates an action. An embedding or rerank call does none of these. It returns numbers for given text; it cannot produce a tool call, a message or a decision; prompt-injected text can at most move its own rank, which `bm25` already allows. It is index maintenance, the same category as the FTS5 tokenizer, served by a separate process. Routing it through a sidecar job was rejected: Knowledge is tenant-wide and has no workspace container to run one in, a backfill would need a container per tenant, and every `memory_search` would pay a process start. The rule therefore reads: the Gateway never calls a generative model; it may call an embedding or rerank service configured in `.env` for retrieval, and nothing else. The retrieval client posts only to the two configured URLs, sends only the request shapes of decision 4, and reads only vectors, scores and usage counts. AGENTS.md is amended to say this. A service that needs a credential is out of scope until a release adds an installation-level secret for it (owner decisions, item 15).

3. **Vectors live in SQLite next to the rows they describe.** `knowledge_chunk_vectors (document_id, model, chunk, tenant_id, dimensions, vector, created_at)` and `memory_chunk_vectors (entry_id, model, chunk, workspace_id, dimensions, vector, created_at)` hold one L2-normalised little-endian float32 BLOB per chunk (`length(vector) = dimensions * 4`), keyed by source, model id and chunk number. They inherit the source's scope: Knowledge vectors carry the tenant and are read only under it; memory vectors carry `workspace_id NOT NULL` with `ON DELETE CASCADE` (ADR-0031 decision 6) and are read only under the run's workspace (ADR-0011 decision 10). No chunk text is stored: chunking is deterministic, so a chunk's text is recomputed from the current body when it is needed. A vector never outlives the text it came from: SQLite triggers delete a document's vectors when its title or body changes and an entry's vectors when its body changes or it is tombstoned, in the same statement, so a forgotten note leaves no embedding behind. Vectors of another model id are never read and are deleted by the indexer.

4. **Chunking and indexing.** A body is split on blank lines and its paragraphs are packed into chunks of at most 1,200 characters (code points); a paragraph longer than that becomes windows of 1,200 characters, consecutive windows sharing 200; a Knowledge chunk is embedded with the document title on its first line. Eligible sources are published Knowledge documents and memory entries that are not tombstoned and not distilled into an episode. A background indexer in the Gateway process finds eligible sources that have no vector for the configured model (one indexed query per corpus), embeds them in batches of at most 16 inputs per request, one tenant or workspace per batch, and writes the vectors of one source in one transaction only if the source still has the body that was embedded. It runs at Gateway start (the backfill), when a Knowledge document is published or edited, and every 30 seconds; a request times out after 30 seconds and a failure ends the pass, retried on the next one. Writes never wait for embedding: a source without vectors is still found by `bm25`. The embedding request is ollama's `POST /api/embed {model, input, truncate: true}` or, when the URL path ends in `/v1/embeddings`, the OpenAI shape `{model, input}` reading `data[].embedding` and `usage.prompt_tokens`.

5. **A query fuses bm25 and vector ranks, then reranks the head.** For one search the Gateway: (a) takes the FTS5 candidates exactly as today's query ranks them (`bm25`, then id; the memory CJK substring fallback included), at most 50; (b) embeds the query (timeout 5 s) and scores every vector of the scope by dot product, brute force, keeping each source's best chunk, dropping sources under the similarity floor and keeping the best 50; (c) fuses the two lists by reciprocal rank fusion, `score = Σ 1 / (60 + rank)`, ties broken by id; (d) when reranking is configured, sends the query and the text of the first 20 fused candidates (the entry body; for Knowledge the title and the best chunk, or the first chunk) to `POST {RERANK_URL} {model, query, documents, top_n}` (timeout 5 s) and orders those 20 by `relevance_score`, ties by fused order, followed by the remaining fused candidates. Every filter of the FTS5 path applies to the vector path in the same SQL (tenant and published state for Knowledge; workspace, scope, liveness, TTL, supersession and episode for memory), so the hybrid result is a reordering and widening of what the run may read, never a wider audience. Results keep their existing shapes (`KnowledgeHit`, `MemorySearchHit`); the run tool limits (5 and 10/20) and the operator page sizes are unchanged, and operator pages slice the fused list (at most 100 sources) with its length as the total.

6. **Defaults (proposed).** Candidates per list 50, RRF constant 60, rerank head 20, similarity floor 0.45 (between the related and unrelated bands of the probe), chunk 1,200 characters with 200 overlap, batch 16, poll 30 s. All are read from `.env` (`RETRIEVAL_CANDIDATES`, `RETRIEVAL_RRF_K`, `RERANK_TOP_N`, `RETRIEVAL_MIN_SIMILARITY`) except chunking, which is a versioned constant because changing it means re-embedding. They are guesses to be calibrated by decision 10.

7. **Degradation is visible and never fails a search.** If the query embedding fails or times out, the search returns the FTS5 result unchanged; if the rerank fails, it returns the fused order. Each failure is recorded as a call row with outcome `error` or `timeout` (decision 8) and logged once; no search returns an error because a retrieval service is down.

8. **Usage is recorded per call.** Every embedding or rerank request writes one `retrieval_calls` row: tenant, run (when a run's tool asked; `ON DELETE SET NULL`), corpus, purpose (`index` or `query`), service (`embedding` or `rerank`), model, number of inputs, input tokens (`prompt_eval_count`, `usage.prompt_tokens` or `usage.total_tokens`; `NULL` when the service reports none, which is unknown, not zero), duration and outcome. The local services are priced as known zero (owner decisions, item 9), so no cost is computed; a priced service would need a price row first.

9. **A run records the retrieval it used.** When any of the four variables is set, `runs.config_json` carries `retrieval: {version: 1, embeddingModel, rerankModel, candidates, rrfK, rerankTopN, minSimilarity, chunkCharacters, chunkOverlap}` (absent members not configured). When none is set the key is absent, so earlier and unconfigured run rows stay comparable.

10. **This is a strategy change and is not yet better.** `memory_search` and `knowledge_search` decide what a run reads, so hybrid retrieval is a retrieval-parameter change (AGENTS.md conventions; measurement design). It stays behind configuration and off by default. It is not called better until `evals/compare.ts` shows it on a paired run against the FTS5 baseline, per duration bucket, one knob at a time (vectors, then rerank). No such evaluation has run.

11. **Scale: brute force, measured, with a stated limit.** Scoring is a dot product over every vector of one tenant or workspace in the Gateway's event loop. On an Apple M1 Pro shared with other work, reading float32 BLOBs from SQLite and scoring 1024-dimension vectors took 4.8 ms per query at 1,000 chunks, 40 ms at 10,000 and 168 ms at 50,000 (3.9, 39 and 195 MiB of vectors read per query). At 10,000 chunks per scope this is acceptable; beyond about 20,000 an approximate index (sqlite-vec or similar) or a worker thread is needed and will be its own decision. The `retrieval_calls` table and the chunk count per scope are the signals to watch.

## Alternatives considered

- **FTS5 only.** Kept as the default and as one input of the fusion, but it cannot match meaning or cross-lingual queries, and CJK needs a substring fallback.
- **Vectors only.** Rejected: dense retrieval misses exact identifiers, error codes and names that `bm25` finds; fusion keeps both.
- **Embedding and rerank as sidecar jobs.** Rejected in decision 2: no container for tenant-wide Knowledge, a process start per query, and nothing about a scoring call needs the sidecar's isolation.
- **sqlite-vec or another ANN extension now.** Rejected for now: a native extension in the Gateway image for a scale this deployment does not have (decision 11).
- **Storing chunk text.** Rejected: it would be a second copy of memory that forget and redaction would also have to erase.
- **Score blending instead of RRF.** Rejected: `bm25` and cosine are on unrelated scales; reciprocal rank fusion needs no calibration between them.

## Consequences

- A configured Gateway makes outbound HTTP calls to two local services; an outage degrades search to FTS5 and is visible in `retrieval_calls`.
- The database grows by about 4 KiB per chunk at 1024 dimensions.
- Changing the embedding model re-embeds everything in the background; until done, search falls back to `bm25` for unindexed sources.
- The open decision "Knowledge base search" in AGENTS.md is resolved: FTS5 stays the default and the always-present lexical half; vectors are added when configured.
