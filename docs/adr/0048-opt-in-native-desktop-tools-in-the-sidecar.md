# ADR-0048: Native desktop tools (LCU) registered by the sidecar, allowed without per-call approval

Date: 2026-10-17
Status: Accepted for decisions 1 to 11 and 13 (owner rulings of 2026-10-17 on issue deskmates-private#7: rulings 1, 2, 4, 5, 7 and 8, and the engineering decisions that carry them; decision 1 rewritten by the owner's follow-up answer of the same day, which turns the tools on by default on a capable image; decision 4's path accepted under owner delegation of the same day, "你来处理"); Proposed for decision 12 (redistribution, ruling 6: undecided, build locally only, never publish). Amendment 1 (2026-10-17) records the follow-up answers: A1, A2, A4 and A5 are Accepted; A3 (concurrent desktop work on the shared screen) was accepted by the owner on 2026-10-18, as recorded in the amendment status below. The settings, the sidecar registration, the hook rules, the proxy, the shared-screen lease, the denial record, the X input record, the workspace-page warning, the image variant's Dockerfile and measurement script and the T2 checks are implemented; all ten scripted T2 cases and the image-size/startup/memory measurement passed on Linux on 2026-10-19 (docs/design/desktop-integration-live-acceptance-2026-10-19.md). The real-model visual task and paired strategy evaluation remain pending; redistribution remains local-only.
Builds on: ADR-0002 (the sidecar is the SDK host; `PreToolUse` gate; amendment 5 code-effect labels; amendment 6 approval modes), ADR-0004 (one shared workspace, no bot-level access control), ADR-0008 (shared desktop, bot screen regions, workspace-wide human takeover), ADR-0010 and ADR-0020 (egress and the default grouping rule), ADR-0023 amendment 2 (vision withholding), ADR-0029 (restart recovery), ADR-0040 (the installation's local vision service)

## Context

Deskmates has governed Playwright browser tools and no first-class native desktop tools. LCU (`amontlabs/lcu`, MIT) exposes an installed upstream desktop application's computer-use runtime through MCP: window discovery, accessibility-based interaction, keyboard input and screenshots. Its model-visible inventory is two tools, `js` (run JavaScript in the runtime's kernel, which calls the runtime's desktop actions) and `js_reset`; it also has host-only tools (`turn_ended`, `js_add_node_module_dir`) that a host must not show the model.

The owner asked for a bounded spike on 2026-10-13, run on the stable host (Gateway v0.6.4, Linux x86_64, Ubuntu 24.04, the existing Xvfb/Fluxbox/noVNC desktop) in a new, dedicated test workspace and container; the stable Gateway, shared images and other workspaces were not changed. Pinned inputs: LCU 0.11.3, runtime-only install; the upstream Linux application 26.915.31945 with its computer-use component 0.0.16, checksum-pinned (a historical tested input, not the latest). Passed, with independent oracles: MCP initialisation and the `js`/`js_reset` inventory; exact window discovery and binding with GTK 3 AT-SPI state; element clicks, Ctrl+A and English, Chinese and emoji input; a Save button, the final `Saved` GUI state and real JPEG screenshot content; an exact byte oracle on the saved file (36 UTF-8 bytes, hash matched); `js_reset` followed by fresh window binding with the GUI content retained; host turn cleanup and client shutdown. One real run then executed the reviewed script once through `Bash` (classified L1 by the existing hook) and read its report with `Read` (L0): succeeded in 3 model turns, about 9.2 s, 2,375 input, 519 output and 48,128 cache-read tokens; cost unknown because the Gateway recorded `pricing_missing` (unknown, not zero).

What the spike shows: SDK, shell, a reviewed fixed script, the LCU MCP client and a native application work together in a workspace container. What it does not show: sidecar tool registration, model-driven visual planning (the model's vision capability was `unsupported`, and no screenshot reached it), human takeover, concurrent bot input, Chrome-extension use or audio.

Measured installed (uncompressed rootfs) sizes in the test container: LCU 39.3 MiB; the complete upstream application 1.32 GiB; nineteen added desktop and fixture packages about 4.8 MiB; removable apt indexes 52.3 MiB; original workspace image 3.13 GiB; the container's writable layer 1.39 GiB, so base plus layer 4.53 GiB, about +44.5%. The application's compressed package is about 417 MB and LCU's archive about 5.9 MB; neither establishes compressed layer growth. The computer-use node alone is 207.3 MiB but is not a standalone runtime: LCU consumes other application components and validates the application's structure, and a stripped runtime was neither assembled nor verified. The cost is the upstream application, not LCU.

Constraints this ADR answers: `run-once.ts` passes `settingSources: []` and builds its own `mcpServers`, so a user's Claude Code registration never reaches a run; arbitrary JavaScript can contain several GUI actions, so a call-level label says nothing certain about nested actions; native input moves the shared focus and pointer that browser tools and human takeover also use; the LCU REPL's variables and window bindings do not survive a process restart; UI text is untrusted; the container could not give LCU's inner sandbox (bubblewrap) a user namespace, so its kernel has the container account's filesystem, process and network access; the spike's install lives in a writable layer that container recreation discards; the upstream application's terms are not LCU's.

### Owner rulings of 2026-10-17

The Proposed draft of this ADR asked eight questions on issue #7. The owner answered them the same day: (1) opt-in as proposed; (2) **no per-call approvals for desktop tools**: the desktop runs in a disposable VM and gates there block the automation the feature exists for, so desktop `js` calls are allowed like L1, the effect classification is still computed and recorded on the `tool_call` event, and the ADR-0020 hard denies still apply to any network the code reaches; (3) the nested-action fence: research LCU first and propose one path with evidence, the ADR staying Proposed on that point; with ruling 2 the fence matters for attribution and the hard denies, not for approvals; (4) share the workspace browser lock and takeover epoch; (5) the optional `images/workspace-desktop` variant, accepted with the named measurements; (6) redistribution undecided: build locally only, never publish; (7) a desktop workspace that holds a signed-in account may also browse untrusted sites, as an explicit exception to the ADR-0010/ADR-0020 grouping rule limited to workspaces with desktop tools enabled, shown on the workspace page; (8) an image-capable model task is authorised at zero cost on the installation's local vision service (ADR-0040), with independent oracles and full token accounting, no paid model.

### What LCU exposes, researched 2026-10-17 (for decision 4)

Read from the LCU repository's README, `AGENTS.md`, `docs/ADAPTERS.md`, `docs/PARITY-STATUS.md`, `adapters/claude.mjs`, `bin/lcu-codex-sandbox` and `lcu/sandbox_shim.mjs` on its default branch, fetched on 2026-10-17. The repository's file tree could not be listed through the GitHub API from the development environment; individual files were read over HTTPS. Nothing below was run.

- **LCU executes nothing itself.** "LCU does not implement browser control, screenshots, accessibility, input, or JavaScript execution": the installed application's original computer-use MCP server handles instructions, execution, elicitation, policy and lifecycle. LCU's own development rule is not to add "another accessibility, input, screenshot, browser, JavaScript, or MCP implementation". An LCU-side per-action hook would contradict LCU's design.
- **Per-call traffic only.** The relays forward each `js` call as one opaque request and return the upstream content and `isError` unchanged. They register no progress or notification handlers; the only per-action traffic they see is MCP elicitation (approval prompts). Their diagnostic logs are metadata only (timing, outcome, approval kind) and never record arguments or results.
- **No per-app gate on Linux.** On macOS and Windows the original runtime asks per application by elicitation; "the original Linux runtime does not ask", so on Linux the harness's gate on `js` is the only gate before desktop control.
- **The sandbox shim decides once per process.** `lcu-codex-sandbox` is set as the runtime's `CODEX_CLI_PATH`; it classifies each sandbox launch by argv (kernel inside the sandbox, the positively identified trusted worker outside, anything else refused) and then `execve`s. It has no visibility into the messages the kernel sends the worker, so it cannot see individual actions either. Where bubblewrap has no user namespace (the spike's container), the kernel is not sandboxed at all.
- **Host identity and cleanup.** A host passes real session and turn ids in the call's metadata; the Claude relay binds them at `PreToolUse` and forwards them under `x-codex-turn-metadata`; `turn_ended` (`Stop`, `Interrupt`, `SubagentStop`) closes a turn; `js_reset` must be preceded by `turn_ended` for every turn that ran `js` on the worker.

## Decision

1. **Native desktop tools are on by default on an image that declares them** (rewritten 2026-10-17 by the owner's follow-up answer "默认开启"; the earlier ruling "opt-in and off by default" is superseded; amendment 1, A1). On a workspace image that declares the capability `desktop-lcu-v1` (decision 11), every workspace and every bot in it has the tools unless a workspace Owner or Admin turns them off, for the workspace or for one bot. On any other image they cannot work, stay off, and cannot be turned on. When the Gateway cannot read the image's labels it treats the tools as off for a workspace that has no explicit setting (fail closed). The Gateway freezes `desktopTools` (`off` or `lcu-v1`) and the LCU and application versions the image declares into `runs.config_json` when attempt 1 starts and keeps them on every later attempt, whatever the setting or the image says later. The default image, and so a default deployment, does not change. A bot on a capable image does change: it gains two tools and the routing guidance of A2. That is a strategy change (AGENTS.md): it is not "better" until `evals/compare.ts` says so on a paired run, that evaluation is pending, and nothing here claims it is better.

2. **No per-call approvals for desktop tools.** The hook allows `mcp__desktop__js` and `mcp__desktop__js_reset` without asking anyone, at L1, under every approval mode; no stored rule, reviewer or human is consulted and no desktop approval card exists. The effect labels of each `js` body are still computed (a keyword scan that compiles and never executes, beside `browser-code-effects.ts`): `read` (window listing, accessibility reads), `capture` (screenshots), `input` (clicks, typing, key presses), `input <phrase>` (an input whose code names one of the browser's side-effect phrases such as send, submit, delete, pay), `launch` (starting or killing a process or application), `file` (filesystem writes from the kernel), `network`, `clipboard` and `opaque` (missing, non-compiling or obfuscated code). They are recorded as `desktopEffects`, with any literal network targets as `desktopTargets`, on the call's `tool_call` ledger event, so the run drawer and the observability sinks (ADR-0046) show what a call may have done. The labels decide no tier. The ADR-0020 hard denies still apply to every network target the hook can read in the code: a literal URL or host that is a private address, an IP literal, `localhost`, the reserved host alias or unreadable is denied before the call runs, unless a root-selected network profile grants that exact origin (ADR-0027 amendment 1); in a locked workspace a literal public host outside the allowlist is denied too, never asked, since a desktop call never waits for a human (owner-accepted 2026-10-17, "但是要记录": every such denial is recorded, A4). Targets the code computes at run time are not readable here; the managed egress proxy, the only route out of a workspace network in a B4 deployment, applies the same denies to the addresses they resolve to.

3. **The sidecar registers LCU explicitly; nothing else does.** When the start request carries `desktopTools: "lcu-v1"` and the sidecar's environment declares the image capability `desktop-lcu-v1`, `run-once.ts` adds one stdio MCP server, `desktop`, to the `mcpServers` it already builds; `settingSources` stays `[]`. A request for the tools on an image without the capability starts the run without them and logs `desktop`/`capability_missing`. The server command is the sidecar's own proxy (`deskmates-sidecar desktop-proxy`), which starts the LCU binary named by the image (`DESKMATES_DESKTOP_LCU_COMMAND` and `DESKMATES_DESKTOP_LCU_ARGS`) and sits between it and the SDK, as `mcp-proxy` does for the browser. The binary path and arguments are image facts, not bot, workspace or model input. The model sees `mcp__desktop__js` and `mcp__desktop__js_reset` only: the proxy removes LCU's host-only tools from `tools/list` and refuses a model call to one. Running LCU from the shell is not this integration and is refused: the hook denies a `Bash` line, or a one-line `tty_session` write, whose command is the LCU binary (basename `lcu` or a path under `/opt/lcu/`), telling the bot to use `mcp__desktop__js` when the run has the tools and that they are off otherwise. That keeps the lock, takeover, wrapping and ledger labels on one path. It reads the literal line only, so a script can still reach the binary indirectly; it is a guard rail.

4. **Nested-action fence (Accepted under owner delegation, 2026-10-17): declared effects by scan, real network denies at the egress proxy, observed input by an X event record.** Decision 2's scan labels what a call's code names; it cannot prove what the runtime executed (names can be computed, strings decoded, loops depend on GUI state). With ruling 2 a fence is needed for attribution and the hard denies, not for approvals. The options, researched in Context:

   | Option | Can fence | Cannot fence | Cost |
   |---|---|---|---|
   | A. Code scan in the hook (implemented) | the effects and literal URLs the code names, before it runs | computed names, decoded strings, data-dependent loops, anything the runtime does internally; no binding between scanned and executed actions | low: about 150 lines like `browser-code-effects.ts`; no added latency beyond compiling the text |
   | B. Upstream per-action hook | everything, if it existed | not available: LCU executes nothing itself and forbids adding an implementation; its relays see one opaque request per call; the Linux runtime sends no per-action elicitation; the sandbox shim sees process launches only | outside both this project's and LCU's control: a change to the upstream application's runtime, unbounded wait |
   | C. Structured tool surface in `desktop-proxy` (`list_windows`, `click`, `type`, `key`, `screenshot`, each a fixed JS template sent to the upstream `js` with JSON-encoded arguments) | exactly one action per call by construction; arguments are data, never code; no URL-taking tool at all | what the one action causes inside the application (a click on Send sends); it diverges from the upstream instructions, which describe the `js` API and remain the application's terms | medium: five templates against an unversioned, undocumented upstream API, revalidated per pinned application version; more turns and tokens per task (multi-step scripts become several calls), unmeasured |
   | D. Observed effects (proposed with A) | network: every packet the kernel sends goes through the managed egress proxy, which already applies the hard denies to resolved addresses (B4: the workspace network is `Internal`); input: the X input events the display receives between a call's dispatch and its result, attributable to that call because decision 6 serialises desktop calls, browser calls and human takeover under one lock | prevention of input (it records, it does not refuse); attribution while a script outside the lock (a bot's own shell) types at the same time | low to medium: an X event recorder in the image variant (the RECORD extension of the existing Xvfb, read by a small helper) and a `desktop_call` log event with event counts; one T2 row |

   Path: **A plus D** (accepted 2026-10-17 under owner delegation, "你来处理"). Keep raw `js` as upstream instructs, record the scan's labels as declared effects (decision 2), rely on the managed egress proxy for the network hard denies of computed targets (existing), and add the X input record as observed effects (A5: built from the display's XInput2 raw events rather than the RECORD extension, since a packaged reader exists). B is not available and is not LCU's design; C costs a second API surface that drifts from the application's own and gives up multi-step scripts, and is kept as the fallback if D's input record proves unattributable in the T2 contention check. Neither the scan nor the record is a security boundary, and no document or UI presents either as one.

5. **Deny, cancel and restart are per call and never replay effects.** A hard deny (decision 2) or the shell refusal (decision 3) returns its reason as the tool's result and nothing runs. Stopping the run, a takeover (decision 6) or the run deadline cancels an in-flight `js` call: the proxy sends MCP cancellation to LCU, then terminates the LCU process if the call has not returned within a short grace period, and answers the call with an error result starting `desktop_call_interrupted`; the run records a `desktop`/`call_interrupted` log with effects unknown, and the call is never retried automatically. There is no defer: with decision 2 no desktop call waits for a human. A call whose `tool_call` event has no `tool_result` after a restart follows ADR-0029 decision 5 and is not replayed; its effects are unknown.

6. **Desktop input shares the workspace's browser lock and takeover epoch** (the lock sentences are replaced by amendment 1, A3, which keeps the takeover and epoch rules below unchanged). Every desktop call acquires the same workspace-level lock the browser tools acquire in the hook (ADR-0008 decision 4). While a human holds the workspace, desktop calls get the same wait message and nothing is dispatched, so no input is sent and no capture is taken. The proxy acquires the lock again at dispatch, keeps the takeover epoch it was granted, and renews the lock while the call runs; a renewal that is refused or reports another epoch cancels the call as in decision 5, so no input arrives after control changes hands. Screen regions remain routing conventions: X11 input and focus are shared, and nothing here isolates bots from each other. The cost is that desktop and browser work serialise across the workspace; lock wait time is measured.

7. **One LCU process per run, rediscovered after any restart.** The proxy starts LCU when the SDK connects and passes the upstream initialisation instructions, tool descriptors, image blocks and `isError` results through unchanged, apart from decision 8's wrapping and the host-only filter of decision 3. It identifies the host session by run id and attempt and the turn by tool-use id, never by a fixed or shared value, and the cleanup (`turn_ended` with `Stop`, then the process kill) is the proxy's, never the model's. A resumed run, or a call after the proxy restarted LCU, gets a harness notice on its next result to rediscover windows; nothing assumes REPL variables, window handles or a previous `js_reset` survived.

8. **UI content is untrusted and keeps its type.** Text from the desktop (accessibility names and values, window titles, error text) is wrapped in the same entity-escaped untrusted wrapper the browser proxy uses (`<untrusted source="desktop:lcu">`) before it enters model context; the ledger's redactor runs over the recorded result as for every tool. Image blocks pass through with their original media type, under the vision withholding of ADR-0023 amendment 2: a model that cannot see gets the notice, not the image. Binary content is never converted to text to fit a wrapper.

9. **No new privilege, and no inner-sandbox claim.** The workspace container gains no capability, user-namespace permission or device for LCU. LCU's kernel runs as the container account with that account's file, process and network access; its outbound traffic goes through the workspace's managed egress proxy like any other process. If a future image makes the inner sandbox work, it is recorded as defence in depth, not as a boundary between bots or between a bot and the workspace (ADR-0004).

10. **Exception to the default grouping rule, limited to desktop workspaces.** A workspace with desktop tools enabled may hold a signed-in account in the upstream application, or in any application on its desktop, and also browse untrusted sites, including the open internet. This is an owner-accepted exception to the ADR-0010/ADR-0020 rule that an untrusted-browsing workspace holds no production credentials; it applies to no other workspace, it lapses when the desktop tools are turned off, and it is a risk accepted, not a mitigation: a bot hijacked by page content can use that signed-in account. The workspace page shows the exception, in every locale, whenever the desktop tools are enabled. Since decision 1 now turns the tools on by default on a capable image, the exception applies to every workspace on a capable image unless its tools are turned off; the warning shows whether they are on by default or by choice.

11. **LCU ships only in an optional image variant, accepted on measured cost.** `images/workspace-desktop` is built `FROM` the content-addressed workspace image and adds the pinned LCU release and the pinned upstream application by version and checksum from local inputs, with no apt indexes and no fixture-only packages, and nothing downloaded at run time. Its tag is `deskmates/workspace-desktop:<arch>-<hash12>`, hashing the base image id, the variant's directory and the pins. Its label `org.deskmates.capabilities` and environment `DESKMATES_IMAGE_CAPABILITIES` declare `desktop-lcu-v1`; the Gateway reads the label before decision 1 can be enabled and the sidecar reads the environment before it registers the server. The default workspace image is unchanged. Before acceptance in use the variant's clean uncompressed and compressed growth over the base, container start time and idle and active memory are measured with `scripts/measure-workspace-desktop.sh` and recorded under `docs/design/`; the spike's +1.4 GiB writable layer is the historical estimate, not the measurement. A reduced upstream payload is allowed only after installation, the original MCP instructions and results, native actions, `js_reset` and cleanup pass against the exact pinned application and runtime.

12. **Redistribution is an open gate (Proposed).** LCU is MIT. The upstream application, its runtime and its instructions keep their own terms. Until those terms are read and the owner accepts them, the variant is built only on an operator's host for that operator's use, by `scripts/build-workspace-desktop-image.sh`, and is not built or published by the release workflow, the stable scripts or any registry push. Publishing it needs this gate recorded as passed.

13. **Visual planning is a separate acceptance, at zero cost.** Decisions 1 to 11 make the tools available and attributed; they say nothing about whether a model can plan from screenshots. That needs the separately scoped task prepared under `evals/desktop/`, run on the installation's local vision service (ADR-0040) at zero model cost, with independent outcome oracles that read the fixture's saved file and window state outside the model, and full token accounting with the zero price recorded explicitly so cost is not `unknown`, under the measurement protocol. No paid model is used. Until it has run, no claim is made about planning from screenshots.

## Alternatives considered

- **Keep the spike's shape: the model runs a reviewed script through `Bash`.** Already works, but the hook sees one L1 shell call and no desktop action at all, the call skips the lock and takeover, and the script must be written by a person. Not a product path; decision 3 refuses it.
- **Per-call effect tiering with L2 approvals and allow-once-only cards.** The Proposed draft's decision 3. Rejected by the owner (ruling 2): the desktop is disposable and per-call gates block the automation the feature exists for.
- **Let a user's Claude Code MCP registration enable LCU.** Contradicts `settingSources: []` and would put a run's tool surface in files the Gateway does not record. Rejected.
- **Expose only structured desktop tools and hide `js`.** Option C of decision 4: kept as the fallback.
- **Install LCU into the default workspace image.** About +44% on every workspace for a feature most will not use, plus an unresolved redistribution question. Rejected for decision 11.
- **A separate desktop lock.** Native input and browser input share one X display, focus and pointer; two locks would let them interleave. Rejected for decision 6.

## Consequences

- `contracts`: `desktop-tools.ts` (the mode, the capability names, the settings view and input, the effect labels); `desktopTools` on `StartRunRequest`; an optional `imageLabels` on `SandboxProvider`.
- `packages/gateway`: `workspace_desktop_tools` and `bot_desktop_tools` tables (an explicit on or off; no row is the default of decision 1), `GET`/`PUT /api/workspaces/:id/desktop-tools` (read by a Member, set by an Owner or Admin), the image capability check and its cached image facts, freezing the knob into `runs.config_json`, the shared-screen lease (A3) and the denial audit row (A4).
- `packages/sidecar`: the `desktop-proxy` subcommand, `desktop/desktop-code-effects.ts`, the hook's desktop rules (hard denies, lock, shell refusal, the recorded denial), the `desktopEffects` on `tool_call`, the server registration, the routing guidance (A2), the lease mode per call (A3) and the X input record (A5).
- `packages/web`: a Desktop tools section on the workspace page with the grouping-exception warning; the denial in the run story, the technical log and the Activity card (A4).
- `images/workspace-desktop` and its build and measurement scripts; not in the release workflow while decision 12 is open.
- AGENTS.md's grouping bullet names decision 10's exception.
- Unchanged: one Chromium and profile per workspace, ADR-0008's regions and takeover, the browser tools' tiers and approvals. Chrome-extension integration is evaluated separately after native desktop tools work.

## Amendment 1 (2026-10-17): on by default, choosing the tool, concurrent work on the shared screen, recorded denials, the input record

Status: A1 to A5 Accepted (the owner's follow-up answers of 2026-10-17, given in chat to the coordinating session: "默认开启"; "要考虑在agent怎么决定走那条"; deny-not-ask "但是要记录"; the fence "你来处理"). A3 was signed by the owner on 2026-10-18 ("可以"), after it was researched and implemented by the implementing session in answer to "是否能做到不同agent共享一个linux窗口的不同部分时能够并发"; which upstream methods are truly focus-free is still to be confirmed with the input record on the pinned runtime. Decisions 1, 4 and 6 above are edited in place where this amendment says so; the other decisions stand.

Found while answering: the workspace browser lock (version 1, `workspaces/browser-lock.ts`) is exclusive only for a human holder. Between runs it guards one tab, and a request without a tab id does not contend with other runs at all. The desktop proxy acquired it without a tab id, so two bots' desktop calls never excluded each other, and decision 6's "desktop and browser work serialise across the workspace" described more than the code did. A3 replaces those sentences with what the code now does.

The X11 facts A3 rests on: Xvfb has one seat, so one core pointer and one keyboard focus for the whole display; pointer and keyboard events synthesised through XTEST (`xdotool`, the runtime's key presses, x11vnc's input) go to the pointer position and the focused window, so two bots' raw input interleaves into each other's windows. AT-SPI calls (reading the accessibility tree, an element's `do_action`, `set_text_contents`, `insert_text`, `set_current_value`) are D-Bus requests to the application's accessibility objects: they neither move the pointer nor need the focus. A screenshot reads the frame buffer. Playwright drives Chromium through CDP (`Input.dispatch*`), which touches neither the X pointer nor the X focus. What does change the focus is a window appearing: an application opening a dialog, or a browser call opening its top-level window under `shared-monitors-v1` (ADR-0008); the window manager focuses a new window. LCU's runtime interacts with elements through AT-SPI (the spike's GTK 3 AT-SPI binding), but its `js` API is the installed application's, unversioned, and which of its methods synthesise pointer or key input was not established; the spike's Ctrl+A was key input.

A1. **On by default on an image that declares the capability** (replaces decision 1, which is rewritten above). The stored settings are explicit choices: a workspace row says on or off, a bot row says on or off, and no row is the default. Effective for a run: off when the workspace is set off, when the bot is set off, or when the image does not declare `desktop-lcu-v1`; otherwise `lcu-v1`. The Gateway reads the image's labels at start-up (bounded, so a daemon that does not answer cannot hold the start) and whenever the setting is read or changed, keeps the last answer, and asks again without waiting when a run starts on an answer older than five minutes; a run whose workspace has no explicit setting starts without the tools while that answer is unknown. Turning the tools on explicitly still needs an image that declares them; turning a bot on needs its workspace on. An explicit choice made before this amendment keeps its effect: a migration marks every bot of an already-enabled workspace that had no row as off, since under the earlier rule it was off. The workspace page states that the tools are on by default on a capable image, shows whether the workspace's state is the default or a choice, and shows decision 10's warning whenever they are on. The setting stays frozen in `runs.config_json` (decision 1).

A2. **The agent chooses the tool by what it acts on.** A run that froze `lcu-v1` gets this rule in its system prompt's fixed guidance; every other run's prompt is byte for byte what it was:
   - web content, anything that opens in Chromium, uses the browser tools (`mcp__browser__*`), which keep the browser's approvals, egress checks, tab leases and screenshots;
   - a native application window on the shared desktop uses `mcp__desktop__js` (`mcp__desktop__js_reset` restarts its JavaScript session);
   - the desktop tools never drive Chromium or a web page: no clicking, typing into or capturing the browser window with them; when an application hands off to a web page, the bot continues with the browser tools;
   - inside desktop code, accessibility actions on elements are preferred over raw pointer and keyboard input, and the bot captures the window it works on, because raw input waits for the whole shared screen (A3) and accessibility actions do not.

   The rule is guidance, not a refusal: the hook does not deny a desktop call that names the browser. The scan labels such a call `browser` (code naming Chromium, Chrome or the browser window) and the label is recorded on `tool_call`, so following the rule is measurable as the share of desktop calls labelled `browser`. The upstream descriptors stay unchanged (decision 7). Changing the default prompt guidance is a strategy change: its paired evaluation is pending, and nothing claims the guidance makes a bot better.

A3. **Focus-free calls share the screen; raw input and focus changes take it alone** (Accepted 2026-10-18; replaces the lock sentences of decision 6). Every desktop call holds a lease on its workspace's shared screen from the Gateway (`POST /internal/runs/:id/desktop-lock`), taken by the proxy at dispatch, renewed while the call runs, released at its result and expiring 15 s after the last renewal if the proxy dies. A lease has one of two modes, chosen by the proxy from the call with the scan of decision 2:
   - **shared** for `js_reset` and for `js` code whose labels are all among `read`, `capture` and `a11y` (the accessibility actions named above, in camel or snake case). Shared leases of any number of bots and runs coexist.
   - **exclusive** for every other `js` call: `input`, `input <phrase>`, `launch`, `clipboard`, `file`, `network`, `opaque`, `browser`, and code with no label at all. When the scan cannot place a call, it takes the exclusive lease (fail safe). An exclusive lease is granted only when no other lease is held, and while it is held no other desktop lease is granted and no browser lock *acquire* of any run is granted, so no browser action, and no browser window, starts during raw desktop input. An exclusive request that has to wait blocks new shared leases, and waiting exclusive requests are served in arrival order, so a stream of shared calls cannot starve it.
   - The proxy waits for a lease another call holds, polling, for up to 30 s, then answers with a busy message and dispatches nothing. A human hold refuses every lease and every renewal with the existing wait message, and an in-flight call is interrupted as in decision 5; the takeover epoch fence is unchanged.

   Not covered, and accepted as residual: a browser call already in flight when an exclusive desktop call starts is not waited for, because its lease spans the run rather than the call; a shared call whose effect makes the application open a window can move the focus during another bot's exclusive call; a bot's own shell (`xdotool`) is outside the lease altogether. A5 records the input these produce; nothing here prevents it. A per-region or per-window lock was rejected: what conflicts is the one pointer and the one focus, not pixels, and the window a call targets cannot be read reliably from its code. The shared set grows only with evidence: a runtime method shown on the exact pinned runtime, by the input record, to send no raw input may join `a11y`; until then `click`, `type`, `setValue`, `focus` and the rest stay exclusive. Like the screen regions, the lease is a soft distinction against mistakes between bots, not a boundary (ADR-0004).

A4. **Every desktop network denial is recorded.** A denial from decision 2, a hard deny or a locked workspace's unlisted public host, writes a `log` event with `source: "desktop"`, `op: "egress_denied"`, `level: "warn"`, the `host`, the `kind` (`unreadable`, `hard_deny` or `not_in_allowlist`), the `reason`, and the `toolName` and `toolUseId` of the call it refused; the URL itself is not stored, since it may carry a token. When the Gateway stores that event it appends one audit row `egress.desktop_denied` (actor `bot:<id>`, target the host, the run id and the reason): the owner accepted a denial in place of an ask, and the record takes the place of the decision an ask would have left (an addition to ADR-0031 decision 11's audit record). The run screen shows each denial as a story step naming the host and counts them at the top of the story; the technical log row says what was denied; the Activity card's opened record counts the denials and names the hosts.

A5. **The X input record (decision 4, option D) is built.** The variant image installs `xinput` and names its reader in `DESKMATES_DESKTOP_INPUT_RECORDER` (`stdbuf -oL xinput test-xi2`, the display's XInput2 raw events, which carry XTEST input too; this replaces the RECORD-extension helper decision 4 sketched, since a packaged reader exists). The proxy runs it for its lifetime and counts raw key presses, button presses and motion events, and nothing else: no key codes, no coordinates, so typed text never reaches the ledger. Each event counts towards every call of this run that is open when it arrives. At a call's result the proxy posts a `log` event `source: "desktop"`, `op: "input_record"` with the `toolUseId`, the lease `mode`, `keys`, `buttons`, `motions` and whether another call of the run was open. Because an exclusive lease is the only one open in the workspace, an exclusive call's counts are its own input plus any input from outside the lease; a shared call's counts should be zero, and a nonzero count is the evidence A3 needs before it moves a method. An image without the reader records nothing. On 2026-10-19 the reader observed real XTEST key, button and relative-motion events. `--root` produced `BadAccess` on this runtime, and stdout needed line buffering. The per-call T2 uses an explicit XTEST input in the LCU kernel; the normal native form is separately checked by its saved bytes. This does not establish that every upstream accessibility method emits raw input.

Redistribution stays undecided (decision 12): the variant is built locally only and never published.
