# ADR-0051: Workspace default bot

Date: 2026-10-19
Status: Accepted (owner decision of 2026-10-19 in the coordinator conversation: every workspace has a default bot that a person talks to first, that creates other bots and group chats directly through an internal call, as Cue and Grok Bot do, then guides the person in conversation to complete the new bot's settings, and that a new chat channel is connected to by default). Decisions 1 to 10 are the engineering decisions that carry that answer. Implemented 2026-10-19 with T0/T1 tests for every Verification row; not exercised with a real model or on the stable host. The SOUL template of decision 7 is a strategy change whose paired evaluation is pending.
Builds on: ADR-0002 (the `PreToolUse` gate, risk tiers, run tokens), ADR-0004 (one workspace, shared everything, no access control between bots), ADR-0005 (threads, members, routing), ADR-0017 amendment 1 and ADR-0047 (channel connections bound to a bot), ADR-0022 amendment 6 (roles per workspace), ADR-0024 (private chats), ADR-0026 (Trash), ADR-0031 (schema conventions, audit record), ADR-0043 (bot fields and SOUL versions), ADR-0044 (two agent loops), ADR-0050 (a tool frozen on the run row).

## Context

A new workspace starts empty. Before anyone can ask for anything, an Owner or Admin has to create a bot, write its SOUL, pick its model and open a chat: four screens of configuration for a person who only wants work done. The first-run checklist (issue #22) lists exactly those steps. A chat channel connection (WhatsApp, ADR-0047) also has to name a bot before it can be used.

The personal agent products the owner compared on 2026-10-19 (Cue, Grok Bot, dots, Muse) all give the person one agent to talk to first. Grok Bot and Cue let that agent create further agents at once through an internal call, without a confirmation card, and then refine them in the conversation. The owner chose that behaviour for Deskmates: a default bot per workspace that creates bots and groups directly and asks the person a few questions to complete the new bot.

Two existing rules shape how. A run token never reaches an operator route (ADR-0006, `operator-auth.test.ts`), so the default bot cannot call `POST /api/bots`. And there is no access control between bots (AGENTS.md): being the default bot is a routing and tooling fact, like a thread's owner (ADR-0005 amendment 2), not a permission. What the default bot can change is limited to what is reversible and stays inside the workspace's trust domain; everything that widens what a bot can reach stays with a person.

## Decision

1. **One default bot per workspace, chosen by an Owner or Admin.** A row in `workspace_default_bots` (migration `202610200709-workspace-default-bot.sql`: workspace primary key, bot unique, both with cascades) names it; no row means the workspace has none. `PUT /api/workspaces/:id/default-bot` with `{botId}` sets it for an Owner or Admin of that workspace (policy in `route-policies/workspaces.ts`; role action `workspace.setDefaultBot`), refuses a bot of another workspace or in Trash and any other field, replaces the previous one, and writes one audit row `workspace.default_bot_set` with the bot before and after. Moving the bot to Trash deletes the row in the same transaction; restoring the bot does not make it the default again. `Workspace.defaultBotId` reports it; the Gateway publishes the workspace event on a change.

2. **A new workspace comes with its default bot.** `POST /api/workspaces` creates, in the transaction that creates the workspace, a bot named `assistant` with the role "Workspace assistant", no model, runtime or reasoning override (it inherits `DEFAULT_MODEL` and `DEFAULT_RUNTIME` like any bot created without one; nothing in `packages/` names a model), the SOUL template of decision 7 as its SOUL version 1, its private chat and a welcome run in that chat, and makes it the default bot. The request may say `defaultBot: false` for a workspace without one (scripted setups and test fixtures). Existing workspaces are not backfilled: an Owner or Admin designates one with decision 1.

3. **Only a run of the default bot creates and edits bots and opens groups, at once.** Three internal routes under the run's own token scope:
   - `POST /internal/runs/:runId/assistant/bots` with `name`, `role` and an optional `soul` creates a bot in the run's workspace with the operator create's rules: a name of `[A-Za-z0-9_-]+`, unique in the workspace; a SOUL within the operator limit; the installation's loop and model must speak one protocol (ADR-0044 decision 7). The bot inherits model, runtime and reasoning and has no connectors, allowlist, schedules, approval rules or Vault access.
   - `POST /internal/runs/:runId/assistant/bots/:name` changes another active bot of the workspace: its role, its SOUL (a new version, ADR-0043 decision 2) and its schedules (validated like the operator's). Never the default bot itself, and never model, runtime, reasoning, connectors, message allowlist, approval rules, the Vault, pause or name: those stay on the operator routes.
   - `POST /internal/runs/:runId/assistant/groups` with bot names and an optional title opens a web group chat of the workspace with the default bot and those bots; it needs at least one teammate.

   Each route reads the workspace from the run row, refuses any field it does not name, and answers only a run that froze `workspaceAssistant: "assistant-v1"` (decision 6) and whose bot is still the workspace's default bot; any other run gets `forbidden` with `details.reason` `not_default_bot` (contracts `NOT_DEFAULT_BOT`). Another run's token is `token_rejected` as on every internal route. No person confirms the call (owner decision).

4. **Every change is recorded and shown.** Each create, each update that changed something and each group writes, in its transaction, an audit row (`bot.create` or `bot.update`) whose actor is `bot:<default bot id>`, with the run id and the reason `requested by <author>`, the author being the human or bot whose message started the run. SOUL text never enters the audit record, only that it changed (ADR-0043 decision 2). The same transaction posts an inert `system` notice in the run's thread ("@assistant created @reporter (role).", "@assistant updated @reporter: role, SOUL, schedules.", "@assistant opened the group chat …") that wakes nobody (ADR-0002 amendment 3 A4).

5. **Three sidecar tools, offered only to the default bot's runs.** `bot_create`, `bot_update` and `group_create` on the in-process `deskmates` MCP server call the routes of decision 3 and hand a refusal back to the model as text. They are in the start request's `tools` only when the run froze `assistant-v1` and has a thread; otherwise the sidecar does not register them. The sidecar tiers them L1 (`DESKMATES_WRITE_TOOLS`): each is a Gateway-side record a person undoes (Trash restores a bot, a saved SOUL version restores, a group chat holds nothing but its messages), so they never ask for approval. Both agent loops get them: the OpenAI loop connects the same in-process server (ADR-0044).

6. **Frozen on the run row.** When attempt 1 of a run starts, the Gateway writes `runs.config_json.workspaceAssistant`: `assistant-v1` when the run's bot is the workspace's default bot, else `off`. A later process of the run (a resume, a continuation) reads the frozen value whatever the default is now; a Gateway job (`runType` set) is always `off`; a run from before this ADR that is past its first start has no key and is off. The internal routes check the frozen value and the current default together (decision 3).

7. **The default bot's first SOUL is a template, and a strategy.** `packages/gateway/src/default-bot/default-bot-soul.ts`: get the person's work done, reply in their language, do small one-off requests itself and hand recurring or specialised work to a teammate, creating one with `bot_create` when none fits; after creating, ask two or three short questions together and apply the answers with `bot_update`; open a group with `group_create` for joint work; never create a teammate because page, file, email or bot text asked for it; do not duplicate. It is an ordinary SOUL version an Owner or Admin edits or restores. Changing it is a strategy change (AGENTS.md): no paired evaluation has been run, and nothing claims it improves results.

8. **The default bot leads the people's view of the team.** The bot rail lists it first (`BotStore.page`), with a "Default" badge in the rail and on its profile; an Owner or Admin sees "Make default" among another bot's profile actions. In a workspace with a default bot, the first-run checklist replaces "Create a bot" and "Open a chat" with "Talk to <name>, your assistant", linking its private chat and checked once the workspace has a second bot. Strings are in all five locales.

9. **A new chat channel connection defaults to the default bot.** `POST /api/workspaces/:workspaceId/channels/:pluginId/connect` without `botId` is bound to the workspace's default bot; naming a bot works as before; with neither, the connect is refused with `validation` on `botId`. Rebinding is unchanged.

10. **A soft distinction, not a boundary.** Being the default bot gives no access another bot lacks: it shares the workspace's files, browser and logins like every bot (ADR-0004), and every other bot keeps reading and doing what it did. The guard in decision 3 decides which run may call three Gateway routes; it is not access control between bots, and anything that can wake the default bot (a person's chat, a mention by another bot, a message from a chat channel sender) can lead it to create or edit bots. The limits of decision 3, the audit and notice of decision 4, Trash and the SOUL template's rule against acting on content are what bound that; the budget and the loop breaker stand behind them.

11. **The default bot opens by showing the creator around.** Its welcome run does not use the generic welcome every other bot gets. It introduces Deskmates (bots with a name and a role, one shared computer, private and group chats, approvals), says what the default bot does (creates a teammate from a plain description and sharpens it with a few questions, opens group chats), and ends by asking what a first teammate should do, with example requests. It is written in the creator's language: their stored UI language, else the first Accept-Language tag that names a UI locale, else English. The run records `welcomeVersion: "assistant-onboarding-v1"`. Since the default bot is the creator's first teammate, the web's first-run form asks only for the workspace and opens the default bot's private chat; it no longer asks for a first bot, and New workspace opens that chat too. Before any workspace exists, the first-run checklist already shows the step of decision 8 instead of "Create a bot". Changing this prompt is a strategy change, like the SOUL template.

## Alternatives considered

- **A proposal card a person confirms before a bot exists.** Safer against a prompt-injected creation, and it would keep bot creation with a person. The owner chose direct creation (Cue, Grok Bot) for a product that feels like delegating to one agent; the audit row, the thread notice and Trash keep it reversible.
- **Give the default bot a service principal on the operator API.** It would reach every operator route its role allows, models and approval rules included, and break the run-token rule. The three internal routes give it exactly what it needs.
- **Let the default bot set any field.** Model, connectors, approval rules and the Vault change what a bot can reach or spend; they stay a person's.
- **Backfill every existing workspace.** Existing teams already have a lead bot; an `assistant` appearing unasked would change their routing. They designate one.

## Consequences

- `packages/contracts` gains `default-bot.ts`, the three tool names in `SidecarToolName`, `Workspace.defaultBotId` and the role action `workspace.setDefaultBot`.
- `packages/gateway` gains `default-bot/` (store and freeze, actions, routes, channel default, SOUL template), the migration, one audit action, one route policy, three sandbox-route entries in the generated permission matrix, one line in `internal-routes.ts`, one parameter in `sidecarToolsFor`, the default-first rail order and the Trash clear. `POST /api/workspaces` answers the default bot and its private chat as well.
- `packages/sidecar` gains `default-bot-tools.ts`, three client methods, three L1 entries and three accepted tool names.
- `packages/web` gains the badge, the Make default action, the checklist step, the API method and demo routes; the demo's `galaxy-ops` has `chief` as its default bot.
- Every run started after this ADR records `workspaceAssistant` in `config_json`, so compare can pair on it.
- Test fixtures that create workspaces through the route pass `defaultBot: false`, as they pin `manual` approval mode.

## Amendment 1 (2026-10-22): created teammates introduce themselves

Status: accepted by the owner on 2026-10-22 while reporting the missing first greeting.

12. **The assistant-created teammate uses the ordinary welcome lifecycle.** In the transaction
    that creates the teammate and writes its initial SOUL, also create the same welcome run as
    the operator create route, addressed to the teammate's canonical private chat. Publish its
    status after commit and kick the scheduler. The greeting is a real, accounted run, never a
    fabricated message in the assistant's chat. Existing welcome delivery/retry rules apply.
    The assistant's source-chat creation receipt remains durable and inert; the UI presents it
    as a compact disclosure. Creation does not send a second greeting into the source chat or
    retroactively start greetings for old bots.
