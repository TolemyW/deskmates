# v0.7.3

2026-10-16, **v0.7.3 activated** at 21:01 Asia/Shanghai, replacing v0.7.2 half an hour after it.
Source `b121c256886c93abd69a6f4eca35adacbd43fde7`: one change, the sandbox provider moves a
workspace's egress proxy back to its pinned address on attach. Release workflow run
`38903922276`; shipped with `LOCAL_BASE=1` and `STABLE_HOST`; base, workspace and egress images
unchanged from v0.7.2 (same content tags, rebuilt offline).

**Why a patch within the hour.** The dockerd restart that fixed the address pools
(`2026-10-16-v0.7.2.md`) restarted every container, and Docker handed each workspace network's
addresses out in start order: in all five live workspaces the workspace container came back on
`.2`, the address its `/etc/hosts` pins for `egress-proxy`, and the proxy on `.3`. Every run then
failed at `attach` with "workspace egress-proxy address is missing or stale" (first seen 20:37 in
one workspace's chat; confirmed on all five by inspecting the pins). The pin cannot change on a
running container, so v0.7.2 could not recover by itself and a by-hand `docker network
disconnect`/`connect` was the only way out. v0.7.3 makes `attach` do that: the workspace leaves
the network while it holds the pinned address, the proxy is reattached there with its alias,
the workspace is reattached with its own aliases; nothing is recreated. A host reboot would have
caused the same thing, and `live-restore` only covers daemon restarts, so the fix is needed
regardless of the daemon change. T0 `sandbox-docker/src/docker-provider.test.ts` covers the three
cases (displaced workspace, free pinned address, pin not obtainable).
