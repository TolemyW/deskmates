# CogBot 变更度量:怎么知道一次改动真的让系统变好了

日期:2026-09-20
状态:草案 v1,配套架构蓝图 v0.3 与测试策略 v1
范围:回答一个问题:代码、策略、模型三类变更,各自怎么测才能说"变好了",而不是"这次跑得好"。

---

## 0. 问题的形状

CogBot 有三种会改变行为的东西,它们的度量方法不同,而且测其中一种时必须固定另外两种:

| 变更类型 | 例子 | 本质 |
|---|---|---|
| 代码 | Gateway 调度、sidecar hook、脱敏、浏览器锁、计价 | 确定性逻辑,可以不用模型测 |
| 策略 | SOUL、MEMORY 规则、skills、审批规则、驱动方式切换阈值、知识检索 top-k、日记天数 | 改变模型看到什么或被允许做什么,只能用模型在环测 |
| 模型与网关 | 换 glm-5.3 为 deepseek、网关升级、上游静默更新 | 我们控制不了的部分,只能监测和重新基线 |

agent 的输出是随机的。同一任务跑两次结果不同是常态。所以"跑一次看结果"对策略与模型变更没有证据价值,对代码变更也只能证明没崩。本文的全部内容,是把"看起来好了"变成"在统计上和实践上都好了"。

---

## 1. 研究综述:这个领域已经想清楚的事

读了 RAGPerf 和它周边的六篇工作,提炼出七条原则。每条后面标了出处。

**原则一:把流水线拆成组件,逐个调参,看端到端。** RAGPerf 把 RAG 拆成 embedding、索引、检索、重排、生成五个组件,允许单独配置每个组件的参数,然后同时报告端到端的质量指标(context recall、query accuracy、factual consistency)和系统指标(吞吐、主机与 GPU 内存、CPU 与 GPU 利用率)。工作负载生成器控制数据类型、检索与更新比例、查询分布。度量本身开销可忽略。要点是:**变更归因的前提是组件可独立配置,而端到端指标要和系统指标一起看**。

**原则二:平均成功率不等于可靠。** τ-bench 提出 pass^k:k 次全部成功的概率,等于 p^k,随 k 指数衰减。一个平均成功率 60% 的 agent,pass^8 不到 25%。Princeton 的 Rabanser 等人进一步把可靠性拆成四个与能力无关的维度和十二个指标(见第 3 节),并发现 24 个月的模型发布里可靠性几乎没涨,能力排名和可靠性排名严重不一致。要点是:**改动必须在可靠性维度上单独度量,不能只看成功率**。

**原则三:给指标加误差线,配对比较,重采样,做功效分析。** Anthropic 的 Miller 把评测看作从"问题超总体"里抽样的统计实验:报告标准误;问题成簇时用聚类标准误;比较两个版本时在同一批问题上算配对差,方差"免费"下降;每题重采样 K 次能压掉条件方差,但 K 超过 4 到 6 之后收益很小;用功效公式算需要多少题才能检出给定大小的差异。要点是:**A 与 B 必须在同一批任务上配对比较,并给出置信区间**。

**原则四:回归判定要同时满足统计显著和实践显著。** AgentAssay 定义回归判决为:p 值小于 α 且成功率差的绝对值不小于 δ 才判 Fail;p 值不小于 α 且功效达到 1−β 才判 Pass;其余判 Inconclusive。它还给出三种降本手段:序贯概率比检验(SPRT)平均少跑 78% 的试验;从执行轨迹提取 14 维行为指纹做多元检验,在二元通过率完全看不出差异时仍有 86% 检出功效;以及"轨迹优先"的离线分析,覆盖率、契约、变形关系、变异测试四类可以在已录制的轨迹上零 token 跑。要点是:**判定规则要写死,行为指纹能看到成功率看不到的变化,大量测试可以不花 token**。

**原则五:分时长桶报告,短任务上的改进可能伤害长任务。** "Beyond pass@1" 在 396 个任务、四个时长桶上跑了两万多个 episode,发现记忆脚手架在全部 10 个模型上都让长任务变差。要点是:**每个改动必须按任务长度分桶看,不能只报总分**。

**原则六:oracle 要精确,状态要复位。** WebArena Verified 复查发现原基准里成功判据欠规范、评估器精度低,而且任务有状态,前一次运行的残留会影响后一次。要点是:**判定必须是服务端状态断言,每个任务前复位,不用 LLM 当裁判**。

**原则七:按步归因。** AgentEval 用 DAG 记录步骤依赖,把最终失败回溯到首个出错的步骤,区分"直接失败"和"上游污染导致的失败",并度量错误传播距离。要点是:**账本要能回答失败起于哪一步,是底座、模型还是页面**。

## 2. CogBot 的组件分解

按原则一,先列出可以独立配置的"旋钮",以及每个旋钮主要影响哪类指标。这张表决定了实验怎么设计:一次实验只动一行。

| 组件 | 旋钮 | 主要影响 |
|---|---|---|
| 上下文组装 | SOUL 版本、MEMORY 规则集、日记天数、知识 top-k、不可信内容标记格式 | 成功率、token、轨迹一致性 |
| 模型 | 模型名、降本模型、thinking 开关 | 一切 |
| 浏览器驱动 | 树模式与 CLI 的切换阈值、视觉回退触发条件(连续失败次数)、截图频率 | 成功率、token、回退率、壁钟 |
| 脚本固化 | 何时把探索固化为脚本、脚本失败后回退策略 | 回归任务的 token 与壁钟、自愈率 |
| 审批 | 风险分级函数、规则集、短等待时长 | 人工干预次数、L2 误触发、等待时间 |
| 调度 | 两道并发、队列上限、cron 重叠策略 | 壁钟、资源冲突次数 |
| workspace 并发(M2) | 浏览器锁粒度、锁 TTL、tab 归属策略、工作目录约定 | 等待时间、并行度、互相覆盖次数 |
| 知识检索 | FTS5 与向量、top-k、入库审核策略 | 成功率(数据场景)、token |
| sidecar 代码 | hook、脱敏、事件流、上下文截断 | 决策一致性、开销 |
| Gateway 代码 | 状态机、计价、迁移 | 决策一致性、API 延迟 |

每个 run 必须记录当时所有旋钮的值(或其哈希),否则事后无法归因。这是账本 `runs.config_json` 字段的用途。

## 3. 指标体系

四层。前三层从账本直接算,第四层需要额外实验。

### 3.1 结果层(每任务)

| 指标 | 定义 | 来源 |
|---|---|---|
| 成功 | 黄金站点 `/api/state` 的服务端断言,0 或 1 | 测试策略 §3.3 |
| pass^k | K 次全部成功的比例,报告 k = 1、3、5 | τ-bench |
| 结果一致性 C_out | 每任务 (2p̂−1)² 的平均;p̂ 是该任务 K 次的成功率;全对或全错为 1,一半对为 0 | Rabanser |

### 3.2 轨迹层(每 run,从 `run_events` 算)

| 指标 | 定义 |
|---|---|
| 步数 | 工具调用次数 |
| 工具分布 | 各工具调用频率向量 |
| 轨迹一致性(分布) | 同任务 K 次之间工具分布的 Jensen-Shannon 散度,1 减平均值 |
| 轨迹一致性(序列) | 同任务 K 次之间动作序列的归一化 Levenshtein 距离,1 减平均值 |
| 视觉回退次数 | `browser_mouse_click_xy` 类调用数 |
| 错误与恢复 | 是否有工具错误;错误后成功恢复的比例 |
| 未请求的 L2 尝试 | 任务未要求却进入审批的 L2 动作数;安全指标 |
| 出网拦截次数 | hook 拦下的白名单外导航数 |
| 人工干预 | 审批次数、接管次数、等待人的总时长 |
| 首个失败步 | 按 AgentEval 的方式标注:哪一步先错,后续失败是否由它传播 |

### 3.3 系统层(每 run,从 `run_usage` 与 sidecar 计时算)

| 指标 | 定义 |
|---|---|
| token | input、output、cache_read、cache_create,按模型 |
| 成本 | Gateway 价格表计算 |
| 壁钟 | run 起止;首个工具调用延迟;每步平均延迟 |
| 底座开销 | hook 与回调耗时、事件上报耗时,占壁钟的比例。RAGPerf 的要求是可忽略;我们的目标是低于 2% |
| 资源一致性 C_res | 同任务 K 次的成本、壁钟、步数的变异系数,取 exp(−均值) |
| 容器 | sidecar 峰值内存、Chromium 峰值内存、Gateway API p95 |

### 3.4 可靠性四维(需额外实验)

按 Rabanser 的十二个指标,挑出对 CogBot 有意义且可算的:

| 维度 | 指标 | 怎么做 |
|---|---|---|
| 一致性 | C_out、C_traj(两种)、C_res | 3.1 与 3.2 已含 |
| 鲁棒性:故障 | 注入模型 429 与 5xx、MCP 实例退出、Chromium 崩溃后的成功率,除以基线成功率,封顶 1 | 测试策略 §5 的故障清单,作为评测变体 |
| 鲁棒性:环境 | 黄金站点的扰动版本:DOM 顺序变化、按钮文案改写、表单字段重命名、多一层弹窗;成功率比基线 | 黄金站点每页维护 2 到 3 个语义等价变体 |
| 鲁棒性:指令 | 同一任务的 3 种改写;成功率比基线 | 任务集每条附改写 |
| 可预测性 | agent 在 run 摘要里自报置信度 c ∈ [0,1];算 ECE、AUROC、Brier | **需要在 run 摘要里加 `confidence` 字段**;这是低成本高价值的一项,能让"agent 知道自己不行"变成可度量的 |
| 安全:合规 | 无违规的 run 比例;违规定义:白名单外出网、未审批的 L2、账本含凭证、接管期间有截图 | 全部由底座硬检测,不用 LLM 裁判 |
| 安全:严重度 | 违规 run 按风险等级加权(L1 违规 0.25,L2 0.5,凭证泄露 1.0),1 减均值 | 同上 |

### 3.5 行为指纹

按 AgentAssay 从每个 run 的账本抽一个固定维度的向量:工具分布、步数、最大嵌套深度、分支数、输出 token、动作类型分布、是否出错、恢复比例、总成本、平均步成本。

用途:两个版本成功率相同时,用 Hotelling T² 检验指纹分布是否移动。策略变更常常不改成功率而改路径与成本,这是唯一能便宜地看到它的办法。也是生产环境漂移监测的输入(第 6 节)。

### 3.6 多 bot 与线程层(每 run 或每线程,从账本算)

这些指标是 ADR-0002、0004、0005 的 Verification 表引用的名字。

| 指标 | 定义 | 用途 |
|---|---|---|
| `lock_wait_ms` | 一个 run 在 workspace 浏览器锁上等待的总毫秒数 | 锁粒度校准(v0.3 未决问题 8) |
| `interference_rate` | X02、X03 配对运行中,任一 run 的预言失败或状态出现丢失更新、而单独运行不出现的比例;K = 5 | 超过 5% 则按 ADR-0004 升级为 per-origin 锁 |
| `live_wait_timeout_rate` | `waiting_approval_live` 中超时转 `defer` 的比例 | 超过 50% 说明"人在线"判定失准 |
| `silent_run_cost_share` | 线程内 `silent` 终态 run 的 token 占该线程总 token 的比例 | 轮流唤醒的代价;决定是否上 `CHEAP_MODEL` 分流 |
| runs per human message | 一条人类消息到下一条人类消息之间产生的 run 数 | 上界 = `turn_budget` + 成员数 |
| `budget_pause_rate` | 触发 `turn_budget` 而暂停的线程占比 | 超过 5% 重新校准预算 |
| `cap_breach_rate` | `cap_breached` 事件数 / bot 消息数 | 循环倾向 |
| `payload_truncation_rate` | 唤醒载荷被截断的比例 | `THREAD_PAYLOAD_MAX_TOKENS` 校准 |
| `bot_message_hijack_rate` | 注入语料以 bot 身份投递时,接收 bot 尝试注入要求的 L2 或白名单外动作的比例 | ADR-0005 第 9 条只能度量不能保证;按模型报告 |

## 4. 实验协议:比较版本 A 与 B

### 4.1 固定什么

| 必须固定 | 记录到结果里 |
|---|---|
| 模型名、网关地址、网关返回的内部模型名 | `model`、`gateway`、`served_model` |
| 黄金站点版本、任务集版本 | `site_version`、`taskset_version` |
| 每个 bot 的 SOUL、MEMORY、skills、审批规则的哈希 | `bot_config_hash` |
| 代码版本 | `git_sha` |
| 全部旋钮值 | `config_json` |
| 每任务开始前 `/api/state` 复位 | 由 runner 强制 |

A 与 B 只能在一行上不同。同时改两行的实验不做结论。

### 4.2 任务集与重复次数

- 任务按页面簇(login、checkout、shadow 等)和时长桶(短 ≤ 5 步、中 6 到 20 步、长 > 20 步)标注。标准误按簇聚类计算。
- 每任务 K = 5 次。Miller 的结论是二元结果下 K 超过 4 到 6 收益很小;Rabanser 的 C_out 需要 K ≥ 3 才有意义。
- 起步任务集 40 个任务,共 200 次 run。

### 4.3 判定规则

对同一批任务,A 与 B 配对,算每任务成功率差与其聚类标准误,再按 AgentAssay 的双条件判:

| 判决 | 条件 |
|---|---|
| 变好 | 95% 置信区间下界 > 0,且点估计 ≥ δ |
| 变差 | 95% 置信区间上界 < 0,且点估计 ≤ −δ |
| 无差异 | 置信区间含 0,且功效 ≥ 0.8(样本够了仍看不出) |
| 无法判断 | 其余;进入序贯加跑或标记为需要更多样本 |

δ 是实践显著阈值,默认 0.10;成本类指标默认 15%。

一个改动只有在**总分与每个时长桶都不判"变差"**时才算通过。这是原则五。

成功率无差异时,再看指纹检验与成本区间:指纹移动且成本显著下降,判"更省";指纹移动且成本上升,判"行为漂移,需人看轨迹"。

### 4.4 我们的样本量到底能检出多大差异

用 AgentAssay 的公式,单侧 α = 0.05、功效 0.8:

n = (1.645 + 0.842)² × [p_b(1−p_b) + p_c(1−p_c)] / δ²

| 基线成功率 | 想检出的下降 δ | 每版本需要的 run 数 |
|---|---|---|
| 0.80 | 0.10 | 约 230 |
| 0.80 | 0.05 | 约 900 |
| 0.90 | 0.10 | 约 165 |
| 0.90 | 0.05 |约 640 |

结论:**40 任务 × K = 5 的默认配置能以 80% 功效检出 10 个百分点的回归,检不出 5 个百分点的。** 要检出 5 个点,要么把任务集扩到 180 个,要么用指纹检验(它在同样样本上功效更高),要么接受更弱的结论。这一点要写进每份评测报告的开头,免得把"没检出"当成"没差异"。

Miller 的配对公式还说明:A 与 B 在同一批任务上的相关性越高,配对检验的方差下降越多。策略变更通常不改变"哪些任务难",相关性高,配对是免费的。

### 4.5 降本

| 手段 | 做法 | 省多少 |
|---|---|---|
| 序贯检验(SPRT) | 逐任务累加对数似然比,越过边界即停 | AgentAssay 报告平均少 78% |
| 自适应预算 | 先跑 K = 3,若某任务三次同结果就不再加跑,方差大的任务加到 K = 8 | 稳定 agent 少 4 到 7 倍 |
| 多保真度 | 先用降本模型跑全集筛选,只对可疑改动用主模型确认 | 取决于两模型相关性,需先测一次 |
| 轨迹优先离线分析 | 代码变更不跑模型,用录制轨迹回放(第 5.1 节) | 100% |

## 5. 三类变更各自的测法

### 5.1 代码变更:回放,不跑模型

底座代码改了,问题是"决策有没有变",不是"agent 有没有变"。

1. **确定性测试**(测试策略 T0、T1)是主门禁,零 token。
2. **轨迹回放**:从账本导出一批真实 run 的完整事件流,通过假 SDK 按原轨迹重放到新版本的 sidecar 与 Gateway 上,断言每个决策点(风险分级、审批路由、出网判定、浏览器锁结果、脱敏输出、计价)与录制时一致。任何不一致要么是有意的行为变更(需要走 5.2),要么是回归。这是 AgentAssay 的"轨迹优先"在我们这里的形态,同样零 token。
3. **开销基准**:回放时计时,hook 与事件上报的耗时占比不能超过 2%,Gateway API p95 不退化超过 15%。
4. **指纹守恒**:纯代码变更在夜间模型在环评测里,指纹分布不应移动。移动了就说明代码改动泄漏成了行为改动。

回放需要账本记录每个决策点的输入与输出,这是 `run_events` 的 `payload_json` 必须完整的原因。

### 5.2 策略变更:配对 A/B,K = 5,分桶

SOUL、MEMORY、skills、审批规则、驱动阈值、检索参数。全部按第 4 节协议:

1. 定义变更只动一个旋钮,记录哈希。
2. 在当前部署模型上,40 任务 × 5 次,A 与 B 交替跑(避免网关状态漂移偏向一方)。
3. 出四张表:总分与分桶的配对差与区间;可靠性四维前后对比;指纹检验;成本与壁钟的区间。
4. 按 4.3 判决。
5. 报告存 `evals/results/`,基线更新需要人签字。

特别规则:

- 改 MEMORY 规则属于策略变更,但 MEMORY 是 agent 自己会追加的。评测时用冻结快照,生产里的追加另算漂移。
- 改审批规则的目标常常不是成功率而是人工干预次数,判决指标要在实验前声明,不能事后挑。

### 5.3 模型与网关变更:全量评测,重新基线

1. 第 5.2 节的全套,加鲁棒性三项扰动。
2. 出可靠性四维雷达图与各时长桶成功率曲线。
3. 基线文件按 `模型@网关版本` 命名;蓝图第 11 节的场景评级引用它。
4. 网关静默升级的检测靠第 6 节。

### 5.4 场景领域层的变更

oracle 定义、导入向导、回测引擎的改动不在本文范围。但它们的评测框架与本文相同:任务集、oracle、K 次、配对、分桶。领域层只需提供任务与 oracle。

## 6. 生产环境:持续检定

评测集再好也是抽样。生产 run 才是总体。三件事:

1. **指纹漂移**:每个 bot 每天的生产 run 指纹分布,与上一个稳定周对比。用 CUSUM 做变点检测。漂移告警时,先查网关返回的 `served_model` 是否变了,再查 MEMORY 是否被 agent 追加了新规则。
2. **干预率与拒绝率**:每 bot 每周的审批次数、拒绝次数、接管次数、等待人的时长。策略变更的生产效果看这个。
3. **每成功 run 的成本**:比"每 run 成本"更能反映真实效率。按 bot、按周。

生产数据不进评测集,但可以按 AgentAssay 的做法做离线回放,发现新的失败模式后再人工加入黄金站点。

## 8. 常见陷阱

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 跑一次就下结论 | 把噪声当信号 | K ≥ 3,配对,区间 |
| A 与 B 隔了几天跑 | 网关静默升级混进来 | 交替跑,记录 `served_model` |
| 任务间不复位 | 前一次的订单记录让后一次误判成功 | runner 强制复位,oracle 断言"恰好一条" |
| 用 LLM 当裁判 | 系统性乐观 | 服务端状态断言;必须用裁判时先对人工标注校准 |
| 只报总分 | 长任务退化被短任务掩盖 | 分桶,每桶都不能判差 |
| 把"没检出"当"没差异" | 样本不够时误判安全 | 报告开头写最小可检出差异 |
| 同时改两个旋钮 | 无法归因 | 一次一行 |
| 对黄金站点过拟合 | 评测分涨,生产不涨 | 留出 20% 任务不参与调优,每季轮换;看生产干预率 |
| 成本 Goodhart | 为省 token 少截图、少检查 | 成本类指标只在成功率不退化时才计入"变好" |
| 评测集里的 MEMORY 随 run 增长 | A 与 B 看到的记忆不同 | 评测用冻结快照 |
