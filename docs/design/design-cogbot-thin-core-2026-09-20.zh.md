# CogBot 设计文档与场景可行性评估

日期:2026-09-20
状态:草案 v0.1
范围:对标 xAI Grok Bot 的"常驻 bot + 自有电脑 + 浏览器操作"产品,采用薄核自研路线;并评估该设计能否支撑三个业务场景。

---

## 0. 文档说明

本文分两部分。第 1 到 9 节是设计文档,描述一个可二次开发、迭代快的技术底座。第 10 到 12 节是客观评估,逐一回答三个目标场景能否实现、平台能覆盖多少、还缺什么、主要风险是什么。

评估结论的口径是:

- **可行性等级**:高 / 中高 / 中 / 中低 / 低,指"在 6 个月内做出可交付、可度量的版本"的把握。
- **平台覆盖度**:通用底座能覆盖该场景工作量的比例,剩余部分是场景专属的"领域层"。

## 1. 背景与目标

### 1.1 对标对象

Grok Bot(2026-08 beta)的产品形态:一组有名字、有岗位的常驻 agent,共享一台账户级持久云电脑(浏览器、文件系统、终端),通过连接器接入常用 SaaS,按计划或事件自动干活,只有需要审批时才回来找人。

它的已知短板:不能自托管,模型单一供应商,记忆是黑盒且不可导出,多 bot 之间没有安全隔离,结构化任务约五分之一失败,只有桌面和 iOS 入口。

### 1.2 本设计的目标

1. 达到 Grok Bot 的八项核心能力(持久电脑、浏览器操作、常驻触发、连接器、审批门禁、多 bot 协作、记忆、客户端)。
2. 在四个短板上超越:可自托管、模型可换、记忆可查可改可导出、每 bot 独立隔离。
3. 底座尽量薄,agent 循环和浏览器操作都用标准件,自研代码集中在产品层,以保证迭代速度。
4. 与现有资产衔接:桌面端 VM、外部模型代理与 skill 市场、数据库 MCP Server 与 数据库 skill。

### 1.3 非目标

- 不做通用多公司治理平台(预算硬停、多人 RBAC、审计合规)。需要时把本底座作为 Paperclip 的一个 adapter 接入,而不是在本项目里重做。
- 不自研 agent 推理循环、不自研浏览器 DOM 理解模型。
- 不做 iOS 客户端(第一阶段)。
- 不承诺替代人做业务判断(见第 10 节)。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  客户端                                                        │
│  Web UI(首选) · 桌面客户端 · Slack/Telegram   │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTPS + SSE
┌───────────────▼──────────────────────────────────────────────┐
│  Gateway(控制面,单进程,Node.js + SQLite)                      │
│  ├─ Bot Registry     名字/岗位/SOUL.md/MEMORY.md/连接器白名单     │
│  ├─ Run Scheduler    chat 触发 · cron · webhook · bot 互唤醒     │
│  ├─ Approval Broker  Allow once / Always / Deny · Auto Review    │
│  ├─ Bot Bus          bot 之间消息,允许列表 + 中继上限             │
│  ├─ Knowledge Store  团队共享知识库(markdown + SQLite FTS)        │
│  ├─ Run Ledger       run 记录、日志、截图、token 成本               │
│  └─ Connector Hub    MCP 注册表 · OAuth 令牌保管 · Composio        │
└───────────────┬──────────────────────────────────────────────┘
                │ docker API / 内网 HTTP
┌───────────────▼──────────────────────────────────────────────┐
│  Bot Computer(执行面,每 bot 一个容器)                          │
│  ├─ Agent Loop       Claude Agent SDK,模型通过模型代理     │
│  ├─ Browser          headed Chromium,持久 profile,Playwright MCP │
│  ├─ Shell + FS       /work 挂卷持久,/home/bot 私有记忆           │
│  ├─ Runtime Tools    连接器 MCP(数据库、GitHub、Slack…)          │
│  ├─ Screen           Xvfb + noVNC,人可随时接管                   │
│  └─ Sidecar          日志、截图、网络策略、健康上报                 │
└──────────────────────────────────────────────────────────────┘
```

设计原则:

- **控制面薄**:Gateway 只做注册、调度、审批、消息、账本,不碰模型推理。
- **执行面标准件**:agent 循环用 Claude Agent SDK,浏览器用 Playwright MCP,桌面接管用 noVNC。
- **一 bot 一容器**:凭证只存在容器里的浏览器 profile 和密钥卷,Gateway 永远看不到密码。
- **一切 run 可追溯**:每次触发落一条 run,日志、截图、成本、审批决定全挂在 run 上。

## 3. 核心组件

### 3.1 Bot 定义

一个 bot 由以下文件和记录组成,全部在 Gateway 的 SQLite 和 bot 容器的 `/home/bot` 中可见:

| 项 | 位置 | 说明 |
|---|---|---|
| `SOUL.md` | 容器 `/home/bot/` | 身份、岗位、口吻、边界。人可编辑,版本化 |
| `MEMORY.md` | 容器 `/home/bot/` | 隐性规则,如"以后安静账号先不动等我看"。agent 可追加,人可删改 |
| `memory/YYYY-MM-DD.md` | 容器 `/home/bot/` | 每日工作笔记,run 结束自动追加 |
| `skills/` | 容器 `/home/bot/` | 安装的技能,来自 skill 市场或本地 |
| bot 行 | Gateway SQLite | 名字、岗位、模型、连接器白名单、审批规则、cron |

记忆三层:bot 私有文件记忆、团队共享知识库(第 3.6 节)、run 账本。三层都是明文 markdown 或 SQLite,天然可查、可改、可导出、可删除。

### 3.2 Agent Loop

- 使用 Claude Agent SDK,默认模型 `claude-opus-5`,可按 bot 切到 `claude-sonnet-5` 降本。模型请求经模型代理转发,bot 不持有上游 key。
- 每次 run 的输入是:`SOUL.md` 作为系统提示、`MEMORY.md` 和最近 3 天日记作为上下文、本次触发载荷(聊天消息、cron 说明、webhook body 或 bot 消息)、可用工具清单。
- 输出是最终回复加一份结构化"run 摘要":做了什么、改了什么文件、访问了哪些站点、待审批项、建议追加到 `MEMORY.md` 的规则。
- 会话续接:按 `(bot, thread)` 保存 SDK session id,同一线程续会话,新线程或 SOUL 变更后重开。

### 3.3 浏览器运行时

- 容器内 headed Chromium,profile 持久在卷上,登录态跨 run 保留。
- 通过 Playwright MCP 暴露给 agent:导航、点击、填表、截图、读取可访问性树。
- 两种驱动模式并存:
  - **探索模式**:agent 直接用 MCP 工具操作未知页面。
  - **脚本模式**:agent 把稳定流程固化成 Playwright 脚本存到 `/work/scripts`,下次直接跑脚本,只在脚本失败时回退到探索模式。
- 每个动作自动截图,存入 run 账本,UI 可回放。
- 人可通过 noVNC 接管屏幕完成验证码、扫码登录等 agent 不该做的步骤。

### 3.4 触发与调度

| 触发源 | 说明 |
|---|---|
| chat | 用户在 Web UI 或渠道里给 bot 发消息 |
| cron | bot 级 cron 表达式,如"每天 9:00 检查昨日数据导入" |
| webhook | Gateway 暴露 `/hooks/<bot>/<token>`,GitHub、Jira、数据库事件都可打进来 |
| bot 消息 | 另一个 bot 通过 Bot Bus 发来任务 |
| 审批回执 | 用户批准后自动续跑被挂起的 run |

调度规则:同一 bot 同一时刻只跑一个 run,后续触发排队;队列有上限,慢任务不会无限堆积;cron 触发若上一轮未结束则跳过并记录。

### 3.5 审批与权限

- 风险动作分三级:
  - L0 只读:浏览、读文件、查询。默认放行。
  - L1 可逆写:写 `/work` 文件、发草稿、非生产库写入。默认放行,可配为需审批。
  - L2 外部副作用:发消息给外部人、提交订单、删除数据、生产库写入、支付。默认需审批。
- 决策选项:Allow once / Always allow(生成规则)/ Deny。规则存 SQLite,可在 UI 查看和撤销。
- Auto Review 规则:按工具名、目标域名、SQL 语句类型、金额阈值匹配。
- run 在等待审批时挂起,SDK session 保留,批准后原地续跑。

### 3.6 团队共享知识库

这是"不同 bot 共享一个知识体系"的落点。

- 存储:Gateway 管理的 markdown 目录,SQLite FTS5 做全文索引,可选接入数据库做向量检索。
- 内容:业务术语、系统清单、schema 说明、操作 SOP、历史决策、失败案例。
- 写入:bot 在 run 摘要中提出"建议入库"的条目,人审后入库;或由指定的"知识维护 bot"定期蒸馏日记和 run 记录。
- 读取:所有 bot 通过 `knowledge_search` 和 `knowledge_read` 工具访问,不区分 bot 底座。
- 与 Paperclip 的做法对齐:知识的真相源在控制面,不在任何 bot 的会话里。

### 3.7 多 bot 协作

- Bot Bus 提供 `message_bot(to, text, attachments)`,默认关闭,需要在 bot 定义里显式声明允许发给谁。
- 每条消息带中继计数,超过上限(默认 5)直接丢弃并告警,防止两个 bot 互相唤醒死循环。
- 共享工作区:同一"小组"的 bot 可挂同一个 `/shared` 卷,交换文件。
- chief-of-staff 模式:一个 bot 负责接收人的目标、拆解、分发给专家 bot、汇总回报。这是 Grok Bot 的做法,也是 Paperclip 中 CEO 的做法,本设计只提供消息和共享卷,拆解逻辑写在 chief 的 SOUL 里。

### 3.8 连接器

| 类型 | 实现 |
|---|---|
| MCP 服务 | Gateway 维护注册表,按 bot 白名单注入容器。数据库 MCP Server 是第一个内置项 |
| SaaS OAuth | 通过 Composio 或自建 OAuth 流程,令牌存 Gateway 密钥卷,以短期 token 注入容器 |
| 浏览器登录 | 人在 noVNC 里登一次,profile 持久,后续 bot 直接用 |
| CLI 工具 | 容器镜像预装 psql、git、gh、python、node,场景镜像可扩展 |

### 3.9 可观测性

- run 账本:状态、触发源、开始结束时间、token 和费用、工具调用序列、截图、最终摘要。
- 实时:SSE 推送 run 日志到 UI。
- 成本:按 bot 按天汇总,可设软上限告警。

### 3.10 安全

- 容器隔离:每 bot 独立容器、独立卷、独立网络命名空间;可配置出网白名单。
- 凭证:浏览器 profile 和 OAuth token 只在容器卷;Gateway 数据库不存明文密码。
- 提示注入:浏览器读到的页面内容视为不可信,L2 动作必须过审批;工具输出经过统一脱敏后才进模型上下文。
- 审计:所有 L1/L2 动作和审批决定写入不可篡改的追加日志。

## 5. 一次 run 的时序

1. 触发到达 Gateway,写入 `runs` 状态 `queued`。
2. 调度器确认该 bot 无进行中 run,置 `running`,通过容器内 sidecar 启动 agent loop。
3. sidecar 组装上下文:SOUL、MEMORY、近期日记、触发载荷、知识库检索结果(按触发文本检索前 5 条)。
4. agent 执行,每次工具调用经 sidecar 转发,sidecar 按风险等级决定直接执行或挂起等审批。
5. 挂起时 run 置 `waiting_approval`,UI 推送审批卡片;决定后续跑。
6. 结束后 agent 输出结构化摘要,sidecar 追加日记、上报成本、提交知识入库建议。
7. run 置 `succeeded | failed | cancelled`,SSE 通知客户端。

## 6. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| Gateway | Node.js + Fastify + SQLite(better-sqlite3) | 单进程好部署,和仓库其余部分技术栈一致 |
| Agent loop | Claude Agent SDK | 自带工具调用、规划、错误恢复,模型升级即产品升级 |
| 浏览器 | Chromium + Playwright MCP | 标准工具层,任何模型可驱动,脚本模式可确定性回放 |
| 容器 | Docker,每 bot 一个;可选桌面端 VM | 隔离与持久化最简单;已有桌面端 VM 可直接复用 |
| 屏幕 | Xvfb + noVNC | 人可接管,零客户端安装 |
| 连接器 | MCP 优先,Composio 补 SaaS | MCP 生态已成标准 |
| Web UI | React + Vite | 与 Cogbox 前端一致 |
| 渠道 | Slack Bolt、grammY(Telegram) | 成熟 SDK,后补 |

对比放弃的选项:

- **fork OpenMausBot**:社区最活跃的开源克隆,但绑定 Electron 桌面形态,bot 跑在用户本机而非独立电脑。
- **基于 OpenClaw**:渠道和技能生态好,但共享主机模型与"一 bot 一电脑"冲突,OpenGrokBot 已因此从 OpenClaw 迁走。
- **直接在 Paperclip 上做**:治理能力完整,但约 100 万行代码、四层契约同步、严格 UI token 规则,不适合快速试错。保留为上层选项。

## 7. 与现有资产的衔接

| 现有资产 | 衔接方式 |
|---|---|
| 桌面端 VM | bot 容器可直接跑在桌面端 VM 里;桌面应用作为一个客户端 |
| 模型代理与 skill 市场 | 模型代理、用量计量、skill 市场直接复用;bot 的 `skills/` 从 skill 市场同步 |
| 数据库 MCP Server | 作为内置连接器,bot 通过它访问 Console 能力;psql 走 PostgreSQL 协议直连 |
| 数据库 skill / 数据库 guidance | 作为知识库的初始内容和 bot 技能 |
| fund-tool | 量化场景的第一个 CLI 工具样例 |
| Paperclip | 需要多人治理、预算硬停、审批链时,把 Gateway 封成一个 Paperclip adapter |

## 9. 未决问题

1. 模型代理的流式和工具调用透传是否已在模型代理中完整支持。
2. 桌面端 VM 是否允许每 bot 一容器,还是一 VM 多 bot。
3. 数据库 MCP Server 的认证是每次工具调用带身份,需要确定 bot 用什么身份。
4. 知识库是否从第一天就用数据库做向量检索,还是先 FTS5。

## 10. 场景可行性评估

评估方法:把每个场景拆成子目标,逐项标注"底座已覆盖 / 需要领域层 / 目前做不到",再给出整体等级、风险和预期效果。

### 10.1 场景一:自动化产品测试(Web 服务 + CLI 服务)

**目标拆解**

| 子目标 | 覆盖情况 |
|---|---|
| 模拟用户在 Web 上走各种场景 | 底座已覆盖(浏览器运行时,探索 + 脚本双模式) |
| 模拟用户在 CLI 上交互 | 底座部分覆盖,需补 tty 会话工具(pexpect 风格,支持交互式提示与超时) |
| 从需求或 PRD 生成测试场景 | agent 能力已覆盖,需领域层提供用例模板 |
| 断言与判定 | 需领域层。agent 自判"看起来对"不可靠,必须有显式 oracle |
| 回归可重复 | 需领域层。探索结果必须固化为 Playwright 脚本或 CLI 脚本 |
| 环境准备与重置 | 需领域层。测试数据种子、服务启停、数据库快照回滚 |
| 报告与缺陷单 | 底座已覆盖(run 账本、截图、Jira webhook) |

**可行性:高。平台覆盖度约 70%。**

这是三个场景中最贴近底座能力的一个。浏览器操作、终端、截图、定时和 webhook 都是现成的,agent 探索未知页面、生成用例、写脚本的能力也是当前模型的强项。

**必须正视的限制**

1. LLM 驱动的浏览器 agent 在结构化任务上仍有约五分之一的失败率。这意味着**不能把 agent 实时探索当回归测试**。正确做法是 agent 负责探索、生成和维护脚本,回归由确定性脚本执行,只在脚本失败时让 agent 介入诊断是"产品坏了"还是"页面变了"。
2. 断言必须由人定义或从规格派生。agent 自己判定通过与否会有系统性乐观偏差。
3. 成本:一次完整探索性测试可能消耗几十万 token。按每日回归算,脚本模式的成本可忽略,探索模式需设预算。
4. CLI 测试的难点在交互式程序、颜色控制符和超时,需要一个封装好的 tty 工具,底座里没有。

**预期效果**

- 探索性测试、新功能冒烟、用例生成:能达到一个中级测试工程师的产出,并且 24 小时可用。
- 回归测试:通过"agent 生成脚本 + 脚本执行 + agent 修脚本"的闭环,可以显著降低脚本维护成本,这是目前商业产品(如 QA Wolf、Momentic)的主要卖点,本设计能做到同等形态。
- 不能做到:替代人定义验收标准;对视觉细节和性能问题的可靠判断。

**验证指标**:脚本自愈成功率、误报率、单条用例从描述到可执行脚本的时间、探索模式发现的真实缺陷数。

### 10.2 场景二:数据平台开发(导入、治理、分析)

**目标拆解**

| 子目标 | 覆盖情况 |
|---|---|
| 连接数据库并执行 SQL | 底座 + 现有资产已覆盖(psql 直连,数据库 MCP Server) |
| 数据导入:格式识别、建表、分区、加载到 DuckLake | 需领域层。导入向导工具,封装 数据库的 COPY/CTAS 路径和 GPU 实例参数 |
| 治理:质量检查、血缘、命名规范、敏感字段 | 需领域层。规则必须先由人定义;agent 执行检查和修复建议 |
| 分析:自然语言到 SQL、结果解读、图表 | agent 能力已覆盖,但准确率取决于 schema 知识 |
| schema 与业务术语知识 | 底座知识库可承载,内容需从 数据库 guidance 和真实库导入 |
| 长任务异步执行 | 底座 run 模型支持,需补作业状态轮询工具 |
| 破坏性操作防护 | 底座审批 broker 已覆盖,需按 SQL 类型配 L2 规则 |

**可行性:中高。平台覆盖度约 50%。**

底座解决了"bot 有电脑、有 psql、有 MCP、有审批"的问题,现有的 数据库 MCP Server、数据库 skill 和 数据库 guidance 知识库让起步比从零开始快很多。

**必须正视的限制**

1. **NL 到 SQL 的准确率是上限**。在几十张表以内、有良好列注释和业务术语表的库上,当前模型可以做到大部分分析查询一次正确;在上百张表、命名混乱的库上会明显下降。知识库和 schema 注释的质量决定效果,这是领域层的主要工作。
2. **治理不是 agent 能凭空做的事**。质量规则、血缘口径、敏感字段清单需要人先定义。agent 的价值是把规则执行自动化、把异常整理成可读报告、给出修复 SQL 并等审批。
3. **数据库引擎自身处于快速迭代期**。GPU 实例是共用机器,资源冲突和引擎 bug 会被归咎到 bot。需要 bot 在报错时能区分"我的 SQL 错了"和"引擎错了",并把后者作为缺陷记录而不是反复重试。
4. 导入路径依赖 数据库的具体能力(DuckLake、parquet、GPU 模式参数),导入向导工具要和 数据库版本绑定,维护成本要计入。

**预期效果**

- 导入:给定文件和目标说明,bot 能完成格式探测、建表、加载、校验行数,人审后执行。这一步可以做到接近全自动。
- 分析:面向有术语表的业务库,bot 能回答大多数描述性分析问题并产出图表;复杂多步分析需要人参与迭代。
- 治理:能做到"规则驱动的日常巡检 + 异常报告 + 修复建议",不能做到"自动发现应该有什么规则"。

**验证指标**:导入任务一次成功率、SQL 首次正确率(对照人工基准集)、巡检报告的人工采纳率、每周节省的数据工程师小时数。

### 10.3 场景三:量化投研小组

**目标拆解**

| 子目标 | 覆盖情况 |
|---|---|
| 数据获取与入库(行情、基本面、持仓披露) | 底座 + 数据库可覆盖;数据源本身是外部依赖(AKShare、付费源) |
| 因子实现 | agent 编码能力已覆盖 |
| 回测执行 | 需领域层。必须是确定性的回测引擎,agent 只是调用者 |
| 统计校验与偏差检查 | 需领域层。前视偏差、幸存者偏差、多重检验校正必须由工具强制,不能靠 agent 自觉 |
| 研究报告与复现 | 底座覆盖(run 账本、知识库、脚本固化) |
| 小组分工:数据 / 因子 / 回测 / 风控 / PM | 底座多 bot 协作已覆盖形态 |
| 自主发现 alpha | 目前做不到可靠交付 |

**可行性:中低(如果目标是自主产出策略);中高(如果目标是投研助理小组)。平台覆盖度约 30%。**

多 bot 的岗位分工与投研小组的结构天然对应,chief-of-staff 模式可以直接映射到 PM bot。但这个场景的瓶颈完全不在 agent 框架,而在领域工具和研究纪律。

**必须正视的限制**

1. **agent 无法自证统计严谨**。模型会写出"看起来合理"的回测,却引入前视偏差或在样本内反复调参。防线只能是工具:回测引擎强制时间切分、参数搜索次数计入多重检验、结果必须附带样本外表现。这些工具不存在于底座,也不是一个 sprint 能做好的。
2. **结果幻觉风险高于其他场景**。数值结果一旦被 agent 汇总进报告,人很难核对。必须要求所有数字来自可复现脚本的输出,报告只能引用 run 账本里的产物。
3. **数据成本与质量**。免费源(如 AKShare)延迟和缺失明显,fund-tool 的设计文档已经指出持仓披露滞后一个季度。付费源需要预算和合规。
4. **合规与责任边界**。任何自动化研究结论进入实盘决策都需要人签字,系统层面要把"研究"和"交易"物理隔开,本设计不包含交易执行。

**预期效果**

- 能做到:数据管道自动维护、因子按规范实现、批量回测调度、报告生成、文献和公告的摘要、每日数据质量巡检。相当于给投研团队配了几个不知疲倦的研究助理。
- 不能做到:可靠地自主发现可交易 alpha;替代人对策略的最终判断。
- 与场景二的协同:如果投研数据全部落在同一个数据库,场景二的导入和治理能力可直接复用,这是本设计里最明显的复利点。

**验证指标**:回测任务从描述到结果的周转时间、报告数字可复现率(应为 100%)、数据管道故障自愈率、研究员满意度。

## 11. 总体结论

| 场景 | 可行性 | 平台覆盖 | 领域层主要工作 | 最大风险 |
|---|---|---|---|---|
| 自动化产品测试 | 高 | 约 70% | oracle 定义、脚本固化、tty 工具、环境重置 | 把非确定性探索误当回归 |
| 数据平台开发 | 中高 | 约 50% | schema 知识库、导入向导、治理规则、破坏性操作规则 | NL 到 SQL 在复杂库上的准确率 |
| 量化投研小组 | 中低 / 中高 | 约 30% | 确定性回测引擎、偏差校验工具、数据源、复现纪律 | 统计不严谨与结果幻觉 |

三点判断:

1. **底座本身可以在 M0 到 M3 的 14 周内做到 Grok Bot 的产品形态**,并在自托管、模型可换、记忆可查、bot 隔离四点上超过它。这一点把握较大,因为核心部件都是标准件。
2. **场景价值由领域层决定,不由底座决定。** 三个场景的差异不在 agent 能不能操作电脑,而在有没有可靠的判定工具。测试场景的 oracle、数据场景的治理规则、量化场景的回测引擎,都是"人先定规则,agent 再执行"的结构。
3. **建议的推进顺序是一、二、三。** 场景一最快出效果、验证底座;场景二依托现有数据库资产,并且为场景三准备数据底座;场景三放最后,并且以"投研助理小组"而非"自主策略发现"作为目标来立项。

## 12. 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 浏览器 agent 可靠性不足 | 高 | 中 | 探索 + 脚本双模式,脚本承担回归 |
| 提示注入通过网页内容攻击 bot | 中 | 高 | L2 动作强制审批,页面内容标记不可信,出网白名单 |
| token 成本失控 | 中 | 中 | 按 bot 日预算,脚本模式替代探索,Sonnet 承担低复杂度任务 |
| 数据库引擎不稳定被归咎于 bot | 中 | 中 | 错误分类,引擎错误走缺陷单而非重试 |
| 量化结果不可复现 | 高 | 高 | 报告数字必须来自 run 产物,回测引擎强制样本外 |
| 多 bot 互相唤醒失控 | 低 | 中 | 允许列表 + 中继上限 |
| 模型代理不支持工具流式 | 中 | 高 | M0 阶段先验证,不支持则 bot 临时直连 |
