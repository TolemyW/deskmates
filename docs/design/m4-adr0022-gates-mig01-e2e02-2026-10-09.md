### What was copied, and how

- **live**: the stable deployment's live database, WAL included. It was opened with
  better-sqlite3 `readonly: true, fileMustExist: true` and copied with the SQLite online backup
  API (36 ms, 18,194,432 bytes). As for any reader in WAL mode, SQLite took its read lock through
  the existing `-shm`. There was no write transaction and no checkpoint, and no file was added in
  `shared/data/` (listed before and after). The service was not touched; `deskmates-stable-gateway`
  was active before and after.
- **legacy**: the last pre-tenancy database, the v0.3.0 to v0.3.2 upgrade backup at schema 0027.
  It is a static file, so it was read as bytes and deserialized in memory: its WAL header was set
  to rollback mode in the in-memory copy only. It was then copied with the backup API (45 ms).
  Opening the file in place would have let SQLite create `-shm`/`-wal` files next to it. Its
  SHA-256 `6432583a…d023` was unchanged at the start, at the end and after cleanup.

The stable data is small: 1 workspace, 6 bots, 3 threads, 21 runs, 6,766 run events, 1 task
(cancelled, never accepted), 3 users, 5 sessions. It has no Knowledge documents, proposals,
connectors, approvals or cost-alert rows, and no accepted task in either copy.

## E2E-02: model-backed two-tenant gate

### Setup

Driver: `spikes/m4-adr0022-gates-20261009/e2e02-run.ts`.

- **Gateway.** A real process, `node packages/gateway/dist/index.js`, with its working directory
  in the isolated directory. Model variables come from that directory's `.env` (mode 0600, only
  the five `MODEL_*`/`*_MODEL` keys, copied from the workstation over an ssh pipe with `umask 077`;
  values never printed). All other settings come from the process environment:
  - `DESKMATES_TENANCY=multi` and `GATEWAY_SESSION_COOKIE=secure`;
  - a file-backed SQLite database in the run directory;
  - a fresh random `GATEWAY_OPERATOR_TOKEN` and `GATEWAY_SECRETS_KEY`, held in memory only; the
    workstation's key was not copied;
  - `RUN_TIMEOUT_SECONDS=900` and `DESKMATES_MAX_TURNS=20`; both were recorded in each run's
    `config_json`;
  - ports: sandbox listener 24380 (0.0.0.0); operator listener 24381 (127.0.0.1); fixture page
    24382 (0.0.0.0); fake connectors 24383 and 24384 (127.0.0.1). All ports were checked free
    first.
- **People.** The platform CLI created the people and tenants, with passwords on stdin:
  - `plat`: bootstrap Owner and platform maintainer, also Admin of B;
  - `alice`: Owner of the Default Tenant (A);
  - `bob`: Owner of the new tenant B.

  Each person signed in through the built UI's sign-in form in their own Chromium context. The
  session cookie was `__Host-`, Secure and HttpOnly. Every later request is a same-origin `fetch`
  from that page, carrying the CSRF token.
- **Per tenant.** A workspace with egress allowlist `host.docker.internal`, created by its own
  Owner. A connector named `ledger`: an ADR-0012 fake on loopback with its own credential,
  registered by `plat` through the tenant selector, because private URLs are platform
  maintenance. A bot `clerk` with `connectors: ["ledger"]` and a SOUL. A one-member thread. A
  task. The natural names `clerk`, `ledger` and the fake's receipt id `rcpt-2` are identical in
  both tenants on purpose.
- **Model run.** One message per tenant asks the bot to:
  1. read a random order code from `http://host.docker.internal:24382/ticket/<a|b>` with the
     workspace browser;
  2. `connector_validate`, then `connector_submit` (effect `external`, L2);
  3. write `<code> <receiptId>` to `/work/e2e02/delivery.txt`;
  4. reply `answer: <receiptId>`.

  No one held an event stream, so each submit was deferred ("nobody online") and the run parked.
  The Gateway was then restarted with SIGTERM and a new process started. The approvals were
  decided by alice and bob after the restart, and the runs resumed.

## Findings

- No tenant-boundary defect was found. There were 0 disclosures and 0 side effects in:
  - 64 paired cross-tenant probes (32 before and 32 after the restart);
  - 6 operator-credential requests (3 per phase);
  - 2 cross-tenant delivery-file reads;
  - 2 cross-tenant task accepts;
  - 2 connector-registration refusals.
- Attempt 1's tenant B failure came from the model upstream or the SDK (an unparseable response
  with no usage); the Gateway answered 200. Not a tenancy defect. Recorded so that repeated
  occurrences can be correlated; no fix was attempted.
- Some proxy `model_requests` rows carry no usage, while the SDK-reported `run_usage` totals
  agree with the requests that do. Whether the requests without usage cost tokens is unknown. This
  is existing ledger behaviour, reported, not changed.
- Harness defect, fixed: the event-stream check must listen for named SSE events. The committed
  driver has the fix. It was verified only without a model.
- `npm run build` at the root fails on a fresh checkout because `packages/channels` builds before
  `packages/contracts`; `npm run typecheck` builds correctly. Not investigated further.

## What this does not establish

- No owner acceptance of ADR-0022, and no permission to expose a second tenant to real users.
- No model-behaviour or reliability claim: one smoke per tenant on one model.
- Model-backed event isolation across a restart: only the model-free rerun passed, and it had
  no restart.
- A crash restart: the Gateway was stopped with SIGTERM; MIG-02's SIGKILL check covers
  migrations only.
- A connector of the real kind (connector-postgres), the integration runtime, Knowledge, the
  desktop and takeover, and SSO in the model run.
- MIG-01's file, checksum and browser-profile reconciliation (NOT RUN, see above), and MIG-04.
