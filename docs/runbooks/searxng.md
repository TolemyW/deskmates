# SearXNG for web search

How to run the self-hosted SearXNG behind the `web_search` tool (ADR-0049 decision 14) on the
stable host, beside the Gateway that `stable.sh` operates
([Stable release and deployment](stable-release.md)). What the tool does and what the Gateway
records is in [web search](../../packages/gateway/docs/web-search.md).

## What runs

One container, `deskmates-stable-searxng`, on the host network but bound to `127.0.0.1` at
`SEARCH_PORT` (default 18710), from the image `deskmates/searxng:<arch>-<hash12>` built from the
current release's `images/searxng` ([image README](../../images/searxng/README.md)). Only the
Gateway's search proxy calls it; no workspace container can reach it. It is not part of the
Gateway's systemd unit and restarts with Docker (`--restart unless-stopped`).

State under the stable root, `searxng/` (0700): `env` (0600) holds `SEARXNG_SECRET`, generated by
`init` and passed with `--env-file`; `cache/` is SearXNG's cache.

## Turning it on

```
releases/<v>/scripts/stable/stable.sh searxng init     # secret, cache, image (needs the registry once)
releases/<v>/scripts/stable/stable.sh searxng start
# shared/.env: SEARCH_URL=http://127.0.0.1:18710, then restart the Gateway
releases/<v>/scripts/stable/stable.sh searxng status
```

With `SEARCH_URL` configured, new bot runs inherit web search on unless their workspace
explicitly disables it (owner amendment 2026-10-22, ADR-0049 amendment 1). Change this beside
Network policy in Tools & network. Existing runs keep their frozen setting. Query text leaves
the host for the public engines SearXNG queries, from locked workspaces too. The owner changed
the default; the paired quality comparison remains pending.

## Upgrades and troubleshooting

- After activating a new release, `searxng start` recreates the container when the release's
  image differs, and is a no-op otherwise. `status` says when the running release is not the
  current one.
- `searxng init` builds the image only when the current release's tag is missing; a build log is
  kept in `searxng/logs/build.log`.
- `start` waits for `/healthz` (`SEARXNG_HEALTH_TIMEOUT`, default 60 s) and prints the container's
  last log lines when it does not answer.
- The Gateway answers `operation_unavailable` with reason `unreachable` when nothing listens at
  `SEARCH_URL`, and `answered_malformed` when the instance answers HTML (JSON output switched off).

A healthy `/healthz` does not prove that public engines answer. Check a public exact-name query
in JSON mode and inspect both `results` and `unresponsive_engines`. Empty results with timeout,
CAPTCHA or rate-limit errors are an outage, not proof that the subject is absent. The Gateway
reports `engines_unavailable` for that case. Choose usable engines in the instance's settings;
keep a backup and preserve operator overrides across container recreation/upgrades. Do not
copy a secret-bearing settings file into the source tree.

The private lab record "Chat polish and search grounding — 2026-10-22" records a live backend
check and the operator's backed-up addition of Mwmbl after the default engines failed.
